## 结论

1. **控制器 v2：测试集上查出的三个问题，修好了一个半。**
   - 看图增益饱和是真问题，改成"有图的空间直接查有图数据的准确率表"之后，N9 归因于饱和的 6 道题（32K）确实救回来了；但新表也改变了其他约 70 道题的选择，净值为零。N9 报告说"改法很直接"过于乐观（§1.3）。
   - 净收益来自另一条规则：有图的空间里问画面细节（视觉线索或位置线索）时不选 L0。开发集 81.2% → 81.7%，测试集事后重放 81.6% → 81.9%（+10 / −5，n.s.），收益都在 MemLens。
   - 按回答模型重新标定准确率表**没有用**（负结果）；按回答模型调 λ 才是有效的旋钮：λ 从 30 降到 15，三个回答模型上都补回了与总是 L2 之间的大部分差距，成本仍比总是 L2 低 16–24%。
2. **门控在真实流量上**：把混合流里构造的无关查询换成 WildChat 里真实用户消息的第一句，门控误送去检索的是 10.5%（N9 构造的混合流 17.3%），混合流成本比总是检索低 46%（N9：41%）。"要不要想起"这一半结论在真实消息上成立，构造的混合流反而偏难。零样本 LLM 路由仍几乎不误召回（0.7%），但会把 3% 的记忆题放到 L0。
3. **写入路径**：对账提示分清"范围不同""现实变了""说错了"，并把新事实出自的那句话交给对账模型（只看抽取出的"Mia 31 岁"，分不清是更正还是过了生日）。同一段新编对话重复 5 次，三类都对（5 / 5）；N9 的提示同样跑 5 次，"说错了"0 / 5，"范围不同"3 / 5。
4. **遗忘不再误伤别的会话**：Agent 的回答缓存按会话归属，遗忘只清受影响会话的缓存（演示回放偶发失败的原因）。两次完整回放里，遗忘之后的检查都通过；各有一项没过，原因与遗忘无关（§3）。
5. **外部基线 Mem0**（开源版 2.2，同一个抽取模型、向量模型、回答模型与判分）：LoCoMo 200 题 80.5%，LongMemEval 100 题 83.0%。CueMem 的 L1 在 LoCoMo 上与它打平（81.0%），在 LongMemEval 上高 9 个点（92.0%，+13 / −4，p = 0.049）；控制器两边都高（85.5%、92.0%，p ≈ 0.08）。Mem0 的写入（名义成本）是 CueMem 的 2.3–2.9 倍。它找得到证据会话（会话召回 99–100%），丢分在时间推理、知识更新与助手说过的细节：只增不改的抽取把这些信息丢了。
6. **评测可信度**：
   - 换一个判分模型（deepseek-flash）重判 12,835 条回答：一致率 94.7–97.9%（κ 0.82–0.93），方法排序基本不变（Kendall τ 0.87–1.0）。17 组关键对比只有一组的显著性变了：LoCoMo 上 L1 低于全上下文（p = 0.038 → 0.31）。
   - 同一配置关掉缓存重跑：准确率变化不超过 0.9 个点，逐题翻转 3–4%。相差 1 个点左右的比较都在波动之内。
   - 人工抽检 50 条已备好，等人工勾选。
7. **工程**：本地向量库被占用时给出能看懂的报错；Qdrant 服务端按 payload 建索引；HTTP 接口与界面可选访问令牌。延迟基准：读路径的本机部分在本地模式下随规模线性增长（4.6 万个检索单元时约 1.08 s），换 Qdrant 服务端后是 91 ms；单进程的并发吞吐量从 8.7 提高到 55 次 / 秒。

### 1.4 换回答模型：重新标定没用，调 λ 有用

N9 发现：控制器的"各档准确率"按主回答模型（deepseek-flash）统计，换成小模型后照样大量选 L1。N11 试了两种补法（LongMemEval 100 题、LoCoMo 200 题的测试子集，事后分析）：

1. **按回答模型重新标定准确率表**（只换表，门控与推理类型模型不变）：
   - 用开发集上 qwen3.8-flash 的结果标定：LongMemEval 93% → 89%，LoCoMo 76.5% → 74.0%，**更差**。这个模型上 L1 与 L2 在多数推理类型上差得很小，新表让控制器几乎只选 L1（L2 4–5.5%）。
   - 在测试子集上两折交叉标定：与不标定持平（±1 题）。
2. **按回答模型调 λ**（同一个 v2 模型）：

| 回答模型 | 数据集 | 总是 L1 | 总是 L2 | v2，λ = 30 | v2，λ = 15 | λ = 15 比总是 L2 省 |
|---|---|---|---|---|---|---|

| | LoCoMo | 77.5% | 82.5% | 80.0% | 82.0% | 23% |
| qwen3.8-flash | LongMemEval | 93.0% | 93.0% | 93.0% | 93.0% | 19% |
| | LoCoMo | 74.0% | 80.5% | 76.5%（+2 / −10） | 79.0%（+1 / −4） | 20% |
| deepseek-flash（主） | LongMemEval | 92.0% | 96.0% | 92.0% | 95.0% | 18% |

括号里是对总是 L2 的逐题胜负。这是测试子集上的事后曲线，用来说明取舍的形状，不是调出来的结果：默认 λ 仍是 30。**结论：准确率表的形状（哪类题 L2 更有用）跨回答模型大体通用，回答模型越弱，L1 与 L2 的差距越大，"多花多少钱换一个正确答案"的旋钮就该放得越低。** 部署时 λ 应按回答模型设置，这比重新标定表更稳。

### 1.5 门控在真实流量上（D-057）

N7 / N9 的混合流里，不需要记忆的查询是构造的（Dolly 的人工指令 + 生成的同话题问题）。这里换成 WildChat-1M 第 1 个分片里真实用户消息的第一句：英文、无毒、没有打码，10–300 个字符，按文字去重后 14,319 条候选，随机抽 1,750 条。会话的开头不可能指向之前的会话，所以都不需要长期记忆；其中 23% 带第一人称（"我的""帮我"），比 Dolly 更难。每条配一个测试集的记忆空间跑探针，用冻结的控制器离线判定；同一批消息再让零样本 LLM 路由（B6z）判一遍作对照。

混合流照 N9 的做法：测试集的 1,750 道记忆题占 20%，其余是无关查询。下表只换无关查询的来源，记忆题与控制器不变。

| 无关查询 | 门控误召回 v1 / v2 | 门控 AUC | 混合流每千条成本（v1） | 比总是 L1 省 | 零样本 LLM 路由：误召回 / 记忆题放到 L0 |

| **WildChat 真实首句** | **10.5% / 9.9%** | 0.994 | $0.83 | **46%** | 0.7% / 3.0% |

- **真实首句上的误召回介于 Dolly 与生成题之间。** N9 的混合流有一半是专门生成的"同话题但不需要记忆"的问题，比真实流量难；"混合流里比总是检索省 41%"在真实消息上是 46%。

## 2. 写入路径：对账提示分清"范围不同""现实变了""说错了"

N9 的错误分析里有两个对账错误：

- "周五 6 点起"取代了"工作日 6 点半起"（两者可以同时成立）；
- 英文示例里"搬到新加坡"被标成"更正"（应是现实变了，validity 要有结束时间）。

修订（`write/reconcile.py`）：

- `correct` 只用于用户说之前记错了（"sorry, I meant…""actually it was…"），或新事实把同一件事说得更精确；搬家、换工作这类现实的变化是 `update`。
- `add` 明确包含"范围不同"的事实：工作日与周五、在公司与在家、这一次旅行与另一次。

联网测试 `tests/live/test_reconcile_live.py` 用一段新编的小对话核对三类情况（不用测试集原题）：工作日 6:30 起床 → 周五改成 6:00（范围不同，应并存）；住在上海 → 上个月搬到新加坡（现实变了）；妹妹 Mia 30 岁 → "之前说错了，是 31 岁"（说错了）。

12–14 点的联网运行里又改了两轮，过程如下：

1. **只改提示**（上面两条）：范围与搬家都对了，"说错了"仍被当成"现实变了"。原因不在提示：对账模型只看到抽取出的"Mia is 31 years old"（6 月）和"Mia is 30"（3 月），看不到用户说的"之前说错了"。只凭这两条，"过了生日"也说得通。
2. **灰区里每条新事实附上它出自的那句话**（用户的原话，最多 400 个字符）。这次"说错了"对了，但"周五 6 点起"又取代了"工作日 6 点半"：原话里的 now 让模型倒向"作息变了"，而 update 的例子里正好有"a changed schedule"。
3. **写明范围更窄的新事实是 add**，即使是新近的变化。例子用"周一在家办公"对"在公司上班"，不用测试里的说法；update 的例子改成"同样的日子换了作息"。

同一段对话重复跑 5 次（每次新目录、不用缓存）：

| 对账 | 范围不同（应并存） | 现实变了（搬家） | 说错了（年龄） |
|---|---|---|---|
| N9 的提示 | 3 / 5 | 5 / 5 | 0 / 5 |
| N11（新提示 + 原话） | **5 / 5** | **5 / 5** | **5 / 5** |

这只是一段对话、三类情况，提示又是对着它改了两轮，有过拟合这段对话的风险。它说明 N9 错误分析里的那两类错误修好了，不代表对账的整体准确率。N9 的提示在这段对话上没有复现"搬家标成更正"，那个错误来自测试集里的一个英文示例。

提示文本不在巩固指纹里，所以已有的评测空间不会因此重建（N9 可以照常复现）；代价是从零重建时，涉及对账的那部分记忆会与 N9 略有不同（D-053）。

## 3. 遗忘与回答缓存：按会话归属

Agent 的回答缓存原来按空间归属（`空间|ask`），遗忘时整个空间的回答缓存一起清掉。演示剧本回放时，遗忘之后的问题重新调用模型，偶尔答得和录制时不一样，回放检查就失败。

改成按会话归属（`空间|session:会话 ID`）：遗忘只清受影响会话的回答缓存，加上巩固、对账的缓存。新测试：在 B 会话里遗忘一条事实，A 会话的回答缓存保留，B 的清空。

演示剧本完整回放了两次（12:01 用旧的对账提示，12:09 用新的），都是 14 项过 13 项。遗忘之后的两项（S3·5 遗忘、S3·6 问妹妹的生日）两次都通过。没通过的两项与遗忘无关：

- **S1·2（第一次）**：回复守住了约束（"no leather or suede""fully synthetic"），只是没写"vegan"这个词。这条回复是 N11 之前录下、留在缓存里的，那次回放就没过。检查改成"vegan / no leather / leather-free 任一出现"；不许列出皮革、麂皮鞋的检查不变。
- **S3·4（第二次）**：问"预算比第一次聊时有什么变化"，Agent 却把上一题（找同款鞋）又答了一遍。对账结果是对的（$120 标为现实变了，$180 为当前），Agent 收到的也是这道题（消息 14 个 tokens）。这一题之前 3 次回放都通过，是回答模型的随机失误；这条回复已在本地缓存里，之后的完整回放会照样失败。

准确率 / 每千题的回答成本（不含写入）。CueMem 各方法取 N9 测试运行里同一批题的结果；题目是 N9 的分层子集（换回答模型的实验用的同一批）。

- **逐题对比**：LoCoMo 上 L1 与 Mem0 打平（+15 / −14），控制器 +18 / −8（p = 0.076）；LongMemEval 上 L1 +13 / −4（p = 0.049），控制器 +15 / −6（p = 0.078）。朴素检索在 LoCoMo 上比 Mem0 低 13 个点（+12 / −38），在 LongMemEval 上反而略高（+8 / −5，不显著）。
- **写入**：Mem0 的名义写入成本是 CueMem 的 2.3–2.9 倍：LongMemEval 100 份历史 $9.76 对 $4.32，LoCoMo 7 段对话 $0.70 对 $0.24（LoCoMo 每个会话写两遍）。Mem0 每次抽取都带上约 8.4k tokens 的提示，这部分前缀命中通义的缓存，实际花费约为名义的一半。
- **差在哪**：Mem0 检索到的记忆几乎总来自证据会话（会话召回 LoCoMo 99%、LongMemEval 100%），丢分不在"找不到"，而在记忆里没有：
  - 时间推理（LongMemEval 27 题：78% 对 L1 96%）与知识更新（16 题：81% 对 100%）。Mem0 2.x 只增不改，旧值与新值并存、没有有效期；CueMem 的事实带双时间轴，L1 还附上原话。
  - 助手说过的细节（11 题：82% 对 100%）：抽取以用户的事实为主，助手给出的具体内容被概括掉了。
  - 偏好题上 Mem0 反而更好（6 题全对，L1 对 4 题）：它的抽取专门记偏好。LoCoMo 上它在多跳（61% 对 56%）与时间题（85% 对 83%）上略高，单跳题低（89% 对 93%）。
- **运行中的修正**：Mem0 的约 5,400 次抽取里有 8 次解析失败。通义的 JSON 模式偶尔直接返回记忆列表，少了外层的 `{"memory": …}`，Mem0 就把那个会话当成"没有可记的"。OpenAI 的 JSON 模式不会返回顶层数组，所以这是换模型带来的差异：适配层补上外层，重建受影响的 7 个空间、重答它们的 70 道题（之前的 LoCoMo 79.5%、LongMemEval 84.0%；重答本身也有波动）。
- **局限**：每个数据集只跑了一次（单次运行有 ±1 个点的波动，§5.2）；Mem0 用的是 CueMem 的模型而不是它默认的 OpenAI 模型，换模型对它有多大影响没有测；Mem0 论文里的数字用的是不同的回答模型与判分，不能直接比。

协议（D-055）：

- 开源版 mem0ai 2.2.1，用它自己的流程写入与检索：每个会话调用一次 `add`（Mem0 内部一次 LLM 抽取 + 向量化 + 实体链接），检索用 `search(top_k=30)`（Mem0 默认 20），装上 spaCy 与 fastembed，让它的混合检索（语义 + BM25 + 实体加权）完整生效。
- 两个人之间的对话（LoCoMo）照 Mem0 论文的评测代码：每位说话人一个 user_id，各写一遍（自己的话是 user，对方的话是 assistant，都带名字；Mem0 2.x 的抽取提示专门说明了这种格式），检索两边各取 30 条，每条注明是谁的记忆。所以 LoCoMo 上 Mem0 的抽取调用是 CueMem 的两倍。
- 同样的模型：Mem0 的 LLM 换成 CueMem 写入路径用的 qwen3.8-flash，向量换成同一个 qwen3.7-text-embedding；回答模型（deepseek-flash）、回答提示、判分（qwen3.8-max）都与其他方法相同。
- 日期：开源版不支持 `timestamp`，抽取提示里的"观察日期"默认是运行当天。适配层把它换成会话日期，相当于平台版传了 timestamp；每条记忆标上来源会话的时间交给回答模型。
- 遥测关闭，Mem0 的配置目录放在 `data/` 下。

## 5. 评测可信度

### 5.1 第二判分模型

主判分 qwen3.8-max；第二判分 deepseek-flash（另一家的模型，非思考模式，提示与解析相同），重判 N9 四个测试集上主要方法（文字数据集 7 个，MemLens 32K 6 个、128K 4 个）的 12,835 条回答。

| 数据集 | 判分条数 | 一致率 | κ | 判对的比例：主 / 第二 | 方法排序 Kendall τ |
|---|---|---|---|---|---|
| LongMemEval | 2,800 | 97.9% | 0.91 | 87.3% / 87.9% | 0.90 |
| LoCoMo | 8,085 | 94.7% | 0.82 | 80.9% / 84.4% | 0.90 |
| MemLens 32K | 1,170 | 96.8% | 0.93 | 58.1% / 61.4% | 0.87 |
| MemLens 128K | 780 | 96.7% | 0.93 | 56.8% / 59.6% | 1.00 |

- 排序的变化都在相邻、相差不到 2 个点的方法之间（LongMemEval：L1 与 B6a，差 0.5 个点；LoCoMo：L2 与 B6a，差 0.1 个点；MemLens 32K：L1 + 看图与 B6a，差 3 道题）。
- 报告里的 17 组关键对比（L1 对全上下文、控制器对 L1 / L2、ReAct 对 L2……），方向与显著性只有一处变了：**LoCoMo 上 L1 低于全上下文**，主判分 +65 / −92（p = 0.038），第二判分 +64 / −77（p = 0.31）。另有两组原本就打平的方向翻了过来，都不显著：LongMemEval 上控制器对 L1（10 / 10 → 11 / 9），LoCoMo 上 B6a 对 L2（39 / 40 → 34 / 31）。
- 第二判分在四个数据集上都更宽松，判对的比例高 0.6–3.5 个点。它和主回答模型是同一个模型，可能偏向自己的回答，所以只用来检验结论是否依赖判分模型，不替换主判分。
- 两个判分不一致的 549 条在 `runs/eval/n11-judge2/disagreements.jsonl`（不进仓库），人工抽检时值得先看。

### 5.2 重复运行

关掉 LLM 缓存（不读也不写，N9 的缓存保持原样），在同样的记忆空间上把 L1 与控制器重跑一遍（LongMemEval 400 题；LoCoMo 1,155 题只跑 L1）。回答、L2 的规划与判分都重新调用；控制器用 v1，与 N9 相同。

| 数据集 | 方法 | N9 | 重跑 | 逐题翻转：对→错 / 错→对 | 回答文字与 N9 完全相同 |
|---|---|---|---|---|---|
| LongMemEval | L1 | 90.5% | 90.0% | 7 / 5（3.0%，p = 0.77） | 178 / 400 |
| | 控制器 | 90.5% | 90.2% | 8 / 7（3.8%，p = 1.0） | 124 / 400 |
| LoCoMo | L1 | 79.7% | 80.5% | 16 / 26（3.6%，p = 0.16） | 538 / 1,155 |

- 温度为 0，回答文字仍有一半以上与 N9 不同（服务端不完全确定）；翻转几乎都来自回答本身，回答相同、只是判分变了的只有 2 条。
- **单次运行的准确率在 ±1 个点内波动，3–4% 的题会翻转。** N9 里相差 1 个点左右的比较都不能当作稳定的结论。LoCoMo 上"L1 比全上下文低 2.3 个点"这一条：重跑后 L1 高了 0.9 个点，换判分模型后不显著，应看作两者接近。差得多的结论（LongMemEval 上 L1 对全上下文 +84 / −14、控制器对 L2）远在波动之外。

### 5.3 人工抽检

`scripts/n11_audit.py` 从 N9 的判分里按数据集分层抽了 50 条（LongMemEval 15、LoCoMo 15、MemLens 32K / 128K 各 10，判对、判错各半），导出到 `runs/eval/n9-final/judge-audit.md`。需要人工逐条勾选，然后 `uv run cuemem eval audit n9-final --score` 统计一致率。

## 6. 工程

### 6.1 延迟与并发（离线，`scripts/n11_latency.py`）

合成的记忆空间（会话与轮走真实的在线写入；事实约为轮数的 1.2 倍，每个会话一条摘要），哈希向量器（1,024 维，不调用 API）。表里是读路径的本机部分：探针（4 路向量检索 + 打分 + 54 个特征）、控制器、L1 打包；线上每次查询还要加一次向量接口（约 110 ms）。Apple M2、8 GB，每档 3 次取中位数。

| 轮数（检索单元） | 本地模式 读 p50 / p95 | 服务端 读 p50 / p95 | 在线写入一问一答 本地 / 服务端 |
|---|---|---|---|
| 500（1.3k） | 32 / 36 ms | 14 / 44 ms | 1.4 / 5.9 ms |
| 2,000（4.7k） | 111 / 112 ms | 20 / 40 ms | 1.4 / 5.7 ms |
| 8,000（1.9 万） | 445 / 465 ms | 33 / 39 ms | 2.8 / 5.2 ms |
| 20,000（4.6 万） | 1,076 / 1,139 ms | 91 / 98 ms | 2.5 / 6.6 ms |

- **本地模式随规模线性增长**：Qdrant 本地模式是 Python 实现的精确检索，每次过滤都要扫全集合。一年每天聊一次约 3,600 轮，读路径的本机部分约 0.2 秒，还能接受；再大就该换服务端。
- **服务端**（Docker 里的 Qdrant 1.19，按 `kind`、`ts` 建 payload 索引）：4.6 万条时读路径 91 ms，其中探针 75 ms（向量检索 27 ms，其余是 SQLite 读取与特征计算）、L1 打包 16 ms。随规模变慢的主要是 SQLite 那部分，以后可以缓存空间统计。
- **并发**（2,000 轮的空间，查询向量化用 110 ms 的等待模拟）：

| 线程数 | 本地模式 吞吐 / 延迟 p50 | 服务端 吞吐 / 延迟 p50 |
|---|---|---|
| 1 | 4.3 次/秒 / 232 ms | 6.8 次/秒 / 146 ms |
| 4 | 8.7 / 452 ms | 23.0 / 170 ms |
| 16 | 8.7 / 1,778 ms | 54.7 / 289 ms |

本地模式在约 9 次 / 秒处饱和（向量库全局一把锁，Python 计算也受 GIL 限制）；服务端把向量检索移出进程，16 线程时 55 次 / 秒。压测时发现同步的 Qdrant 客户端不能被多个线程同时使用（服务端模式下出现 "Bad file descriptor"），所以服务端模式也保留了全局锁；吞吐量的提高来自检索本身变快。

### 6.2 多进程与服务端模式

- Qdrant 本地模式同一时间只允许一个进程打开同一个目录。之前 `cuemem serve` 运行时再开命令行，会得到库内部的 `RuntimeError`；现在报 `StorageLockedError`，告诉你停掉哪个进程，或者设置 `CUEMEM_VECTOR_STORE__URL` 改用服务端。
- 服务端模式下新建集合时按 `kind`、`ts` 建 payload 索引（检索时就按这两个字段过滤）。
- 新命令 `cuemem migrate-vectors --to URL`：把本地模式的向量库原样复制到服务端。写入是幂等的，数据库里已有的记忆不会被重新写入向量库，不迁移就切换会得到一个空的向量库。用临时的 Qdrant 容器实测过：迁移后服务端的检索结果与本地相同。
- 新方法 `VectorStore.indexed()`：大批写入后服务端在后台建 HNSW 索引，期间检索变慢，基准测试等它建完再测。

### 6.3 访问令牌

设置 `CUEMEM_API_TOKEN` 后，`/api` 下除健康检查外的接口都要带 `Authorization: Bearer <令牌>`，界面先要求登录（用户名任意，密码填令牌）。没设置时不鉴权；`cuemem serve` 监听非本机地址又没设令牌时给出警告。
