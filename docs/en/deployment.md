# Deploying and operating CueMem

English · [中文](../deployment.md)

How to run CueMem as a server: access tokens, limits, Docker, a Qdrant server, a public deployment, backups and upgrades. These four sections were in the README until 0.10.0 (D-077), which keeps a short summary under the same four headings; messages that say "README, Public deployment", "README 的备份与恢复" or "README 的“升级”一节" lead here through it. For a failure message and what to do about it, see [Troubleshooting](troubleshooting.md); every setting is in the [configuration reference](configuration.md), and every route, error code and environment variable in the [API reference](api.md).

## Deployment

By default CueMem uses embedded SQLite and Qdrant in local mode. A database is opened by one process at a time, also with a Qdrant server: a second process (an SDK `Memory()`, a stdio `cuemem mcp`, `cuemem reindex`) gets `StorageLockedError` naming the holder's pid and command, so apps that should share a memory talk to one `cuemem serve` through `MemoryClient` or `/api/v1`. Read-only commands (`cuemem export`, `spaces`, `inspect`, `doctor`, `keys`) work next to a running serve, and `CUEMEM_ALLOW_SHARED_DB=1` turns the lock off at your own risk. Installed with pip, it keeps its data in `~/.cuemem` (`CUEMEM_HOME` to change it). Local mode keeps one open file per user space (two with photos) and loads all vectors into RAM, so a shared server with many users should use a Qdrant server (`cuemem migrate-vectors --to URL`, then `CUEMEM_VECTOR_STORE__URL`, below). Every `cuemem` command raises its open-file soft limit to the hard limit, and `cuemem doctor` shows the collection count against it. Near that limit, local mode refuses to create a new space (503 with code `capacity`) while existing spaces keep working (except an existing space's first image, which needs a collection of its own and gets the same 503) and the server can still restart; it keeps a tenth of the soft limit, at least 256 files but at most half, for the database, images and connections. In local mode CueMem commits each vector write once instead of once per point and filters by kind with NumPy, so a 2,000-point delete takes 0.05 s instead of 2.8 s and a 6-search L1 recall over 25,000 points 0.35 s instead of 1.9 s, with the same results (benchmarks of the vector store with 64-dimensional vectors); deleting one session of a 50,000-turn log-only space takes about 0.15 s instead of 3.0–3.3 s.

- **Access tokens.** `cuemem serve` and `cuemem proxy` refuse to listen beyond loopback without a token (add `--insecure-no-auth` to run without authentication on a trusted network; without a token, only IP addresses, localhost, the bind hostname and the names in `CUEMEM_ALLOWED_HOSTS` are accepted as Host). Off loopback, tokens must be at least 16 characters (generate them with `openssl rand -hex 32`); shorter ones refuse to start (exit code 2) unless `--insecure-weak-token` is given (in compose, add it to `command:`); `sha256:` entries cannot be measured and are not checked. `--insecure-no-auth` skips the length check as well: with a token set, the server still requires that token, however short. Both checks also apply on loopback when `CUEMEM_ALLOWED_HOSTS` names a host that is not loopback-like (or `*`), the reverse-proxy setup of [Public deployment](#public-deployment). `CUEMEM_API_TOKEN` is the admin token. Scoped keys, in a YAML file named by `CUEMEM_API_KEYS_FILE` (or inline in `CUEMEM_API_KEYS`), limit each key to listed users and agents; `TOKEN=$(cuemem keys add alice-app --user alice)` mints one (it prints the token once, on stdout only, and stores only its sha256), `cuemem keys list` shows names, scopes and limits, and `cuemem keys revoke alice-app` removes it (the manual form `{name: alice-app, sha256: <printf %s "$TOKEN" | sha256sum>, scopes: [{user: alice}]}` still works). A key with `--user` but no `--agent` admits any agent id, and each new one is a new space (one more open file in local mode): give less-trusted clients `--agent`, or `--max-spaces N`, beyond which writes that would create a new space get 429. `cuemem serve` and `cuemem proxy` re-read the `CUEMEM_API_KEYS_FILE` file while running (checked at most once a second; changes apply within about a second, no restart). Inline `CUEMEM_API_KEYS` and `CUEMEM_API_TOKEN` are still read once at startup. A reload is refused, and the previous keys stay active with one log warning that names only key names, if the file is missing, unreadable or invalid, if it would leave no keys while `CUEMEM_API_TOKEN` is unset (a reload never turns authentication off), or if it contains plaintext tokens shorter than 16 characters in a setup where the server would refuse to start with them. Per-key rate limits are tracked by key name and are not reset by a reload. A UI session signed in with a revoked or rotated key loses access. A key gets 403 for a user, agent or space outside its scope, on `/api`, `/api/v1`, `/mcp`, the UI and the proxy alike, other tenants' memory ids look like missing ones (404), and `POST /api/v1/reset` deletes only the key's own spaces. Format and rules are in the [API reference](api.md#authentication-and-scoped-keys).
- **What a key can spend.** A scoped key limits whose memory a caller reaches, not what it spends. Any valid key makes the server call the operator's providers: `/v1/chat/completions` and `/v1/responses` (with or without a user; model, `n`, `max_tokens` and switches such as `enable_thinking` are forwarded as sent), `/v1/embeddings` (up to 2,048 inputs), chat on `/api`, `POST /api/v1/answer`, `/mcp`, and every write (extraction later sends about 2 characters upstream per byte written). Give keys only to parties you would trust with that budget, set spend limits at the provider, rate-limit by the `Authorization` header in a reverse proxy (for example nginx `limit_req_zone $http_authorization ...`), and lower `CUEMEM_MAX_BODY_BYTES` to bound what one write can cost. A key can also carry optional limits, for example `{name: alice-app, sha256: ..., scopes: [{user: alice}], rate_per_minute: 60, models: [qwen3.8-flash], max_output_tokens: 2000}`: `rate_per_minute` counts its requests other than GET, HEAD and OPTIONS (POST, PUT, DELETE, so searches over POST, `/v1/embeddings` and every MCP call count too) on `/api`, `/api/v1`, `/v1` and `/mcp` and answers 429 with `Retry-After` beyond it; `models` limits the proxy to the listed aliases or model ids (403 otherwise) and applies the catalogue's settings, such as `enable_thinking`, over the caller's; `max_output_tokens` caps or sets the proxy's `max_tokens` and refuses an `n` other than 1. `max_daily_tokens` (0.10.0) is a daily budget of input plus output tokens through the memory proxy, per key and server-local day: once it is reached, the key's requests get 429 with code `budget_exceeded` until local midnight. Without these fields nothing changes. They do not cover UI sessions. Separately, each scoped key may have at most 8 requests in progress at once on `/api`, `/api/v1`, `/v1` and `/mcp` (`CUEMEM_MAX_CONCURRENT_PER_KEY`, or the key's own `max_concurrent`; 429 with `Retry-After: 1` beyond it), so one key cannot tie up the server's threads; the admin token is not limited. Several keys together can still take all 40 threads, so lower the cap on a server shared by many keys.
- **MCP over HTTP.** `cuemem serve` also serves the MCP tools at `/mcp` (Streamable HTTP, POST only; other methods get 405), behind the same tokens; `X-CueMem-User` picks the user, and `--no-mcp` turns it off. Register it with `claude mcp add --transport http cuemem http://127.0.0.1:7860/mcp --header "Authorization: Bearer $KEY" --header "X-CueMem-User: alice"`. Non-ASCII IDs go in the header percent-encoded as UTF-8: `--header "X-CueMem-User: utf-8''%E5%BC%A0%E4%B8%89"` (raw UTF-8 bytes from curl work too). The stdio `cuemem mcp` cannot share a data directory (local or Qdrant server mode) with a running serve; use serve's `/mcp` instead. Configuration-file entries for Claude Code, Cursor, Claude Desktop and VS Code are in the [integrations guide](integrations.md#mcp-client-configuration-files).
- **Request limits.** Bodies are refused with 413 before they are read: 64 MiB for `/api`, `/v1` and UI uploads (`CUEMEM_MAX_BODY_BYTES`), 1 GiB for imports (`CUEMEM_MAX_IMPORT_BYTES`; raise it for very large exports), 8 MiB elsewhere. A scoped key imports at the body limit, and its request bodies in flight together are capped at the same limit (429 with `Retry-After: 1`), since parsed JSON takes about 24 times its size in memory; size a shared server's memory for the keys it serves, or lower the limit. Images must be JPEG, PNG, WEBP, GIF, BMP or TIFF, and images above Pillow's pixel limit (about 89 million pixels) are refused; both checks run before any decoder or model call.
- **Long-running servers.** Chat sessions, `/api/v1` runs and proxy sessions idle for 30 minutes end and go to extraction (`--idle-minutes`). The next add with the same `run_id` reopens an idle-closed run; when it ends, the run is extracted again in full and the user's whole space is replayed from the log (D-045), and while that replay runs the user's facts are missing from search and `get_all` for about the extraction latency. A run left open when `cuemem serve` stops or crashes survives the restart: the next add with the same `run_id` continues it, nothing else adopts it during the first idle period, and serve and proxy hand any that nobody continues to extraction one idle period after start-up. A run that an earlier process had already closed for idleness or handed to extraction (it kept both records only in its own memory) is a plain session after the restart, and so is one this process handed over and no longer remembers (beyond 10,000 runs): each later add re-extracts it and replays the user's whole space. Clients that pause for long should call `end_run` at natural breaks and open a new run. Traces (`runs/traces/*.jsonl`, which hold the users' questions) are kept until forgotten unless `CUEMEM_TRACES_RETENTION_DAYS` is set, and expired memories until deleted unless `CUEMEM_EXPIRED_RETENTION_DAYS` is set (`cuemem serve`, `cuemem proxy` and, since 0.10.0, `cuemem mcp` apply both at start-up and then daily). Up to 4 users' extractions run at once (`CUEMEM_CONSOLIDATION__BACKGROUND_WORKERS`). Each user (memory space) can have at most 64 open chat sessions, 64 memory-proxy sessions and 64 `/api/v1` runs (`CUEMEM_MAX_OPEN_SESSIONS`): at the cap a chat session with no messages yet is ended first, and the proxy parks its least recently seen session with nothing waiting for retry and no request in flight (it stays open and continues under the same id when the caller returns, and is extracted once after the idle period); when none can be ended or parked, or for a new `/api/v1` run (or an `add` that would reopen one), the request gets 429; and during an embedding or vector-store outage the proxy keeps at most 100 write-backs or 32 MiB per session for retry. On a full or read-only disk, CueMem keeps answering: a failed write to the embedding cache, LLM response cache or usage ledger logs one warning (`cuemem.store.files`) and is skipped until writes succeed again; evaluations stay strict and fail. The embedding and LLM caches keep every new question's vector and reply (about 6–7 KB per distinct question with 1,024-dimension vectors); only `CUEMEM_TRACES_RETENTION_DAYS` prunes query vectors. If the process is killed (`kill -9`, OOM, power loss) during an image write or a forget, the markers in `media/.journal/` let `cuemem serve`, `cuemem proxy` and `cuemem mcp` (at start-up and hourly) or `cuemem reindex` delete the leftover originals; `cuemem doctor` reports interrupted operations. When SQLite cannot open (a read-only directory, a full disk, a corrupt or non-SQLite file), the commands that open it, `serve` and `proxy` included, print one line naming the file and exit 1. `cuemem doctor` also lists failed and pending extractions per space (background retries stop after 3 attempts, for example with an expired key, while writes still succeed), spaces extracted under an older configuration, and the size of the caches and traces. A failed extraction whose error starts with `OutputTruncatedError` means that one single message produced more extraction output than the provider's output limit: use shorter messages, or an extraction model with a larger output limit. Since 0.10.0 `cuemem ingest --consolidate`, `cuemem consolidate` and `cuemem import --consolidate` print the stored reason and exit 1 when a session fails extraction.
- **Health, logs and stopping.** `/api/health` (and the proxy's `/health`) only says the process is up (since 0.10.0 it also counts the proxy's write-backs waiting for retry and dropped); `/api/ready` (and `/ready`) answers 503 naming `vector_store` or `worker` when a Qdrant server does not answer or the background extraction threads have died, and the Docker health check uses it. Logs are one line per record on stderr (`YYYY-MM-DD HH:MM:SS,mmm LEVEL logger: message`), with `CUEMEM_LOG_LEVEL` (default WARNING) and `--access-log` on serve (`--no-access-log` on proxy); since 0.10.0 uvicorn's start-up and access lines use the same format on stderr. `cuemem serve --metrics` and `cuemem proxy --metrics` (or `CUEMEM_METRICS=1`) add `GET /metrics` in the Prometheus text format for the admin token only; it is off by default ([API reference](api.md#metrics)). On SIGTERM (`docker stop`, systemd, `kill`) serve and proxy finish requests in flight, write buffered proxy write-backs, end sessions, wait for background extraction and remove the UI's temporary photo copies, then exit with code 143.
- **The UI contacts no third party by default:** it uses the IBM Plex Sans font bundled with Gradio, and Gradio's usage analytics and version check (api.gradio.app, huggingface.co) are off unless you set `GRADIO_ANALYTICS_ENABLED=True`. Markdown images in model replies and in the profile are shown as text, so a stored memory cannot make the browser load a third-party URL. The one exception on the server is `/docs` (on `cuemem serve` and `cuemem proxy`): it loads the pinned Swagger UI 5.34.1 from cdn.jsdelivr.net with integrity checks, so it is blank on a machine without internet access; `/openapi.json` works offline, and `/redoc` is no longer served (404).
- **Provider failures** have their own status codes on the HTTP API instead of a bare 500: 429 (with `Retry-After`) for rate limits, 402 for an empty balance, 503 (with `Retry-After`) when the provider is unavailable, 504 for timeouts, 422 when its content filter refuses, and 502 for other provider errors. An unreachable Qdrant server gives 503 (`vector_store_unavailable`, `Retry-After: 5`) and a slow one 504 (`vector_store_timeout`); the memory proxy still answers, without recalled memory.
- **Browsers.** Browser requests from other origins get 403 on `/api`, `/v1`, `/mcp`, the UI's `/gradio_api`, its sign-in `/login` and its `/config`, and on the UI's index page `/` when they carry an `Origin` (opening the UI from a link is unaffected); a `/logout` request with `Sec-Fetch-Site: cross-site` gets 403 too. On a loopback address only 127.0.0.1, localhost and [::1] are accepted as the Host. Without a token (`--insecure-no-auth`) on another address, only IP addresses, localhost and the bind hostname are. Behind a reverse proxy, or under another hostname, list those hostnames in `CUEMEM_ALLOWED_HOSTS` (comma-separated, can go in `.env`).
- **Files on disk.** The `cuemem` command creates its data files readable only by you (files 0600, new directories 0700). The SDK (`Memory`) creates missing data directories 0700 but leaves file modes to your application's umask. Neither changes directories that already exist. In an existing checkout run `cuemem doctor`, which prints the `chmod 700 <dir>` / `chmod 600 <file>` commands for anything others can read (for example `chmod 700 data runs/traces`); it also checks `.env` and `CUEMEM_API_KEYS_FILE`. The UI keeps uploads and gallery copies in a private temporary directory that is removed on exit; set `GRADIO_TEMP_DIR` to choose your own.

For Docker, `install -m 600 .env.example .env` (in a checkout, the `.env` that `uv run cuemem configure` wrote is the same file compose reads). Then set `CUEMEM_API_TOKEN` (for example from `openssl rand -hex 32`) and the keys of your configuration:

- `DEEPSEEK_API_KEY` and `DASHSCOPE_API_KEY` for the default configuration;
- or `CUEMEM_PRESET=openai` with `OPENAI_API_KEY`;
- or `CUEMEM_PRESET=deepseek` with `DEEPSEEK_API_KEY` (the image includes local embeddings);
- or `CUEMEM_PRESET=ollama` with `CUEMEM_PROVIDERS__OLLAMA__BASE_URL=http://host.docker.internal:11434/v1` (Ollama on the host must listen on an address the container can reach, not only 127.0.0.1).

Keep comments in `.env` on their own lines: `docker run --env-file` takes everything after `=` as the value. `docker compose up -d` then runs the UI, the HTTP API and the memory proxy on 127.0.0.1:7860 with a Qdrant server, and stops with an error if the token is missing. It returns once the containers start: if http://127.0.0.1:7860/ does not answer, `docker compose ps` shows the cuemem container Restarting and `docker compose logs cuemem` shows a one-line error (usually a missing key, or a token shorter than 16 characters); fix `.env` and run `docker compose up -d` again. Setting `CUEMEM_VECTOR_STORE__API_KEY` in `.env` makes compose's Qdrant require that key and cuemem send it; left unset, the internal Qdrant (which publishes no port) runs without one, as before. A single container is `docker run --stop-timeout 90 -p 127.0.0.1:7860:7860 -v cuemem-data:/data --env-file .env cuemem` after `docker build -t cuemem .`. docker-compose.yml sets `stop_grace_period: 90s` for the same reason: on stop, cuemem waits up to 20 s for in-flight requests, retries buffered proxy write-backs and waits up to 30 s for background consolidation, then exits with code 143; with Docker's default 10 s it is killed mid-shutdown and buffered write-backs are lost. The image's health check probes `/api/ready` (bypassing any `HTTP_PROXY`), so the container shows unhealthy while Qdrant is down. `docker compose up -d` rebuilds the image from the checkout each time (`pull_policy: build`); `cuemem --version` and the image label `org.opencontainers.image.revision` show the commit it was built from when `CUEMEM_BUILD` is passed (see [Upgrading](#upgrading)). The image includes the UI and local embeddings (the `ui` and `local` extras); `--build-arg EXTRAS=` builds an API-only one, and a missing extra is added by rebuilding (for example `docker build --build-arg EXTRAS="--extra ui --extra local --extra eval" -t cuemem .`), not with pip inside the container. For scoped keys in a container, put the keys file in the data volume (`/data`) and point `CUEMEM_API_KEYS_FILE` at it, or put the keys inline in `CUEMEM_API_KEYS`; compose still requires `CUEMEM_API_TOKEN`. Without Docker, run a Qdrant server with an API key and protect the API with a token:

```bash
export CUEMEM_VECTOR_STORE__API_KEY=$(openssl rand -hex 32)   # also put it in .env
docker run -d --name cuemem-qdrant -p 127.0.0.1:6333:6333 -v cuemem-qdrant:/qdrant/storage \
  -e QDRANT__SERVICE__API_KEY="$CUEMEM_VECTOR_STORE__API_KEY" qdrant/qdrant:v1.19.1
uv run cuemem migrate-vectors --to http://localhost:6333   # copy existing local vectors first
export CUEMEM_VECTOR_STORE__URL=http://localhost:6333     # also put it in .env
echo "CUEMEM_API_TOKEN=$(openssl rand -hex 32)" >> .env   # the token never appears in shell history
uv run cuemem serve --host 0.0.0.0   # Bearer token for /api, /api/v1, /v1 and /mcp, sign-in for the UI
uv run python scripts/n11_latency.py --out runs/n11-latency   # offline latency benchmark, no API calls
```

Without `127.0.0.1`, Docker publishes the Qdrant port on every interface and bypasses ufw; without `-v`, `docker rm` (for example to upgrade the image) deletes every vector (stop serve first, then `cuemem reindex --all` rebuilds them from the database; with compose, `docker compose stop cuemem`, then `docker compose run --rm cuemem reindex --all`; see [Backup and recovery](#backup-and-recovery)). CueMem sends `CUEMEM_VECTOR_STORE__API_KEY` (from the environment or `.env` only; there is no command-line flag) as Qdrant's `api-key` header, also from `cuemem migrate-vectors`, and `cuemem doctor` shows whether it is set. With an `http://` URL, qdrant-client warns once per client that the key is used over an insecure connection: harmless on loopback and on compose's internal network; use `https://` for a remote server or Qdrant Cloud. Serving on `0.0.0.0` as above suits a trusted network; to reach the server from the internet, keep it on 127.0.0.1 behind a TLS reverse proxy, as below.

## Public deployment

`cuemem serve` speaks plain HTTP. The Bearer token and the UI password are the same secret, and without TLS they cross the network in cleartext together with every memory. To reach it from outside a trusted network:

- Without Docker, keep `cuemem serve` on 127.0.0.1; with compose, keep the `127.0.0.1:7860:7860` mapping.
- Put a TLS reverse proxy in front. Caddy forwards the Host and `X-Forwarded-Proto` by default: `mem.example.com { reverse_proxy 127.0.0.1:7860 }`. With nginx, inside the `location` that does `proxy_pass http://127.0.0.1:7860;`, set `proxy_set_header Host $host; proxy_set_header X-Forwarded-Proto $scheme; proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; proxy_buffering off;` (the last items keep the UI's streaming working).
- Set `CUEMEM_ALLOWED_HOSTS=mem.example.com` in `.env`, so the Host and Origin checks accept that name.
- A token is required: set `CUEMEM_API_TOKEN` (at least 16 characters, for example `openssl rand -hex 32`) or scoped keys. `cuemem serve` and `cuemem proxy` refuse to start (exit code 2) on a loopback bind when `CUEMEM_ALLOWED_HOSTS` names a host that is not loopback-like (or `*`) and no token is set, or a token is shorter than 16 characters; `--insecure-no-auth` / `--insecure-weak-token` override this, and `--insecure-no-auth` then prints a warning naming those hosts. Entries that only name this machine (127.x, ::1, localhost, *.localhost) do not count. With a token (including under `--insecure-weak-token`) the plain-HTTP notice prints in this setup too.
- Keep `.env` private (`chmod 600 .env`; `cuemem configure` and `install -m 600` create it that way) and use tokens from `openssl rand -hex 32`.
- CueMem does not rate-limit sign-ins or failed tokens; do that in the proxy, for example nginx `limit_req` on `/login` by client address and on the API by the `Authorization` header.

## Backup and recovery

- **What to back up:** in the data directory (`data/` in a checkout, `~/.cuemem/data` after pip), `cuemem.sqlite` with its `-wal` and `-shm` files (the raw log and derived memory), `ledger.sqlite`, `media/` (the original images) and `qdrant/` (or the Qdrant server's storage); `claude_memory.sqlite` with its `-wal` and `-shm` (only if you use the Claude memory tool integration: the `/memories` files Claude wrote; it is not in `cuemem export` and cannot be rebuilt from the log); `cache/` is optional (it can be rebuilt, at the cost of requests), and `runs/` is not needed for recovery.
- **How:** stop `cuemem serve` and copy the whole directory, or copy each SQLite file (`cuemem.sqlite`, `ledger.sqlite` and, if present, `claude_memory.sqlite`) with `sqlite3 FILE ".backup DEST"` (or Python's `sqlite3.Connection.backup`). Never `cp` a live `.sqlite` file without its `-wal`: recent commits are still in the `-wal` file. `cuemem export --space S -o FILE` (raw log and images, per space; not the Claude memory tool's files) writes FILE atomically, so a failed export (a full disk, say) leaves the previous backup untouched; it opens only the database, so it works while serve runs. An export contains the turns that existed when it started: turns added while it is being produced are in the next export. Copy a Qdrant server's storage only with the Qdrant server stopped; otherwise rebuild the vectors with `cuemem reindex --all` after a restore.
- **With Docker / compose:** in the image the data directory is `/data/data` (`CUEMEM_HOME=/data`): `cuemem.sqlite`, `ledger.sqlite`, `claude_memory.sqlite`, `media/` and `cache/`. The simplest backup is `docker compose stop cuemem && docker compose cp cuemem:/data/data ./cuemem-backup && docker compose start cuemem`; a live backup with Python's `sqlite3.Connection.backup` inside the container (the image has no `sqlite3` command), and the restore steps (stale `-wal` files removed, `docker compose cp`, a `chown` to the image's uid 1000 user, `reindex --all`), are in the [API reference](api.md#backup-and-restore). Do not copy the `qdrant-storage` volume while the qdrant service runs.
- **Restore:** with `cuemem serve` stopped, put back the SQLite files, then `media/`, then optionally `qdrant/`, and run `cuemem doctor --vectors` and `cuemem reindex --all`. If the vector store is lost or out of step with the database (search returns nothing while `get_all` still lists memories), `cuemem doctor --vectors` shows which spaces differ and `cuemem reindex --space S` (or `--all`) restores them; it makes no LLM calls, with a warm embedding cache it sends no requests, and `--full` rewrites every vector, not only the missing ones. Before putting back a `.backup` copy, delete any `cuemem.sqlite-wal` / `-shm`, `ledger.sqlite-wal` / `-shm` and `claude_memory.sqlite-wal` / `-shm` left in the data directory (a crashed serve leaves them, and SQLite would replay that unrelated WAL onto the restored file); a copy of the stopped directory comes back together with its own `-wal` and `-shm`.
- **A broken local vector store:** if `data/qdrant/meta.json` was emptied (a kill while a collection was being created), stop serve and run `cuemem doctor --repair-vectors`, which rebuilds it from `collection/` and keeps the old file as `meta.json.broken-<timestamp>`. Do not delete `data/qdrant/meta.json` by hand: Qdrant writes an empty one and the existing collections are orphaned.
- **A corrupt file:** if `cuemem.sqlite`, `ledger.sqlite`, `cache/llm.sqlite` or `cache/embed.sqlite` is corrupt or is not a SQLite database, CueMem names the file and exits with one line. Restore `cuemem.sqlite` from a backup; the LLM cache, the embedding cache and the ledger can simply be deleted and are rebuilt (the ledger loses its usage history).
- **Upgrades:** data directories upgrade automatically; downgrades are not supported. A database written by a newer CueMem is refused with a one-line error; to move to an older version, export with the newer one and import.

## Upgrading

Each recipe ends with `cuemem doctor`, whose first line is `cuemem <version> (build <commit>)`.

- **Docker Compose:** `git pull && CUEMEM_BUILD=$(git rev-parse --short=12 HEAD) docker compose up -d --build`, then `docker compose exec cuemem cuemem doctor`. A plain `docker compose up -d` rebuilds too (`pull_policy: build`; before 0.8.0 it restarted the old image); `docker compose build --pull` also refreshes the base image.
- **A single container:** `docker build --build-arg CUEMEM_BUILD=$(git rev-parse --short=12 HEAD) -t cuemem .`, then remove and recreate the container with the same `-v cuemem-data:/data`.
- **pip:** `pip install -U --force-reinstall "cuemem[ui,local] @ git+https://github.com/FlickYan/cuemem@vX.Y.Z"`, or pin a tag. pip skips a git URL whose version did not change, so `-U` alone does nothing between commits of one version; `--no-deps` would also skip dependency changes.
- **A source checkout:** `git pull && uv sync --locked`.

**Upgrading to 0.10.0.** What behaves differently after the upgrade (the full list is in [D-077](decisions.md)):

- **Ids.** A `user_id` or `agent_id` longer than 256 characters, or with an unpaired surrogate, is refused on every surface (ValueError in the SDK, 400 on `/api/v1`, `/mcp` and the memory proxy), and a `run_id` longer than that on `add` and `open_run`. Nothing stored is rewritten: spaces with longer ids stay reachable by space id for the admin token on `/api` and for the command line (`--space`). A keys file that names a longer id does not load.
- **Memory proxy.** An `X-CueMem-Session` name that is not ASCII or is longer than 80 characters gets a new id (its first 64 characters and a hash), so a session still open under the old id is not continued and ends by the idle sweep. A request whose last user message is followed only by system or developer messages is a new turn, and its user message is stored.
- **Exit codes.** `cuemem ingest --consolidate`, `cuemem consolidate` and `cuemem import --consolidate` exit 1 when a session fails extraction.
- **Imports.** `cuemem import --from mem0` writes batches of 200 sessions, each its own transaction (`--batch 0` restores one transaction per user and agent). A `CUEMEM_URL` in the environment sends every `cuemem import` to that server; the command prints `经 <url> 导入。` when it does.
- **Logs and routes.** uvicorn's start-up and access lines are in CueMem's log format on stderr (access lines used to go to stdout), and the access line ends with the status code alone. Without the UI, `GET /` is a JSON index where it was a 404. The health bodies have more fields.
- **`cuemem mcp`** deletes old traces and expired memories when `CUEMEM_TRACES_RETENTION_DAYS` or `CUEMEM_EXPIRED_RETENTION_DAYS` is set, as serve and proxy do.
- **Dependencies.** Locked installs (the Docker image, `uv sync --locked`) run qdrant-client 1.19.1 again; a pip install without the lock resolves `>=1.19.1` and may get 1.20.
- **Chinese and Indic text.** Several Chinese time expressions are read differently, and names and values in Indic and Southeast Asian scripts keep their vowel signs, so new facts with such names get their own entities and ids. Text without Han characters and without those marks is unaffected.
