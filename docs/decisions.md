## D-001 检索时机与深度由解耦的控制器决定，而不是由 LLM 自主决定

- **状态**：已采纳（N0）
- **背景**：让 LLM 通过工具调用自主决定检索，效果取决于模型能力，小模型尤其不可靠；行为难预测、难评测；项目价值会被模型能力掩盖。
- **决策**：每轮先运行不调用 LLM 的记忆探针，再由轻量、可训练的控制器在 L0 / L1 / L2（以及是否再感知原图）之间做成本感知的决策；证据不足时级联升级。LLM 自主检索保留为对照基线（B3）和逃生通道。
- **备选**：总是检索（浪费 token、引入干扰）；纯规则触发（脆弱）；基于模型不确定度触发（FLARE / DRAGIN 式，对私人记忆不可靠，而且 API 模型拿不到内部信号）。
- **后果**：可度量、可训练、与底座无关、成本可调；代价是需要构造训练标签，控制器本身也可能过拟合。
- **验证**：N7 的帕累托曲线、与 B3 的对比、跨数据集与跨底座实验（H1–H3）。

## D-002 原始日志不可变、派生记忆可重建；事实采用双时间轴有效期

- **状态**：已采纳（N0）
- **背景**：用户信息会变化。直接覆盖或删除旧事实会丢失历史，无法回答"我以前……"；派生数据（摘要、事实）可能抽错，需要能修复。
- **决策**：原始轮次是唯一事实来源；事实、摘要、画像、图片描述都是带溯源、可全量重建的派生数据；冲突时让旧事实失效（设置 `valid_to`、`superseded_by`），而不是删除。
- **备选**：Mem0 式 UPDATE / DELETE 覆盖（简单，但丢失历史）；不做抽取、只存原文（无法显式处理冲突）。
- **后果**：能回答历史状态问题、可审计、抽取逻辑升级后可以重跑；代价是存储与实现更复杂。
- **验证**：N3 的场景单测；开发集"知识更新"类别（H4）。

## D-003 多模态采用"索引时压缩 + 回答时再感知"

- **状态**：已采纳（N0）
- **背景**：MemLens 发现长上下文 LVLM 随长度退化，而记忆智能体因存储时压缩丢失视觉细节。
- **决策**：图片以三种表示入库（视觉向量、上下文感知描述 + OCR、实体绑定）；回答时由控制器决定是否取回原图交给 VLM。
- **备选**：只存描述（便宜但丢细节）；所有图片常驻上下文（昂贵，且随长度退化）。
- **后果**：兼顾长度稳定性与视觉保真度；代价是回答时多出图片 token，需要控制器管理。
- **验证**：N6 在 MemLens 上的对比（H5、H6）。

## D-004 模型全部走 API：DeepSeek + 通义千问，按角色分工

- **状态**：已采纳（N0 提出，N1 修订）
- **背景**：开发机为 Apple M2、8GB 内存、可用磁盘约 29GB。可用的 API 是 DeepSeek 与通义千问（2026-10-12 确认）。DeepSeek 只提供对话模型（其中 deepseek-flash 支持图片输入）；通义提供对话、视觉、文本向量、多模态向量与重排。
- **决策**：
  - LLM / VLM 通过 OpenAI 兼容接口按角色接入，分工见设计文档 §9.3；
  - 向量也走通义 API（qwen3.7-text-embedding，原生接口一次返回 dense + sparse），外面套一层内容哈希缓存；本地向量模型作为可选后端，接口已预留，暂不实现。
- **修订原因**：N0 原计划在本地运行 BGE-M3。改走 API 是因为：
  1. 8GB 内存跑本地模型，会和浏览器、IDE 抢内存；
  2. 通义向量每百万 tokens 只要 $0.07（QwenCloud），加上缓存后评测的向量化成本可以忽略；
  3. 原生接口同样给出 sparse 向量，混合检索不受影响；
  4. 不必下载约 1GB 的 torch 与 2GB 的模型权重，环境一条命令就能装好。
- **代价**：查询向量化多一次网络往返，探针的"几十毫秒"目标要放宽（待实测）；依赖网络。
- **验证**：`scripts/spike_embeddings.py` 实测延迟；N4 比较召回质量。

## D-005 存储全部嵌入式：SQLite + Qdrant 本地模式（可切服务端）+ 进程内图计算

- **状态**：已采纳（N1 技术验证后确认）
- **背景**：希望在笔记本上一条命令跑起来，不依赖 Docker 或外部服务；内存有限。
- **决策**：结构化数据和事实用 SQLite；向量用 Qdrant 本地模式（命名向量支持 dense / sparse / image，payload 支持时间与有效性过滤）；PPR 用 scipy.sparse 计算。所有存储都在接口之后；配置 `vector_store.url` 即可改用 Qdrant 服务端，代码不变。
- **备选**：Neo4j（图能力强但重）；Postgres + pgvector（需要起服务）；LanceDB（嵌入式、磁盘友好）。
- **验证数据**：N1，M2 / 8GB，1024 维 dense + 每条约 60 个非零项的 sparse，`scripts/spike_storage.py`。

  | 点数 | 写入耗时 | dense p50 / p95 | sparse p50 / p95 | 带过滤的 dense p50 | 重新打开 | 进程峰值内存 |
  |---|---|---|---|---|---|---|
  | 1,000 | 0.8 s | 1.2 / 1.4 ms | 12.2 / 12.4 ms | 5.3 ms | 0.1 s | 223 MB |
  | 5,000 | 4.0 s | 4.7 / 4.9 ms | 61.0 / 61.8 ms | 25.4 ms | 0.4 s | 661 MB |
  | 20,000 | 16.2 s | 16.9 / 17.5 ms | 244.5 / 248.0 ms | 100.6 ms | 1.9 s | 1,676 MB |

- **结论**：评测时每个样本是一个独立的记忆空间，规模在几千条以内，本地模式完全够用。本地模式的检索是暴力计算，sparse 与带过滤的检索在 Python 里逐点计算，2 万条时分别到约 245 ms 和 100 ms，内存也接近 1.7 GB。规模更大时切到 Qdrant 服务端（有 HNSW 与倒排索引），或在 N4 用 BM25 倒排索引替代 sparse 路。
- **后果**：零运维、易复现；分布式能力不在本地体现。

## D-006 自研 Agent Runtime，不用 LangChain / LlamaIndex 作为核心

- **状态**：已采纳（N0）
- **背景**：本项目最想展示的正是 agent loop / harness、上下文组装与记忆读写这些机制。自己构建 runtime，它们才讲得清楚、能单独测试；框架的抽象会把它们遮住。
- **决策**：核心循环、上下文组装、工具调用、记忆读写全部自研；只使用基础库（LLM SDK、存储客户端）。
- **后果**：每个机制都讲得清楚、可控、可测；代价是要自己处理重试、并发、结构化输出等细节（见 D-009、D-011）。

## D-007 评测先行

- **状态**：已采纳（N0）
- **背景**：文本记忆基准的报告值已经接近饱和，而且不同论文的 reader、judge、prompt 各不相同，数字不能直接比较。
- **决策**：在实现任何高级方法之前，先搭好统一的评测框架与基线；所有方法在同一框架、同一 reader 与 judge 下比较；主结果是准确率–成本帕累托曲线。
- **后果**：每个改动都有证据，结论可信；代价是前期看起来进展慢。

## D-008 judge 与主 reader 来自不同模型家族

- **状态**：已采纳（N1）
- **背景**：用 LLM 判分时存在自我偏好，倾向于给同家族模型的回答打高分。LongMemEval 的官方 judge 是 GPT-4o，但我们没有 OpenAI 的 API。
- **决策**：主 reader 用 DeepSeek（deepseek-flash），judge 用通义（qwen3.8-max），所有实验固定同一个 judge。跨底座实验中 reader 换成通义模型时，额外人工抽检，看 judge 是否偏向同家族。
- **备选**：reader 自己判分（偏差大）；多个 judge 投票（成本翻倍，留作 N9 的鲁棒性检查）。
- **验证**：N2 人工抽检 50 条看一致性；N9 做跨家族交叉检查。

## D-009 同步核心 + 线程池并发，而不是全面 asyncio

- **状态**：已采纳（N1）
- **背景**：评测要并发调用大量 API；很多 Agent 框架基于 asyncio。
- **决策**：核心代码全部同步。需要并发的地方（评测 runner、L2 的多路检索）用线程池；每个供应商一个信号量限流；SQLite 与 Qdrant 本地模式的访问加锁。
- **理由**：瓶颈是网络 I/O，线程足够；同步代码更容易读、调试和讲解；避免 async 的"传染性"（整条调用链都得改成 async，而 SQLite、Qdrant 本地模式都是同步库）；FastAPI 也能在线程池里运行同步接口。
- **代价**：极高并发的在线服务场景下不如 asyncio；届时可把 LLM 客户端换成 openai SDK 的异步版本。

## D-010 成本口径：名义成本用于比较，实际花费单独统计

- **状态**：已采纳（N1）
- **背景**：DeepSeek 有错峰半价，两家都有缓存命中折扣，通义还有新用户免费额度；命中本地响应缓存时更是一分钱不花。如果直接用"实际花费"比较方法，同一个实验在不同时间运行，成本会不一样。
- **决策**：账本给每次调用记两种成本。
  - **名义成本**：全部按高峰、未命中缓存的标价计算，用于实验比较与帕累托分析；
  - **估算花费**：扣除本地缓存命中和供应商缓存折扣，用于管理预算。
  - token 数与调用次数作为与价格无关的补充指标。
- **后果**：实验结论不受运行时间影响；价格变动时只需改 `configs/default.yaml`。

## D-011 结构化输出：JSON 模式 + Schema 提示 + 校验重试

- **状态**：已采纳（N1）
- **背景**：抽取、规划、判分都需要可靠的结构化输出。两家都支持 JSON 模式，但对严格 json_schema 模式的支持不一致（DeepSeek 文档未提及）；DeepSeek 的 JSON 模式偶尔会返回空内容。
- **决策**：统一使用 `response_format={"type": "json_object"}`，把 pydantic 生成的 JSON Schema 写进系统提示，再用 pydantic 校验。校验失败时把具体错误反馈给模型重试，默认最多 3 次；空回复不写入缓存。
- **后果**：与供应商无关；失败可观测（重试次数记录在结果里）；代价是偶尔多一次调用。

## D-012 两个存储之间不用事务：确定性 ID + 写入顺序保证一致

- **状态**：已采纳（N1）
- **背景**：一条记忆要同时写 SQLite（内容）和 Qdrant（向量），两者无法放在同一个事务里。
- **决策**：
  - 所有 ID 都由内容确定性地派生，重复写入是覆盖而不是新增；
  - 先写向量、后写数据库，所以数据库里有的记录一定有向量；中途失败时重跑即可补齐，向量化命中缓存，不会重复计费；
  - 建库时把向量模型指纹写进数据库，换模型时直接报错，避免新旧向量混用。
- **后果**：写入幂等、可恢复，不需要事务协调器。

## D-013 通义经 QwenCloud 接入；Key 只进 .env；成本统一按美元计

- **状态**：已采纳（N1）
- **背景**：阿里把 DashScope、百炼、Model Studio 统一成了两个品牌：中国大陆以外叫 QwenCloud，中国大陆叫千问 AI 平台。不同平台的接口域名、API Key、可用模型都不一样，例如 QwenCloud 目前没有 qwen3-vl-embedding，多模态向量用的是 tongyi-embedding-vision 系列。本项目的账号在 QwenCloud。
- **决策**：
  - 默认配置直接指向 QwenCloud：对话走 `https://maas.qwencloudapi.com/compatible-mode/v1`，向量走同一域名下的原生接口（只有原生接口能返回 sparse 向量）。换平台只需覆盖这两个地址；
  - API Key 只写入 `.env`（不进仓库），用 `cuemem configure` 交互式填写：输入不回显，只显示首尾几位，文件权限 600。缺 Key 时在调用前就提示运行 `cuemem configure`；
  - 名义成本统一用美元标价：DeepSeek 与 QwenCloud 都公布美元价格，评测比较只需要一种币种。
- **后果**：仓库里没有任何账号信息；成本可以直接相加比较。代价：换用其他平台时，名义成本仍按 QwenCloud 标价计算，与实际账单不完全一致，但不影响方法之间的比较。

## D-014 文本向量默认用 text-embedding-v4

- **状态**：已采纳（N1 联网验证后），检索质量的正式对比在 N4 完成
- **背景**：N1 原定用 qwen3.7-text-embedding。拿到 Key 后实测（`scripts/spike_embeddings.py`，QwenCloud）：

  | 模型 | 单条查询 p50 / p95 | 10 条文档一批 | 稀疏向量非零项（平均） | 稀疏向量的性质 |
  |---|---|---|---|---|
  | qwen3.7-text-embedding | 164 / 247 ms | 1,481 ms | 约 523 | 带语义扩展："Max 是一只金毛"扩展出"狗狗、汪汪、狗粮"，甚至德语"Hunde" |
  | text-embedding-v4 | 52 / 69 ms | 113 ms | 约 20 | 原文词项权重："Max 是一只金毛"只有"毛、是、金、Max、一只" |
  | qwen3.7-text-embedding-flash | — | — | — | QwenCloud 上不存在该模型 |

  在一个小样例上，两者的语义区分度接近：问题与相关 / 无关文档的余弦相似度，v4 为 0.646 vs 0.225，qwen3.7 为 0.601 vs 0.166。
- **决策**：默认改用 text-embedding-v4。
  1. 写入快 13 倍：写入 LongMemEval 这种规模的数据，从约 10 小时降到 1 小时以内，评测迭代快得多；
  2. 查询约 50 ms，与探针"几十毫秒"的目标一致；
  3. 稀疏向量是真正的词项权重，正好承担混合检索中"精确匹配"的角色；带语义扩展的稀疏向量与 dense 路重叠，而且每条 500 多项，会让 Qdrant 本地模式的稀疏检索慢一个数量级（参见 D-005 的测试条件：每条约 60 项）。
- **代价与验证**：qwen3.7-text-embedding 是更新的模型，检索质量可能更好。N4 在开发集上用 Recall@k 正式对比，模型只是一个配置项，可以随时切回。
