## D-001 检索时机与深度由解耦的控制器决定，而不是由 LLM 自主决定

- **状态**：已采纳（N0）
- **背景**：让 LLM 通过工具调用自主决定检索，效果取决于模型能力，小模型尤其不可靠；行为难预测、难评测；项目价值会被模型能力掩盖。
- **决策**：每轮先运行不调用 LLM 的记忆探针，再由轻量、可训练的控制器在 L0 / L1 / L2（以及是否再感知原图）之间做成本感知的决策；证据不足时级联升级。LLM 自主检索保留为对照基线（B3）和逃生通道。
- **备选**：总是检索（浪费 token、引入干扰）；纯规则触发（脆弱）；基于模型不确定度触发（FLARE / DRAGIN 式，对私人记忆不可靠，而且 API 模型拿不到内部信号）。
- **后果**：可度量、可训练、与底座无关、成本可调；代价是需要构造训练标签，控制器本身也可能过拟合。
- **验证**：N7 的帕累托曲线、与 B3 的对比、跨数据集与跨底座实验（H1–H3）。

## D-002 原始日志不可变、派生记忆可重建；事实采用双时间轴有效期

- **状态**：已采纳（N0）
- **背景**：用户信息会变化。直接覆盖或删除旧事实会丢失历史，无法回答"我以前……"；派生数据（摘要、事实）可能抽错，需要能修复。
- **决策**：原始轮次是唯一事实来源；事实、摘要、画像、图片描述都是带溯源、可全量重建的派生数据；冲突时让旧事实失效（设置 `valid_to`、`superseded_by`），而不是删除。
- **备选**：Mem0 式 UPDATE / DELETE 覆盖（简单，但丢失历史）；不做抽取、只存原文（无法显式处理冲突）。
- **后果**：能回答历史状态问题、可审计、抽取逻辑升级后可以重跑；代价是存储与实现更复杂。
- **验证**：N3 的场景单测；开发集"知识更新"类别（H4）。

## D-003 多模态采用"索引时压缩 + 回答时再感知"

- **状态**：已采纳（N0）
- **背景**：MemLens 发现长上下文 LVLM 随长度退化，而记忆智能体因存储时压缩丢失视觉细节。
- **决策**：图片以三种表示入库（视觉向量、上下文感知描述 + OCR、实体绑定）；回答时由控制器决定是否取回原图交给 VLM。
- **备选**：只存描述（便宜但丢细节）；所有图片常驻上下文（昂贵，且随长度退化）。
- **后果**：兼顾长度稳定性与视觉保真度；代价是回答时多出图片 token，需要控制器管理。
- **验证**：N6 在 MemLens 上的对比（H5、H6）。

## D-004 模型全部走 API：DeepSeek + 通义千问，按角色分工

- **状态**：已采纳（N0 提出，N1 修订）
- **背景**：开发机为 Apple M2、8GB 内存、可用磁盘约 29GB。可用的 API 是 DeepSeek 与通义千问（2026-10-12 确认）。DeepSeek 只提供对话模型（其中 deepseek-flash 支持图片输入）；通义提供对话、视觉、文本向量、多模态向量与重排。
- **决策**：
  - LLM / VLM 通过 OpenAI 兼容接口按角色接入，分工见设计文档 §9.3；
  - 向量也走通义 API（qwen3.7-text-embedding，原生接口一次返回 dense + sparse），外面套一层内容哈希缓存；本地向量模型作为可选后端，接口已预留，暂不实现。
- **修订原因**：N0 原计划在本地运行 BGE-M3。改走 API 是因为：
  1. 8GB 内存跑本地模型，会和浏览器、IDE 抢内存；
  2. 通义向量每百万 tokens 只要 $0.07（QwenCloud），加上缓存后评测的向量化成本可以忽略；
  3. 原生接口同样给出 sparse 向量，混合检索不受影响；
  4. 不必下载约 1GB 的 torch 与 2GB 的模型权重，环境一条命令就能装好。
- **代价**：查询向量化多一次网络往返，探针的"几十毫秒"目标要放宽（待实测）；依赖网络。
- **验证**：`scripts/spike_embeddings.py` 实测延迟；N4 比较召回质量。

## D-005 存储全部嵌入式：SQLite + Qdrant 本地模式（可切服务端）+ 进程内图计算

- **状态**：已采纳（N1 技术验证后确认）
- **背景**：希望在笔记本上一条命令跑起来，不依赖 Docker 或外部服务；内存有限。
- **决策**：结构化数据和事实用 SQLite；向量用 Qdrant 本地模式（命名向量支持 dense / sparse / image，payload 支持时间与有效性过滤）；PPR 用 scipy.sparse 计算。所有存储都在接口之后；配置 `vector_store.url` 即可改用 Qdrant 服务端，代码不变。
- **备选**：Neo4j（图能力强但重）；Postgres + pgvector（需要起服务）；LanceDB（嵌入式、磁盘友好）。
- **验证数据**：N1，M2 / 8GB，1024 维 dense + 每条约 60 个非零项的 sparse，`scripts/spike_storage.py`。

  | 点数 | 写入耗时 | dense p50 / p95 | sparse p50 / p95 | 带过滤的 dense p50 | 重新打开 | 进程峰值内存 |
  |---|---|---|---|---|---|---|
  | 1,000 | 0.8 s | 1.2 / 1.4 ms | 12.2 / 12.4 ms | 5.3 ms | 0.1 s | 223 MB |
  | 5,000 | 4.0 s | 4.7 / 4.9 ms | 61.0 / 61.8 ms | 25.4 ms | 0.4 s | 661 MB |
  | 20,000 | 16.2 s | 16.9 / 17.5 ms | 244.5 / 248.0 ms | 100.6 ms | 1.9 s | 1,676 MB |

- **结论**：评测时每个样本是一个独立的记忆空间，规模在几千条以内，本地模式完全够用。本地模式的检索是暴力计算，sparse 与带过滤的检索在 Python 里逐点计算，2 万条时分别到约 245 ms 和 100 ms，内存也接近 1.7 GB。规模更大时切到 Qdrant 服务端（有 HNSW 与倒排索引），或在 N4 用 BM25 倒排索引替代 sparse 路。
- **后果**：零运维、易复现；分布式能力不在本地体现，扩展方案见设计文档 §12。

## D-006 自研 Agent Runtime，不用 LangChain / LlamaIndex 作为核心

- **状态**：已采纳（N0）
- **背景**：本项目最想展示的正是 agent loop / harness、上下文组装与记忆读写这些机制。自己构建 runtime，它们才讲得清楚、能单独测试；框架的抽象会把它们遮住。
- **决策**：核心循环、上下文组装、工具调用、记忆读写全部自研；只使用基础库（LLM SDK、存储客户端）。
- **后果**：每个机制都讲得清楚、可控、可测；代价是要自己处理重试、并发、结构化输出等细节（见 D-009、D-011）。
- **N8 落地**：`src/cuemem/agent/` 里的对话循环、上下文装配与工具约 1,000 行（不含导购的领域代码），没有引入 agent 框架；FastAPI、Gradio、MCP SDK 只用在服务的外壳上（D-042 至 D-047）。

## D-007 评测先行

- **状态**：已采纳（N0）
- **背景**：文本记忆基准的报告值已经接近饱和，而且不同论文的 reader、judge、prompt 各不相同，数字不能直接比较。
- **决策**：在实现任何高级方法之前，先搭好统一的评测框架与基线；所有方法在同一框架、同一 reader 与 judge 下比较；主结果是准确率–成本帕累托曲线。
- **后果**：每个改动都有证据，结论可信；代价是前期看起来进展慢。

## D-008 judge 与主 reader 来自不同模型家族

- **状态**：已采纳（N1）
- **背景**：用 LLM 判分时存在自我偏好，倾向于给同家族模型的回答打高分。LongMemEval 的官方 judge 是 GPT-4o，但我们没有 OpenAI 的 API。
- **决策**：主 reader 用 DeepSeek（deepseek-flash），judge 用通义（qwen3.8-max），所有实验固定同一个 judge。跨底座实验中 reader 换成通义模型时，额外人工抽检，看 judge 是否偏向同家族。
- **备选**：reader 自己判分（偏差大）；多个 judge 投票（成本翻倍，留作 N9 的鲁棒性检查）。
- **验证**：N2 人工抽检 50 条看一致性；N9 做跨家族交叉检查。（实际：人工抽检推迟到 N11，改抽 N9 测试集的判分，勾选的 48 条全部同意、2 条未勾选；跨家族交叉检查也在 N11 做，deepseek-flash 重判，一致率 94.7–97.9%。）

## D-009 同步核心 + 线程池并发，而不是全面 asyncio

- **状态**：已采纳（N1）
- **背景**：评测要并发调用大量 API；很多 Agent 框架基于 asyncio。
- **决策**：核心代码全部同步。需要并发的地方（评测 runner、L2 的多路检索）用线程池；每个供应商一个信号量限流；SQLite 与 Qdrant 本地模式的访问加锁。
- **理由**：瓶颈是网络 I/O，线程足够；同步代码更容易读、调试和讲解；避免 async 的"传染性"（整条调用链都得改成 async，而 SQLite、Qdrant 本地模式都是同步库）；FastAPI 也能在线程池里运行同步接口。
- **代价**：极高并发的在线服务场景下不如 asyncio；届时可把 LLM 客户端换成 openai SDK 的异步版本。

## D-010 成本口径：名义成本用于比较，实际花费单独统计

- **状态**：已采纳（N1）
- **背景**：DeepSeek 有错峰半价，两家都有缓存命中折扣，通义还有新用户免费额度；命中本地响应缓存时更是一分钱不花。如果直接用"实际花费"比较方法，同一个实验在不同时间运行，成本会不一样。
- **决策**：账本给每次调用记两种成本。
  - **名义成本**：全部按高峰、未命中缓存的标价计算，用于实验比较与帕累托分析；
  - **估算花费**：扣除本地缓存命中和供应商缓存折扣，用于管理预算。
  - token 数与调用次数作为与价格无关的补充指标。
- **后果**：实验结论不受运行时间影响；价格变动时只需改 `src/cuemem/configs/default.yaml`。
- **更新（D-024）**：估算花费现在也计入 DeepSeek 的错峰价（非高峰 = 标价 × 0.5），名义成本不变。

## D-011 结构化输出：JSON 模式 + Schema 提示 + 校验重试

- **状态**：已采纳（N1）
- **背景**：抽取、规划、判分都需要可靠的结构化输出。两家都支持 JSON 模式，但对严格 json_schema 模式的支持不一致（DeepSeek 文档未提及）；DeepSeek 的 JSON 模式偶尔会返回空内容。
- **决策**：统一使用 `response_format={"type": "json_object"}`，把 pydantic 生成的 JSON Schema 写进系统提示，再用 pydantic 校验。校验失败时把具体错误反馈给模型重试，默认最多 3 次；空回复不写入缓存。
- **后果**：与供应商无关；失败可观测（重试次数记录在结果里）；代价是偶尔多一次调用。

## D-012 两个存储之间不用事务：确定性 ID + 写入顺序保证一致

- **状态**：已采纳（N1）
- **背景**：一条记忆要同时写 SQLite（内容）和 Qdrant（向量），两者无法放在同一个事务里。
- **决策**：
  - 所有 ID 都由内容确定性地派生，重复写入是覆盖而不是新增；
  - 先写向量、后写数据库，所以数据库里有的记录一定有向量；中途失败时重跑即可补齐，向量化命中缓存，不会重复计费；
  - 建库时把向量模型指纹写进数据库，换模型时直接报错，避免新旧向量混用。
- **后果**：写入幂等、可恢复，不需要事务协调器。

## D-013 通义经 QwenCloud 接入；Key 只进 .env；成本统一按美元计

- **状态**：已采纳（N1）
- **背景**：阿里把 DashScope、百炼、Model Studio 统一成了两个品牌：中国大陆以外叫 QwenCloud，中国大陆叫千问 AI 平台。不同平台的接口域名、API Key、可用模型都不一样，例如 QwenCloud 目前没有 qwen3-vl-embedding，多模态向量用的是 tongyi-embedding-vision 系列。本项目的账号在 QwenCloud。
- **决策**：
  - 默认配置直接指向 QwenCloud：对话走 `https://maas.qwencloudapi.com/compatible-mode/v1`，向量走同一域名下的原生接口（只有原生接口能返回 sparse 向量）。换平台只需覆盖这两个地址；
  - API Key 只写入 `.env`（不进仓库），用 `cuemem configure` 交互式填写：输入不回显，只显示首尾几位，文件权限 600。缺 Key 时在调用前就提示运行 `cuemem configure`；
  - 名义成本统一用美元标价：DeepSeek 与 QwenCloud 都公布美元价格，评测比较只需要一种币种。
- **后果**：仓库里没有任何账号信息；成本可以直接相加比较。代价：换用其他平台时，名义成本仍按 QwenCloud 标价计算，与实际账单不完全一致，但不影响方法之间的比较。

## D-014 文本向量默认用 text-embedding-v4

- **状态**：已采纳（N1 联网验证后），检索质量的正式对比在 N4 完成
- **背景**：N1 原定用 qwen3.7-text-embedding。拿到 Key 后实测（`scripts/spike_embeddings.py`，QwenCloud）：

  | 模型 | 单条查询 p50 / p95 | 10 条文档一批 | 稀疏向量非零项（平均） | 稀疏向量的性质 |
  |---|---|---|---|---|
  | qwen3.7-text-embedding | 164 / 247 ms | 1,481 ms | 约 523 | 带语义扩展："Max 是一只金毛"扩展出"狗狗、汪汪、狗粮"，甚至德语"Hunde" |
  | text-embedding-v4 | 52 / 69 ms | 113 ms | 约 20 | 原文词项权重："Max 是一只金毛"只有"毛、是、金、Max、一只" |
  | qwen3.7-text-embedding-flash | — | — | — | QwenCloud 上不存在该模型 |

  在一个小样例上，两者的语义区分度接近：问题与相关 / 无关文档的余弦相似度，v4 为 0.646 vs 0.225，qwen3.7 为 0.601 vs 0.166。
- **决策**：默认改用 text-embedding-v4。
  1. 写入快 13 倍：写入 LongMemEval 这种规模的数据，从约 10 小时降到 1 小时以内，评测迭代快得多；
  2. 查询约 50 ms，与探针"几十毫秒"的目标一致；
  3. 稀疏向量是真正的词项权重，正好承担混合检索中"精确匹配"的角色；带语义扩展的稀疏向量与 dense 路重叠，而且每条 500 多项，会让 Qdrant 本地模式的稀疏检索慢一个数量级（参见 D-005 的测试条件：每条约 60 项）。
- **代价与验证**：qwen3.7-text-embedding 是更新的模型，检索质量可能更好。N4 在开发集上用 Recall@k 正式对比，模型只是一个配置项，可以随时切回。
- **N4 修订：默认改为 qwen3.7-text-embedding（只取 dense）**。N1 选 v4 的两个理由在 N4 之后都不成立了：稀疏路改由本地 BM25 承担（D-026），不再需要 qwen3.7 那种带语义扩展、又慢的稀疏向量；只取 dense 时速度慢约 6 倍，但写入是一次性的。而语义召回差距很大（`scripts/compare_embeddings.py`，dev100 分层抽 30 题，只比较"轮"上的 dense 检索，k = 10）：

  | 向量模型 | 发言召回（任一） | 发言召回（全部） | 会话召回（全部） | 发言 NDCG | 30 份历史的向量化耗时 |
  |---|---|---|---|---|---|
  | text-embedding-v4 | 83.3% | 74.1% | 84.4% | 54.3% | （缓存） |
  | qwen3.7-text-embedding | 93.3% | 89.3% | 89.2% | 72.7% | 354 秒 / 328 万 tokens |

  两者单价相同（QwenCloud 标价 $0.07 / 百万 tokens）。端到端（同一份代码、同一批题，只换向量模型）：B2 在 dev100 上 65% → 76%，在 LoCoMo 385 题上 71.2% → 75.6%；B2F 只从 80% → 80%、77.7% → 78.7%，说明事实增强键已经补上了弱向量模型的大部分召回损失（`docs/results/n4-dev100-l1/README.md`）。教训：**N1 时只看了速度与稀疏向量的性质，没有量化语义召回**——选型要用目标指标说话，前提条件变了要重新评估。

## D-016 评测运行器的设计

- **状态**：已采纳（N2）
- **决策与理由**：
  - **每题独立的内存存储，共享缓存**：LongMemEval 每道题有自己的对话历史，评测时为每组题新建内存中的数据库与向量库，用完即弃；向量缓存与 LLM 缓存则持久共享，重跑时不重复计费。这样内存占用稳定，8GB 机器上也能并发。
  - **用 trace 计量**：每个（题目，方法）在独立的 trace 中执行，从事件里汇总 token、调用次数和名义成本；判分在另一个 trace 中，不计入方法成本。trace 允许嵌套，内层调用（如 `MemorySystem.ask`）的事件会记到外层。
  - **断点续跑**：结果逐行追加到 `results.jsonl`，已完成的组合自动跳过；出错的组合记入 `errors.jsonl`，不算完成，下次运行会重试。
  - **预算保护**：按实际花费（不含本地缓存命中）累计，超过 `--max-cost` 就不再开始新的组合。
  - **可追溯**：`run.json` 记录配置、各角色的模型 ID 与标价、向量模型、代码版本（git 提交号，有未提交改动时带 `-dirty`）。
  - **先试跑再全量**：从开发集分层抽 10 题试跑，确认流程、成本与判分质量后再跑全量。
- **后果**：一条命令即可复现结果表；一次 100 题开发集评测的成本与耗时可以准确预估。

## D-017 试跑后修订 Reader 提示词（v2），只在开发集上调整

- **状态**：已采纳（N2）
- **背景**：pilot10 试跑后逐条检查了答错的题，判分都正确，但发现两个与方法无关的 Reader 问题：

## D-019 事实对账：规则只管合并、否定与多值累积，取代一律由 LLM 确认；取代分"现实变了"与"认知变了"

- **状态**：已采纳（N3；dev100 实测后修订）
- **背景**：新事实要和已有记忆比较，决定新增、取代、合并还是忽略。Mem0 对每条新事实都调用一次 LLM 在 ADD / UPDATE / DELETE / NONE 之间选择，简单但贵（LongMemEval 一题约 50 个会话、几百条事实），而且行为难以审计。
- **最初的设计**：规则优先——登记过的单值谓词（住址、工作、职位……）换了新值就直接取代，只有未登记的谓词才交给 LLM。
- **实测推翻了它**：dev100 首轮运行后，从回放里抽样人工核对：
  - 规则取代 31 次，正确的只有 3 次（**约 10%**）。原因有二：抽取模型给谓词贴标签不稳定（"有个小衣柜""家里墙多影响 Wi-Fi"都被标成 `lives_in`，"在做某个项目"被标成 `works_at`）；LongMemEval 的干扰会话来自不同的人，"用户 32 岁"与"用户 20 岁"本来就互相矛盾。
  - LLM 裁决的取代 28 次，正确约 18 次（**约 64%**），错误主要是把能同时成立的事实判成了"更新"。
  - 错误的"已失效"标签会误导 reader：知识更新题里有 2 题因此答错（新值被标成了"不再成立"），而不标有效期的消融版本反而答对。
- **修订后的决策**：
  1. **规则只做精确的事**：同主语、同谓词、同宾语 → 合并溯源；陈述几乎相同且宾语一致 → 合并；否定已有的同宾语肯定事实（"不再喜欢……"）→ 取代；登记过的多值谓词 → 新增。
  2. **取代一律由 LLM 确认**：单值事实（登记过的或模型标注的）遇到同谓词或相似的已有事实、多值事实遇到高度相似的已有事实，交给 LLM 在 update / correct / duplicate / add 中选择。提示词明确"两条事实能同时成立就选 add，拿不准也选 add"。同一会话的灰区事实合并成一次调用，每条最多带 3 条候选。
  3. **取代分两种**：现实变了（update：搬家、换工作）时，旧事实的 `valid_to` = 新事实的开始时间；认知变了（correct：用户更正、补充细节）时，旧事实只设 `invalidated_at`，`valid_to` 保持为空——它在现实中并没有"结束"。单一时间轴区分不了"我搬家了"和"我说错了"。
  4. **相似度不能单独决定合并**：向量对数字和专名不敏感，"预算 8000 元"和"预算 6000 元"的余弦相似度可能很高，所以按相似度合并时还要求宾语一致。
  5. **时间先后的比较**：只有两条事实都带明确的事件时间时才按事件时间比较，否则按说出的先后。首轮里"参加了五次互助小组（事件时间 2022）"被拿去和"参加了三次（2023-05 说的，没有事件时间）"的说出时间比较，更新的计数反被判成迟到的旧消息。
- **备选**：每条事实都问 LLM（Mem0 式，贵且难审计）；只存原文不对账（冲突留给 reader，即 B2 的做法）；改进抽取提示让谓词更规范（会让 4,800 个会话的抽取缓存全部失效，留到下次升级流水线版本时一起做）。
- **后果**：对账的 LLM 调用增加（单值冲突也要确认），但每次只是一次很短的批量调用；每个决定都记录了来自哪条规则，可以审计。教训：**规则的前提（谓词标签可靠）要先验证**；结构化信息错了会主动误导模型，比没有更糟。
- **验证**：`tests/test_reconcile.py`、`tests/test_consolidate.py` 的场景测试；修订前后的 dev100 对比见 [N3 结果](results/n3-dev100-facts/README.md)。

## D-020 巩固流水线：抽取无状态、并行；对账有状态、串行；记录时间取对话时间

- **状态**：已采纳（N3）
- **背景**：一个 LongMemEval 记忆空间约 50 个会话。逐个会话"抽取 → 对账"串行处理太慢；而对账依赖之前所有会话的结果，不能随意并行。
- **决策**：
  - **拆成两段**：抽取只看会话本身（和会话日期），是无状态的，可以并行，并且命中响应缓存（不同题目共用的会话只抽一次）；对账、实体消歧依赖已有记忆，按会话时间顺序串行。中间一步把所有新陈述、实体描述、摘要一次性批量向量化。
  - **任务键** = 记忆空间 + 会话 + 会话内容指纹 + 流水线版本：同一任务只执行一次；会话追加了轮次、或抽取逻辑升级，任务键随之改变。版本变化时自动清空派生记忆并重放。
  - **原子写入**：每个会话的结果（事实、实体、片段、检索单元、任务状态）在一个数据库事务里提交；向量先写、数据库后写（沿用 D-012）。中途失败只需重跑，已完成的会话不会重复处理。
  - **记录时间取对话时间**，不取程序运行时间：重放结果确定、可复现。代价是"系统何时得知"指的是"用户何时说的"，与真实的入库时间不同；对记忆系统来说前者才有意义。
  - **迟到的旧消息不覆盖新状态**：如果新事实的事件时间早于当前事实（例如后导入一段更早的对话），它直接作为历史版本写入，失效时间取取代它的那条事实被说出的时间。测试验证了"先导入新会话、再导入旧会话"与"按时间顺序导入"得到相同的当前事实。
  - **抽取时助手回复只保留开头**（默认 600 字符）：LongMemEval 里助手回复占对话文本的 87%，而记忆主要关于用户；完整回复仍在原始日志和"轮"索引里，"助手说过什么"照样能检索到。
  - **后台线程**：在线写入只登记任务，`ConsolidationWorker` 在后台按空间串行执行，不阻塞对话；评测与命令行可以同步执行。
- **后果**：一个空间的巩固耗时约等于"最慢的几次抽取 + 串行对账"，而不是所有抽取之和；重建派生记忆几乎免费（全部命中缓存）。代价是要处理并行线程里的 trace 上下文传递（`contextvars.copy_context`），否则抽取成本不会被计入。
- **验证**：`test_consolidation_is_idempotent_and_replayable`、`test_late_arriving_old_session_does_not_override`、`test_background_worker`。

## D-021 遗忘 = 删除原始日志 + 重放派生记忆，并按归属清理缓存

- **状态**：已采纳（N3）
- **背景**：用户说"忘掉这件事"或在界面里删除时，必须删得干净（新加坡 PDPA、欧盟 GDPR 的被遗忘权）。难点在派生数据：一条事实可能取代过别的事实，删掉它之后，被取代的旧事实应该恢复为当前有效；实体、摘要、画像也都可能受影响。逐条追溯这些关系很容易漏。
- **决策**：
  1. **派生记忆是原始日志的函数**。遗忘 = 从日志里删除这些轮次 + 用剩下的日志重放派生记忆。重放命中缓存，未受影响的会话不需要重新抽取。
  2. **缓存同样要清**：LLM 响应缓存的每个条目带归属标签（抽取按会话、对账与回答按空间），遗忘时删除受影响会话的抽取缓存和该空间的对账、回答缓存；向量缓存删除"遗忘前有、遗忘后没有"的文本对应的条目——向量本身也可能泄露原文信息。
  3. **物理删除**：SQLite 打开 `secure_delete`，删除时覆写内容；遗忘结束后执行 `VACUUM`。测试直接读取数据库文件的字节，确认被删的词不存在（取证式测试）。
- **备选**：沿溯源关系逐条级联删除（实现复杂，取代关系的恢复容易出错）；只标记删除（不满足被遗忘权）。
- **后果**：正确性容易保证，测试也简单（遗忘后的状态应当等于"从没说过这段话"的状态）；代价是整个空间重放一遍。当前实现命中缓存后很快；空间很大时可以按会话做快照，只重放受影响会话之后的部分。
- **已知限制**：~~trace 文件里有提问和回答原文，目前没有随遗忘清理~~（N8 已补：属性里含被删原话的 trace 条目一并删除，见 D-046）；Qdrant 本地模式的存储文件没有做字节级检查，但 payload 里本来就不存原文。
- **验证**：`tests/test_forget.py`。

## D-022 核心记忆是事实表的物化视图，由规则生成，不用 LLM 改写

- **状态**：已采纳（N3）
- **背景**：核心记忆（用户画像）每轮常驻上下文，内容必须准确。常见做法是让 LLM 把重要信息改写成一段画像，但改写可能编造内容，也可能和事实表不一致（事实被取代了，画像里还是旧的）。
- **决策**：画像 = 参与者（用户本人，或多人对话里的各位说话人）的重要度 ≥ 4、当前有效的事实，按重要度和新近程度排序，截断到约 400 tokens。事实一变就重新生成，不调用 LLM。
- **后果**：画像永远不会和事实表矛盾，每一条都能追溯到来源，生成零成本；代价是行文是逐条陈述，不如 LLM 改写流畅——对 reader 来说并无影响。
- **验证**：`test_core_memory_is_a_view_of_current_facts`；B2F 与"不给核心记忆"消融的对比。

## D-023 用 B2F 隔离写入路径的贡献：检索算法不变，只换写入结构

- **状态**：已采纳（N3）
- **背景**：N3 只做了写入路径，但需要在开发集上证明它有用。如果同时改检索算法，就分不清提升来自哪里。
- **决策**：新增方法 B2F，检索仍是 B2 的 dense top-k（k = 10），只是用上写入路径的产出：
  - **事实增强键**：事实与"轮"一起检索，命中的事实把分数传给它的来源轮（LongMemEval 论文的 key expansion：键是事实，值仍是原始对话）；
  - **带有效期的事实**：命中的事实连同时间和有效状态放进上下文，并沿版本链把新旧版本互相带出；
  - **核心记忆**常驻上下文。
  
  同时跑四个消融：只用事实增强键（不展示事实）、只给当前事实（相当于覆盖式更新）、事实不标有效期、不给核心记忆。
- **后果**：写入路径的贡献可以单独度量，后续 N4 的检索改进也有了清晰的对照；B2 本身保持不变（只检索"轮"），之前的结果可以直接复用。
- **结果**（dev100，详见 [N3 报告](results/n3-dev100-facts/report.md)）：B2 65% → B2F 80%（配对符号检验：+18 / −3，p = 0.001），与 ORACLE 83% 无显著差异；只用事实增强键 78%，只给当前事实 80%，不标有效期 80%，不给核心记忆 79%——四个消融与完整版的差异都不显著。检索层面：发言召回 87% → 96%，NDCG 58% → 80%。
- **跨数据集**：LoCoMo 前 3 段对话（385 题，未在其上调参）：B2 71.2% → B2F 77.7%（+42 / −17，p = 0.002），多跳 42% → 61%。
- **比较方式**：两种方法在同一批题上比较时用配对检验（只看"一个对、一个错"的题），比两个独立的置信区间灵敏得多：B2 与 B2F 的置信区间有重叠，但配对检验的 p = 0.001。脚本见 `scripts/paired_compare.py`。

## D-024 DeepSeek 错峰调度：批量任务在高峰时段暂停，花费估算计入错峰价

- **状态**：已采纳（N4 开始前）
- **背景**：DeepSeek 工作日 09:00–12:00、14:00–18:00（北京时间）为高峰，价格是其他时段的两倍。评测里 reader（deepseek-flash）是花费的大头，用户希望大部分调用落在便宜的时段。
- **决策**：
  - 供应商配置里声明高峰时段（`providers.deepseek.peak_hours`：时区、星期、时段、错峰系数 0.5）；没有分时价格的供应商（QwenCloud）不受影响；
  - LLM 客户端在真实调用之前检查：`peak_policy = wait` 时暂停到这一段高峰结束，命中本地缓存的请求不受影响；`warn` 照常调用并记录事件；`allow` 照常调用；
  - 评测（`cuemem eval run`）默认 `wait`，进入高峰时打印提示，可用 `--peak allow` 关闭；交互式命令（ask、ingest、consolidate）发的请求很少，用 `warn` 照常调用并提示一句；
  - 名义成本仍按高峰标价（D-010，保证不同时间的实验可比）；估算花费改为计入错峰折扣，预算保护按估算花费累计；
  - 工作安排：需要大量 DeepSeek 调用的评测放在清晨、午间（12–14 点）、晚上或周末；高峰时段写代码、跑离线测试。
- **后果**：同样的实验，实际花费最多可降一半，代价是评测可能被暂停几小时；可测试性靠注入时钟保证（测试不依赖运行时刻）。法定节假日未处理（按普通工作日算高峰），影响很小。
- **验证**：`tests/test_peak.py`。

## D-025 L1 融合：模态内按分数取最大，模态间用 RRF

- **状态**：已采纳（N4）
- **背景**：L1 要把三种粒度（轮、事实、会话摘要）和两种模态（dense、sparse）的检索结果合成一个"轮"的排序。RRF（倒数排名融合）是最常用的做法，最初的实现是每种单元、每种模态各自排名，全部做 RRF。
- **实测**：dev100 上纯检索评测（`scripts/tune_l1.py`，不调用 reader）：按单元类型全部 RRF 的发言 NDCG 只有 65.8%，比 N3 的 B2F（dense，事实键按余弦取最大）的 80.1% 还低 14 个点；"助手说过"类题从 79% 掉到 39%。原因是 RRF 只看名次、丢掉了分数大小：助手说的内容没有对应的事实，一条余弦很高的直接命中，被好几条名次中等的事实键叠加挤了下去。
- **决策**：先在**同一模态内部**按分数取最大值（轮自己的分数与它来源事实的分数取最大，即事实增强键；dense 的余弦在各类单元间本来可比，sparse 分数按各自列表的最大值归一化），再只在 **dense 与 sparse 两种模态之间**做 RRF（sparse 权重 0.5，网格搜索确定）。RRF 适合融合分数尺度不同的列表，不适合拆开本来可比的分数。
- **后果**：dense 部分与 B2F 完全一致（可作为正确性校验），加入 BM25 后发言召回（任一）95.7% → 100%，NDCG 基本持平（79.3% vs 80.1%）。按类型 RRF 保留为 `fusion="kind"` 的对照选项。
- **换用 qwen3.7-text-embedding 后复测**（dev100 纯检索，k = 10）：结论不变。按类型 RRF 的 NDCG 75.3%，模态内取最大 79.5%；"助手说过"类题 51.5% 对 95.5%。不用稀疏路时，L1 的排序与 B2F 仍然完全一致。

## D-026 稀疏路用 BM25，不用 text-embedding-v4 的词项权重

- **状态**：N4 采纳；**N5 复议后修订**：qwen3.7 下 L1、L2 默认都不用 BM25（实现保留为选项）；N4 的 B4 仍按原配置评测，结果可复现
- **背景**：text-embedding-v4 的原生接口同时返回稀疏向量（词项权重），N1 起就存进了 Qdrant；也可以在本地对文本建 BM25 索引。
- **实测**（dev100，纯检索，k = 10）：

  | 稀疏路 | 发言召回（任一） | 发言召回（全部） | 会话召回（全部） | 发言 NDCG |
  |---|---|---|---|---|
  | BM25 | 100.0% | 92.5% | 96.4% | 79.3% |
  | v4 词项权重 | 96.8% | 90.4% | 94.8% | 77.1% |

  端到端准确率：BM25 版 80%，v4 版 82%，配对差异不显著（p = 0.73）。
- **决策**：默认用 BM25。检索指标更好；分词可控（去掉每轮都有的 "User:" "Assistant:" 标签、数字整体保留、中文单字加二字组）；不依赖向量接口，离线可用、零成本，结果可解释（命中了哪些词）。
- **代价**：每个空间的 BM25 索引在内存里现建（LongMemEval 一个空间约 25 ms，之后按空间缓存，查询约 3 ms）；没有词形还原（"buy"匹配不到"bought"），留给 dense 路弥补。
- **换用 qwen3.7-text-embedding 之后**（D-014 修订）：qwen3.7 只取 dense，v4 词项权重这个选项不存在了，问题变成"还要不要稀疏路"。

  | 对比 | 带 BM25（B4） | 不用稀疏路 |
  |---|---|---|
  | dev100 纯检索（k = 10，不加时间分）发言召回（全部） / NDCG | 92.9% / 79.5% | 96.8% / 83.0% |
  | dev100 端到端 | 83% | 81%（B4 对 +5 / −3，p = 0.73） |
  | LoCoMo 385 题端到端 | 84.9% | 86.2%（B4 对 +10 / −15，p = 0.42） |

  纯检索上 BM25 反而让多会话与时间题的排序变差；端到端两个数据集方向相反，都不显著。dense 足够强以后，关键词路的边际价值消失了。N4 报告的数字保持评测前定好的配置（BM25 权重 0.5），不事后换默认值；N5 加入重排后，BM25 的角色是给重排提供候选，而不是直接参与排序，到时再决定去留。
- **N5 复议**（dev100 纯检索，94 道非拒答题，`scripts/tune_l2.py`；按 token 预算装入，指标是"发言召回（全部） / 发言 NDCG"）：

  | 配置 | 带 BM25 | 不用 BM25 |
  |---|---|---|
  | L1，预算 4k | 90.1% / 79.2% | 91.4% / 81.8% |
  | L1，预算 6k、最多 60 轮 | 92.2% / 80.2% | 95.6% / 83.7% |
  | L1 6k + 重排（qwen3-rerank，前 30 条） | 94.3% / 83.4% | 96.0% / 85.1% |
  | L2：查询规划 + 补检索 | 96.3% / 83.7% | 96.3% / 85.7% |

  BM25 在每个预算、有没有重排、单查询还是多查询下都不提高召回，多数情况下降低；它只在"L2 规划、不补检索"时让多会话题的召回高一些（87.6% 对 84.0%），补检索之后这点差别也没了。重排救不回来：作为重排的候选来源，加上 BM25 的召回反而更低。
- **修订后的决策**：L1 与 L2 的默认配置都不用稀疏路（`L1Config.sparse = "none"`）。BM25 的实现保留：向量模型较弱时它是有用的（text-embedding-v4 时就是）。B4 及其消融固定用 N4 的配置（带 BM25）评测，N4 的数字照样可以复现；N5 起"L1 的默认"等同于 B4-nobm25（dev100 81%、LoCoMo 86.2%，与 B4 的差异都不显著）。端到端不显著时，选纯检索指标更好、更简单、延迟更低的一边。

## D-027 时间感知：区间加分按宽度打折 + 相对时间打包；摘要先验与新旧加分默认关闭

- **状态**：已采纳（N4）
- **决策与依据**（dev100）：
  - **时间表达解析**：规则解析中英文时间表达，以**提问时间**为参照换算成区间（"两周前""上周六""in March""去年""5月20日""情人节"）。"today / tonight"在提问里通常指当下（"今晚看什么电影"），不当作检索线索。
  - **区间加分**：落在区间内的轮（或来源事实的事件时间在区间内的轮）加分，并按区间宽度打折（"上周六"全额，"过去两个月""去年"几乎不加）——宽区间覆盖大半历史，加分只会打乱排序。纯检索上时间题 NDCG 73% → 77%（qwen3.7），但"会话召回（全部）"下降：LongMemEval 的时间题会把几段相似的会话都标成证据，而题目只问其中一段，加分把答案顶上来、把干扰挤下去。dev100 里只有 12 道题带可解析的时间表达，LoCoMo 385 题里有 31 道；端到端都没有可测的差异（dev100 83% vs 不加分 84%，LoCoMo 两者相同）。代价几乎为零、可解释，保留默认开启；时间约束的完整处理交给 N5 的查询规划。
  - **相对时间打包**：每条证据标"距提问 N 天"。最终评测（qwen3.7）去掉后 dev100 83% → 79%（+5 / −1，p = 0.22），多会话题 54% → 42%、时间推理题 80% → 76%；LoCoMo 持平（+11 / −11）。text-embedding-v4 时也是同一方向（80% → 78%）。不显著但方向一致，保留。
  - **会话摘要先验、"最近 / 最早"新旧加分**：纯检索上都降低了 NDCG，默认关闭（保留开关，N5 的查询规划可能按问题类型启用）。

## D-028 评测提速：记忆空间落盘复用、纯检索调参、相同请求合并

- **状态**：已采纳（N4）
- **背景**：N3 起每次评测都要为每道题重建记忆空间（写入 + 巩固，全部命中缓存时 dev100 也要 5 分钟以上），而 N4 要反复调检索参数。
- **决策**：
  - **记忆空间落盘**：评测运行器把每道题的空间存在 `paths.eval_spaces` 下，下次运行直接复用（写入与巩固都是幂等的，复用时只是空操作）；`build.json` 记下首次构建时的写入与巩固统计，报告里的写入成本照样有数；向量模型或巩固配置变了时自动重建。dev100 的 100 个空间约 1 GB。
  - **纯检索调参**：`scripts/tune_l1.py` 直接在落盘的空间上跑各种检索配置，只算召回与 NDCG、不调用 reader，一轮 dev100 约 30 秒、零 LLM 成本，可以在 DeepSeek 高峰时段做。端到端评测只用来确认最终配置。
  - **相同请求合并（single-flight）**：多个线程同时发出同样的请求（不同题目共用的会话被同时抽取）时，只调用一次 API，其他线程等结果。
  - **续跑一致性检查**：同名运行会断点续跑。N4 换向量模型后误用了已存在的运行名，新结果差点混进旧目录（发现后立即停止、按原始行数恢复）。现在续跑前核对数据集、划分、向量模型与回答模型，不一致就报错，要求换运行名。
- **后果**：N4 的检索迭代从"每次几分钟加几美元"变成"每次半分钟、几乎零成本"。

## D-029 L1 上下文按 token 预算打包，而不是按固定条数

- **状态**：已采纳（N4）
- **背景**：B2、B2F 都是"取前 k = 10 轮"。但一"轮"的长度因数据集差很多：LongMemEval 的一轮是用户提问加助手的长回复，约 490 tokens；LoCoMo 是两个人的闲聊，一轮只有一句话，约 40 tokens。固定 k 会让两个数据集拿到的上下文差十几倍，在 LoCoMo 上，10 轮常常装不下多跳题需要的几处证据。
- **决策**：按 L1 的分数从高到低装入轮，直到用完 token 预算（默认 4k tokens，至少 1 轮，最多 40 轮）。事实（10 条，含版本链补齐）与核心记忆另算。
- **数据使用的说明**：这一项不是只在开发集上定的。text-embedding-v4 时的 LoCoMo 检查里，固定 10 轮的 B4（76.1%）不如 B2F（77.7%），这才引出了按预算打包；预算大小也同时看了两边：2k 在 dev100 上明显更差，在 LoCoMo 上与 4k 相当，所以取 4k。因此 LoCoMo 对 D-029 不是独立检验，N9 的最终评测（test400 与 LoCoMo 其余对话）才是。
- **实测**（qwen3.7-text-embedding；括号里是平均装入的轮数与每题输入 tokens）：

  | 配置 | dev100 | LoCoMo 385 题 |
  |---|---|---|
  | 固定 5 轮 | 82%（5 轮，3,908） | — |
  | 固定 10 轮 | 82%（10 轮，6,559） | 77.1%（10 轮，2,104） |
  | 预算 2k | 78%（4.7 轮，3,149） | 85.5%（37.7 轮，4,378） |
  | **预算 4k（默认）** | **83%（8.2 轮，4,973）** | **84.9%（40 轮，4,586）** |

  LoCoMo 上预算 4k 对固定 10 轮配对 +41 / −11（p < 0.001），多跳题 53% → 81%。dev100 上 4k 与固定 10 轮准确率相当，输入少 24%；2k 在 dev100 上少答对 5 题（p = 0.23，平均不到 5 轮，长回复题装不下证据）。
- **后果**：同一个配置在两种数据上都合适，不用按数据集调 k。LoCoMo 上实际起作用的是 40 轮的上限（40 轮只占约 2k tokens），这个上限没有在 LoCoMo 上调过。每题输入 token 随数据变化，所以检索质量表新增"平均轮数"一行：按预算装入的方法与固定 k 的方法，召回不能直接比较。

## D-030 L2 深度检索：查询规划 + 多查询"取最好名次"融合 + 充分性检查补检索 + 笔记式阅读

- **状态**：已采纳（N5）
- **背景**：N4 之后 B4 在 dev100 上答错 17 题，多会话题只有 54%（13 / 24）。错题有两类：一类是"一共几次 / 一共多少钱"这种聚合题，证据散落在多次对话里，L1 只找到一部分（多会话题的发言召回（全部）只有 71%）；另一类连只给证据会话的 ORACLE 也答错，是阅读与推理问题（数漏、重复计数、日期算错）。
- **决策**（各组件的默认值先在 dev100 的纯检索上定，再跑端到端）：
  1. **查询规划**：一次 qwen3.8-flash 调用，给出答案类型、是否需要穷尽、1–4 个子查询、时间区间、目标实体；失败时退回规则版计划。
  2. **多查询融合用"取最好名次"**：每条候选取它在各查询里最好的名次分，再加 0.1 倍的名次分之和打破平局。子查询各找一块信息，每块的最佳命中都应该进入上下文；名次分直接求和（RRF）奖励的是"几个查询里都排中游"的轮。
  3. **预算 6k tokens、最多 60 轮**；计数、求和、列举类问题给 25 条事实（L1 是 10 条）。
  4. **充分性检查**：最多 2 次，每次一次 qwen3.8-flash 调用；不够时按它给的查询补检索，每次再装入 1k tokens。
  5. **笔记式阅读**：系统提示不变，上下文末尾加阅读提示，输出先写笔记再作答（见设计文档 §6.5）。
  6. 图扩散、重排、BM25 默认都不用（D-031、D-032、D-026 修订）。
- **纯检索**（dev100，94 道非拒答题，发言召回（全部） / NDCG / 多会话题召回）：

  | 配置 | 召回（全部） | NDCG | 多会话题 | LLM 调用 / 题 |
  |---|---|---|---|---|
  | L1，4k（B4） | 90.1% | 79.2% | 70.9% | 0 |
  | L1，6k、60 轮（带 BM25） | 92.2% | 80.2% | 77.8% | 0 |
  | L1，6k、60 轮，不用 BM25 | 95.6% | 83.7% | 85.0% | 0 |
  | 规划，名次分求和（RRF） | 92.5% | 80.2% | 76.8% | 1 |
  | 规划，取最好名次 | 95.4% | 83.3% | 87.6% | 1 |
  | 规划 + 补检索，不用 BM25（B5 的检索） | 96.3% | 85.7% | 89.9% | 2.2 |

  RRF 融合的多查询完全没有收益，换成"取最好名次"后多会话题召回 +10 个点。但要如实看：同样 6k 预算，单查询的 L1 去掉 BM25 就能到 95.6%，L2 的检索只再多 0.7 个点（多会话题多 5 个点）。

- **端到端**（dev100，100 题，同一个 reader 与 judge）：

  | 方法 | 准确率 | 多会话 | 时间推理 | 名义成本 / 题 | LLM 调用 / 题 |
  |---|---|---|---|---|---|
  | B4（N4 的 L1） | 83% | 54% | 80% | $0.0016 | 1.00 |
  | B4-nobm25（N5 起的 L1 默认） | 81% | 58% | 72% | $0.0016 | 1.00 |
  | B4-b6k：L1 给 6k 预算 | 85% | 58% | 80% | $0.0022 | 1.00 |
  | B4-note：L1 + 先记笔记 | 86% | 62% | 84% | $0.0019 | 1.00 |
  | **B5：L2** | **89%** | **79%** | **84%** | **$0.0034** | **3.25** |
  | B5-noplan：不做查询规划 | 88% | 79% | 84% | $0.0033 | 2.29 |
  | B5-noiter：不做充分性检查 | 85% | 62% | 84% | $0.0026 | 2.00 |
  | B5-nonote：不记笔记 | 81% | 58% | 72% | $0.0031 | 3.25 |
  | B5-ppr：加图扩散 | 88% | 71% | 84% | $0.0034 | 3.26 |

  配对符号检验：B5 对 B4 +10 / −4（p = 0.18），对 B4-nobm25 +11 / −3（p = 0.057）；多会话题对 B4 +8 / −2（p = 0.11）。消融：不记笔记 −8（+12 / −4，p = 0.077），不补检索 −4（+4 / −0，p = 0.13），不做规划 −1，加图扩散 −1。

- **怎么解读**：
  - **最大的杠杆是阅读方式，不是检索**：同样的 L2 证据，不记笔记只有 81%；L1 的证据加上笔记就有 86%。"ORACLE 也答错"的阅读类错题从 B4 的 11 题降到 B5 的 6 题。计数题的笔记里，模型会逐项列出每次看房、每张专辑，再去重计数。
  - **检索上真正起作用的是补检索**：补检索救回来的 4 题都是"散落在多次对话里"的计数或时间题（看过几个医生、预约前一天几点睡），检查模型给出的补充查询都很对路。
  - **查询规划的子查询在纯检索上提升明显，端到端几乎没有**：没有规划时，充分性检查自己会提出补充查询，起到了同样的作用（B5-noplan 的纯检索召回反而略高）。
  - **误拒答减少**：有答案的题回答"不知道"，L1 6 次，B5 1 次（按措辞粗略识别）。
- **成本与延迟**：B5 每题名义成本 $0.0034，是 L1 的 2.1 倍；平均 3.25 次 LLM 调用（规划 1 次、检查 1.25 次、回答 1 次），输出 tokens 从 87 涨到 405（笔记）。回答端到端延迟 p50 1.8 秒、p95 6.2 秒（L1 约 1 秒）。
- **LoCoMo 检验**（前 3 段对话，385 题；L2 的所有默认值都只在 dev100 上定，LoCoMo 没有参与任何调参）：

  | 方法 | 准确率 | 多跳 | 时间 | 名义成本 / 题 |
  |---|---|---|---|---|
  | B4（N4 的 L1） | 84.9% | 81% | 87% | $0.0015 |
  | L1（B4-nobm25） | 86.2% | 80% | 88% | $0.0015 |
  | B4-note：L1 + 先记笔记 | 88.6% | 84% | 92% | $0.0017 |
  | **B5：L2** | **89.1%** | **88%** | **93%** | **$0.0032** |
  | B5-nonote：不记笔记 | 86.8% | 86% | 87% | $0.0030 |
  | ORACLE | 87.5% | 74% | 91% | $0.0005 |

  B5 对 B4 +27 / −11（**p = 0.014**），对当前 L1 +21 / −10（p = 0.071）；多跳题对当前 L1 +10 / −4（p = 0.18），时间题 +5 / −0（p = 0.06）。笔记式阅读的方向与 dev100 一致：L1 加上笔记就到 88.6%，B5 对它只多 2 题（+8 / −6）。误拒答：L1 12 次，B5 6 次。
- **验收**：路线图要求"多会话推理、时间推理显著提升"。两个数据集上方向都一致（dev100 多会话 +8 / −2、时间 +1 / −0；LoCoMo 多跳 +10 / −4、时间 +5 / −0），但分题型都没有到 p < 0.05；整体只有 LoCoMo 上对 B4 显著。最终以 N9 的 test400 与 LoCoMo 其余 7 段对话为准。
- **另一个代价**：笔记式阅读让回答更长（LoCoMo 平均 33 → 41 个词），按 LoCoMo 原论文的 token F1 计反而下降（0.236 → 0.195）。F1 惩罚长回答，本项目以 LLM 判分为主指标，F1 只作参考。

## D-031 图扩散（个性化 PageRank）：实现了，默认不开

- **状态**：已实现，默认关闭（N5；回答了设计文档 §11 "图结构用三部图还是只用实体图"）
- **背景**：设计里 L2 的多跳手段是 HippoRAG 式的实体图扩散：以问题点名的实体为种子，在"实体—事实—片段"图上跑个性化 PageRank，一步召回多跳相关的事实与片段。
- **先看图本身**：只用巩固时抽取出的实体关系，图上几乎没有边可走。dev100 的一个空间平均约 230 条事实、150 个实体，"用户"本人连着约 95% 的事实，其余实体的中位度数是 1；LoCoMo 每段对话的两位说话人各连着 39%–56% 的事实。所以图做了三处改动：
  - 节点用实体、事实、轮三类（三部图），边有四种：事实—实体、事实—来源轮、实体名在原话里出现的提及边（抽取只把少数关系记成事实，原话里提得更多）、语义相近的事实之间的边（余弦 ≥ 0.8，每条最多 5 个邻居，把散落在不同会话的同类事实连起来，相当于结构化的伪相关反馈）；
  - 连着超过 20% 事实的枢纽实体不进图：经过它们的扩散等于把分数均匀撒开；
  - 种子 = 问题与计划里点名的实体（越专指权重越高）+ 第一轮融合后排在前面的 10 条事实与 5 轮；d = 0.5，scipy.sparse 迭代，几百个节点几毫秒。图扩散作为一路排名，以 0.5 的权重并入融合。
- **实测**（dev100 纯检索，与"查询规划、不补检索"相比；指标为发言召回（全部） / NDCG / 多会话题召回）：

  | 配置 | 召回（全部） | NDCG | 多会话题召回 |
  |---|---|---|---|
  | 查询规划，不做图扩散 | 95.4% | 83.3% | 87.6% |
  | + 图扩散（四种边） | 95.2% | 84.1% | 86.9% |
  | + 图扩散（只用抽取出的边） | 95.5% | 83.8% | 87.8% |
  | + 图扩散（不连相似事实） | 95.0% | 83.9% | 85.9% |
  | + 图扩散，权重 1.0 | 95.2% | 81.1% | 86.9% |
  | 查询规划 + 补检索，再加图扩散 | 96.3% → 96.4% | 83.7% → 84.6% | 90.9% → 91.4% |

  所有变体的召回差异都在 ±0.5 个点以内。证据按时间排序展示，排序只决定"哪些轮装得进预算"，NDCG 的小幅变化对 reader 没有意义。
- **决策**：默认关闭，保留为选项（`L2Config.ppr`）。LongMemEval 的多会话题主要是"同一类事情散落在多次对话里"（买过几件首饰、修过几样厨房用品），靠的是把同一类事情找全，不是沿实体关系跳几步；这件事子查询与补检索做得更直接。dev100 端到端：B5-ppr 88%，B5 89%（+1 / −2）。LoCoMo 的多跳题更依赖人物关系，所以在 LoCoMo 上另跑一个预先声明的变体 B5-ppr 作检验。
- **LoCoMo 检验**（385 题）：B5-ppr 90.1%，B5 89.1%（+8 / −4，p = 0.39）；多跳题 91% 对 88%（+3 / −1）。对当前 L1，B5-ppr +22 / −7（p = 0.008），多跳题 +10 / −2（p = 0.04），比不加图扩散的 B5（+21 / −10、+10 / −4）更稳。方向与"实体关系更稠密的数据上图扩散更有用"一致，但对 B5 的差异不显著，默认值不因检验集的结果改变；N9 用 LoCoMo 其余 7 段对话（没看过的数据）再测一次。
- **为什么在这里不灵**：图扩散的上限由图的质量决定，而对话抽取出的实体图是"一个人连着所有事"的星形图；PPR 适合实体关系稠密、需要桥接实体的多跳问答。

## D-032 重排（cross-encoder）：不采用

- **状态**：已实现，不采用（N5）
- **实现**：QwenCloud 的 qwen3-rerank（原生接口，$0.10 / 百万 tokens），对融合后的前 30 条候选打分，最终名次 = 融合名次与重排名次的 RRF；结果进响应缓存，用量记账。
- **实测**（dev100 纯检索，发言召回（全部） / NDCG）：查询规划 95.4% / 83.3%，加重排 95.2% / 84.7%；L1 6k 不用 BM25 95.6% / 83.7%，加重排 96.0% / 85.1%。召回基本不变，NDCG 提高 1–1.5 个点。成本：LongMemEval 一轮约 490 tokens，30 条候选每题约 1.5 万 tokens，约 $0.0015，是查询规划的 10 倍，与 B4 整题的回答成本相当；延迟加几百毫秒。
- **决策**：不采用。原因是打包方式：证据按时间排序展示，排序只决定哪些轮装得进预算，衡量它的是"预算内的召回"，而重排没有提高这个指标；NDCG 的提高只是预算内部的顺序，对 reader 没有影响。实现保留，供以后"证据按相关度排序"或预算更紧的场景使用。
- **附带结论**：重排没有让 BM25 变得有用（D-026 修订）。

## D-033 N7 的两个基线：规则版控制器（B6r）与模型自主检索（B3）

- **状态**：已采纳（N5）
- **背景**：核心问题（D-001）是"要不要检索、检索多深"由谁决定。N7 要训练可学习的控制器，需要先有两条基线：最简单的外部策略（规则），以及把决定完全交给 LLM 的做法（ReAct 式自主检索）。N5 有了 L1、L2 两档之后就能实现它们。
- **决策**：
  - **B6r 规则版控制器**：只看问题里的线索，不调用 LLM、不看检索结果；问计数或聚合（how many、total、几次……）、时长（how long、几天）、先后（first、last、before、after，排除 "last week" 这类时间表达）、比较（more、most……）时走 L2，其余走 L1。规则在看到 L2 的逐题结果之前写定。L1、L2 两条路径与 B4-nobm25、B5 完全相同，回答直接命中它们的缓存，成本按实际走的路径计。
  - **B3 模型自主检索**：reader（同一个 deepseek-flash、同一套系统提示）带 `memory_search`（L1 检索，每次 2k tokens，跨次去重、编号连续）与 `date_diff` 两个工具，再加一个 `answer` 工具交卷；最多 5 步，最后一步点名要求调用 `answer`。只限制可用工具不够：最后一步只给 `answer` 时，DeepSeek 仍会照着历史里出现过的工具名继续调用 `memory_search`，第一版因此在多步之后全部回答"不知道"。点名之后仍不交卷的（100 题里 3 题），用标准 reader 读它检索到的全部记忆作答，并在结果里注明。
- **dev100 结果**：

  | 方法 | 准确率 | 名义成本 / 题 | LLM 调用 / 题 | 说明 |
  |---|---|---|---|---|
  | L1（B4-nobm25） | 81% | $0.0016 | 1.00 | |
  | B6r 规则版控制器 | 88% | $0.0028 | 2.45 | 62% 的题走 L2 |
  | B5 always-L2 | 89% | $0.0034 | 3.25 | |
  | B3 模型自主检索 | 86% | $0.0033 | 2.59 | 平均检索 2.8 次 |
  | 理想路由（每题选最便宜且答对的一档，事后看答案） | 92% | $0.0019 | — | 不可部署，N7 的上限 |

  B6r 对 L1 +8 / −1（p = 0.039），对 B5 −1（+2 / −3），成本低 18%。走 L2 的 62 题里答对 90%，走 L1 的答对 84%；多会话类的 27 题（含 3 道拒答题）里 26 题走 L2，单会话题几乎都走 L1。B3 对 L1 +5（p = 0.30），对 B5 −3（p = 0.55）。
- **成本口径的说明**：名义成本按全部输入计价（D-010）。B3 每一步都把前面的对话重新发一遍，DeepSeek 的前缀缓存命中了 46% 的输入 tokens，按缓存价计算每题约 $0.0020；B5 的各次调用之间没有这种重复。比较 B3 时两种口径都要看。
- **LoCoMo**（385 题）：B6r 只把 30 题（8%）送到 L2，准确率 86.0%，与 L1（86.2%）几乎一样，比 always-L2 少 12 题（+9 / −21，p = 0.043）；理想路由 91.7%、每题 $0.0016。规则看的是计数、时长、先后、比较这类措辞（how many、how long、first……），LongMemEval 的多会话题和时间题大多带这些词；LoCoMo 的多跳题（"Caroline 可能会选什么专业？"）几乎不带：74 道多跳题里只有 5 道走了 L2。只看问题措辞的规则不能跨数据集迁移，这正是 N7 要用检索探针特征、做跨数据集评测的原因。B3 只在 dev100 上跑（成本与 N7 的计划）。
- **后果**：在 dev100 上，规则版控制器拿到了 L2 的大部分收益；在 LoCoMo 上它几乎不触发、等于 L1。两个数据集上理想路由都在 92% 左右、成本接近 L1，说明"何时升级到 L2"还有很大的空间，这是 N7 可学习控制器要做的事，规则版是它必须超过的基线。
- **N7 复核**：上面"还有很大的空间"的判断不成立。理想路由的大部分收益来自回答的随机翻转：同一道题 L1、L2 的证据只差一点，回答就可能翻转，三个开发集上 L2 救回 45 题、又弄错 17 题。按真实题型路由（多会话与时间题走 L2）才是现实的上限，见 D-038。B3 在 LoCoMo 上 88.8%（每题 $0.0028），接近 always-L2。B3 在这个强 reader 上不差，但调用次数和延迟不可控（检索 0–10 次），N7 会把它作为"让 LLM 自己决定"的代表做正面比较，并在更小的 reader 上复测（H3）。

## D-034 MemLens 的接入：开发集取子集之外的题，官方 195 题整体留作测试；判分用官方提示词

- **状态**：已采纳（N6；修订了设计文档 §8.1 "从 195 题子集里划出约 45 题做开发"）
- **数据**：MemLens（arXiv 2605.14906，CC-BY-4.0）789 题，五种能力（信息抽取 / 多会话推理 / 时间推理 / 知识更新 / 拒答），同一批题按对话历史长度分 32K、64K、128K、256K 四档；图片附在发言上，共 4,695 张（中位尺寸约 390×280）。格式与 LongMemEval 相同，证据只标到会话。32K 档每题约 13.5 个会话、12.8 张图；128K 档约 47 个会话、48 张图。
- **划分**：原计划从官方的 195 题记忆智能体子集里划 45 题做开发，太少。改为：子集之外还有 594 题，从中按题型分层抽 100 题作开发集（`memlens_dev100`），195 题子集（`memlens_agent195`，61 / 35 / 48 / 29 / 22）整体留作测试集，便于与论文里的 7 个记忆智能体比较。两套划分没有重叠；划分文件对 32K、128K 两档通用。
- **判分**：逐字照搬官方 `llm_judge.py` 的提示词（按题型给评分标准与例子，`src/cuemem/evals/memlens_prompts/`，MIT 许可），输出 `{"answer_score": 0/1}`；超过 500 词的回答按官方做法直接判 0。官方判分模型是 Qwen3-VL-235B，QwenCloud 上没有，用与其他数据集相同的 qwen3.8-max（与 DeepSeek 的回答模型不同家族）。数字与论文横向比较时要注明这一差异。判分提示词约 1,750 tokens，每次名义 $0.004；QwenCloud 的隐式前缀缓存命中约 1,024 tokens 后，实际约 $0.0022。
- **构建与回答分开**：`cuemem eval run --build-only` 只做写入与巩固（全部用通义的模型：向量、图片向量、图片描述、事实抽取），可以在 DeepSeek 高峰时段跑；回答与判分放到非高峰。巩固时遇到通义内容审核误拒，兜底用 deepseek-flash，在高峰时段会暂停到 18:00（32K 开发集 3 / 100 份、32K 测试集 12 / 195 份、128K 测试集约 20 份）。线程会被这些暂停占住，128K 的构建因此改用 24 个线程，暂停的空间各占一个线程，其余照常推进。
- **评测中发现并修复**：QwenCloud 在 JSON 模式下偶尔中止生成（400 "Model output became abnormal"），同样的请求重发多半还会中止。结构化输出遇到它时补一句提示、换一个请求重试；单张图描述失败不再让整份历史的巩固失败。

## D-035 图片写入：原图按内容哈希存放，描述在巩固时生成（上下文感知 + 孤立两种），并填回原话参与事实抽取

- **状态**：已采纳（N6）
- **决策**：
  - **在线写入**（不调用 LLM）：原图按 SHA-256 存进媒体库（同一张图只存一份），每次出现记一条图片记录（同一张图在不同发言里上下文不同）；用 tongyi-embedding-vision-plus 算图片向量（1152 维，与文字同一个向量空间），每个记忆空间另建一个图片向量集合。
  - **巩固**：每张图生成两种描述——**上下文感知**（模型同时看图和前后各一条发言）与**孤立**（只看图），外加图中文字与关键词。模型用 qwen3.8-flash：实测能读图，单价最低，写入不在读路径上，不受 DeepSeek 高峰影响。两种描述都作为检索单元（`image`、`image_iso`），像事实一样指回原话所在的轮；孤立描述只用于对比实验。
  - **实体绑定**：抽取事实时，把上下文感知描述填回原话里图片的位置（`[Image: 描述 Text in the image: …]`），图片里的信息因此也进入事实与实体（"用户在 Oxford Street 拍到一辆 390 路红色双层巴士"）。不带图的会话渲染结果与之前逐字相同，LongMemEval、LoCoMo 的抽取缓存照常命中，流水线版本不变。
  - **遗忘**：删除发言时一并删除图片记录与图片向量；原图文件没有其他记录引用时删除。
- **成本**（MemLens 32K dev100，100 份历史、1,279 张图、1,205 个不同的会话）：构建实际花费 $1.28，其中通义对话模型（描述 + 抽取 + 对账）$1.07、文本向量 $0.20、图片向量 $0.008。图片描述一次平均输入 652 tokens（图片 + 前后对话 + 提示词）、输出 147 tokens，每张图两种描述约 $0.00033。128K 测试集 195 份 $7.95（每份约 $0.04）。
- **描述的作用**（dev100 端到端）：加上下文感知描述，对纯文本记忆 +13 / −3（p = 0.021），38% → 48%；"不知道"式的误拒答 48 → 30 次。
- **上下文感知 vs 孤立（H6）：没有得到支持**。检索上上下文感知描述略好（关键图片所在轮的召回 65.1% 对 60.7%），端到端反而是孤立描述多对 3 题（51% 对 48%，+7 / −4，p = 0.55）。例子里能看到原因：上下文感知描述会写出图片在对话里的含义（"用户提到的、上一段感情留下的礼盒""用户说自己喜欢的那副图案简洁的塔罗牌"），孤立描述把同样的字数都用在画面细节上；MemLens 的题大多问画面细节（颜色、数量、图中文字）。默认仍用上下文感知描述：它帮助检索，也把图片和对话里的实体绑在一起（事实抽取的输入）；"描述里该写多少对话含义、多少画面细节"留到 N9 用更有针对性的题检验。

## D-036 图片检索：描述作检索键，再加一路以文搜图（默认开启）

- **状态**：已采纳（N6）
- **背景**：图片的信息在检索时只有两条路能用上：描述（文字）与图片向量。MemLens 每道题的关键图片放在 `needle_images/` 下，可以直接衡量"关键图片所在的轮有没有装进上下文"。
- **实测**（dev100 中已构建完成的 89 道非拒答题，75 道的证据会话里有关键图片；`scripts/tune_mm.py`，只用通义的向量接口）：

  | 配置 | 会话召回（全部） | 关键图片所在轮的召回 |
  |---|---|---|
  | 纯文本（图片只留占位） | 90.9% | 51.2% |
  | 对话 + 上下文感知描述 | 90.9% | 64.2% |
  | 对话 + 孤立描述 | 90.2% | 60.1% |
  | 对话 + 描述 + 事实 | 92.5% | 56.5% |
  | 对话 + 描述 + 事实 + 以文搜图 ×0.5 | 92.6% | **85.3%** |
  | 只用以文搜图（不用描述键） | 94.1% | 85.4% |

  - 描述让关键图片所在轮的召回 +13 个点；上下文感知描述比孤立描述多 4 个点（H6 在检索上方向成立）。
  - 事实键会把预算让给别的轮，多会话题上关键图片的召回从 48% 掉到 26%。
  - **以文搜图是最大的杠杆**：+29 个点，多会话题 26% → 80%、知识更新 48% → 78%。问题里的视觉线索（"那辆红色巴士""收据上的金额"）与图片本身在图文向量空间里很近，而描述只是有损的文字转述。
- **决策**：L1 默认开启以文搜图（作为与 dense、sparse 并列的第三种模态参与 RRF，权重 0.5）。空间里没有图片时这一路自动跳过，不增加延迟与成本，LongMemEval、LoCoMo 的结果不变。描述键保留：只用以文搜图时召回相同，但描述还要作为可读的证据给 reader。
- **端到端：检索提高了，准确率没有**。

  | 对比（去掉以文搜图 → 默认） | 关键图片所在轮的召回 | 准确率（配对） |
  |---|---|---|
  | dev100：B4-novis → B4-mm | 57.0% → 86.2% | 52% → 51%（+2 / −3） |
  | dev100：B4-see-novis → B4-see | — | 61% → 58%（+3 / −6，p = 0.51） |
  | 测试 32K：B4-see-novis → B4-see | 61.7% → 87.2% | 62.6% → 63.1%（+8 / −7） |
  | 测试 128K：B4-see-novis → B4-see | 53.6% → 72.0% | 57.4% → 55.9%（+8 / −11，p = 0.65） |

  事先声明的"历史越长、以文搜图越有用"在 128K 上也没有出现。可能的原因：以文搜图找来的是"看起来像"的图，所在的轮挤掉了预算里别的证据（装入的轮数少 1–2 轮）；而关键图片本身，描述键与事实已经能把它附近的对话找回来，回答需要的往往是对话里的信息加上看清图。默认值是在端到端之前按开发集的纯检索定的，不因为测试集的结果改；它的价值可能在"挑哪几张原图附上"而不是"装哪几轮"，留给 N7（控制器决定要不要用、用在哪）与 N9 复核。

## D-037 回答时再感知：附上相关度最高的 3 张原图

- **状态**：已采纳（N6；验证了假设 H5）
- **背景**：MemLens 论文的发现是：长上下文模型能直接看图，但随长度退化；记忆智能体对长度稳定，但写入时把图压缩成文字，丢了视觉细节。设计上的折中是"索引时压缩 + 回答时再感知"（D-003）：检索与阅读都基于描述，需要细节时把原图取回来再看一眼。
- **决策**：装入上下文的轮里的图片按相关度排序（描述键与以文搜图的名次），取前 3 张，缩放到最长边 768 像素，附在文字证据之后、问题之前；文字里在对应位置注明"see picture k"。回答模型仍是 deepseek-flash（实测能读图），方法之间只差"给不给原图"。是否附图目前是方法级的开关（B4-see、B5-see），N7 交给控制器按问题决定。
- **实测**：

  | 对比（配对） | dev100（32K） | 测试 32K | 测试 128K |
  |---|---|---|---|
  | B4-see 对 B4-mm（再感知） | +8 / −1，p = 0.039 | +26 / −2，p < 0.001 | +19 / −5，p = 0.007 |
  | 准确率 | 51% → 58% | 50.8% → 63.1% | 48.7% → 55.9% |
  | 信息抽取题 | 45% → 71% | 41% → 72% | 44% → 69% |
  | 误拒答（"不知道"） | 25 → 14 | 49 → 20 | 45 → 24 |

  提升集中在信息抽取题：颜色、数量、图中文字、位置关系这类细节，描述写不全，看原图才答得出。
- **成本**：每题多约 670 个输入 tokens（3 张图，每张约 220 tokens；MemLens 的图中位尺寸约 390×280），名义成本 +$0.0002，约 +11%；延迟 p50 +0.2 秒。对照：全上下文直接看图每题 2.7 万（32K）到 13.5 万（128K）tokens。
- **长度稳定性**（同一批 195 题从 32K 换到 128K，配对）：B1 全上下文 52.3% → 46.2%（+4 / −16，p = 0.012），成本涨 5 倍；L1 的 B4-see 63.1% → 55.9%（+8 / −22，p = 0.016，证据会话的召回 93% → 80%）；L2 的 B5-see 65.6% → 64.6%（+14 / −16，p = 0.86，会话召回 89%）。"记忆系统对长度稳定"不是自动成立的：L1 的单次检索在长历史里同样会丢证据，靠 L2 的子查询与补检索才稳住。
- **与只给证据会话的 ORACLE 比**：B5-see 在 32K 上比 ORACLE 高 10 个点（+30 / −11，p = 0.004）。ORACLE 一次给出全部证据会话与其中所有图片，回答模型要在长对话和十几张图里自己找；B5-see 给的是事实、带描述的片段、挑过的 3 张原图，外加先记笔记再回答。"给对的东西"比"给全部相关的东西"更好。
- **参照**（判分模型不同，不能直接比较）：论文里最强的长上下文模型在全部 789 题、32K 上是 58.68%，128K 上表现最好的 Gemini-3.1-Pro 是 51.99%；多会话推理上多数系统低于 30%。本项目 B5-see 在 195 题子集上 65.6% / 64.6%，多会话题 49% / 49%。

## D-038 检索控制器：两段式（门控 + 推理类型 → 查表），标签按推理类型构造

- **状态**：已采纳（N7；修订了设计文档 §6.3 的"进阶版"）
- **背景**：设计文档的方案是离线全信息标注——每道题的每个动作（L0 / L1 / L2，MemLens 上另有再感知开 / 关）都跑一遍、判分——再为每个动作学一个校准后的答对概率 P̂(a | x)，按 P̂ − λ · ĉ 选动作。三个开发集 585 道记忆题标注完之后，发现结果标签的噪声很大：
  - L2 对 L1 救回 45 题、又弄错 17 题；单跳 / 单点事实题上是 +6 / −5，基本是随机翻转；
  - 事后的"理想路由"（每题选最便宜且答对的动作）88.5%、每千题 $1.41，比 always-L2 还准还便宜，但它吃进了这些翻转；
  - 按真实题型路由（多会话与时间题走 L2）只有 84.4%、$2.44。
  直接拟合每个动作答对与否，模型学到的主要是"这题难不难"（几档同时对或同时错），而不是"哪一档更好"。
- **决策**：控制器分两段。
  1. **门控与推理类型**：用探针特征（54 个，`read/probe.py`）先估计"这一问与记忆无关"的概率（二分类逻辑回归），再在记忆题里估计属于哪类推理：单点事实、多会话 / 多跳、时间推理、知识更新、偏好、开放推断、拒答。多分类逻辑回归，只在记忆题上训练。三个数据集的题型映射到这七类。
  2. **查表**：各档在各类题上的准确率从训练数据统计，样本少的类向记忆题的总体均值收缩（先验强度 5）；再感知的增益只从有图的数据（MemLens）统计。P̂(a | x) = Σ_t P(t | x) · acc(a | t)，按 P̂ − λ · ĉ(a) 选，平局选便宜的。
  门控与类型分开学：混合流里无关查询是记忆题的两倍，放在同一个多分类里会挤占推理类型的分类，"要不要记忆"的概率也不够锐利。标准化后的特征截断在 ±5 以内：换了向量模型、换了语言时不会外推出极端的概率（第一版在离线哈希向量的测试空间上把一道聚合题判成"100% 与记忆无关"）。
- **备选与取舍**（交叉拟合，三个开发集合并）：
  - 直接拟合每档答对概率（原方案）：记忆题曲线下面积 0.814，两段式 0.820；
  - 只分"深 / 浅"两类：与七类相近，七类还能给出知识更新、拒答这些信息；
  - Adaptive-RAG 式的"最便宜且答对的动作"作多分类标签：同样受翻转噪声影响，而且没有 λ 可调；
  - 梯度提升树（sklearn 的 HistGradientBoosting）：探索阶段在"直接拟合每档答对概率"的设定下不比逻辑回归好，也不好导出成可读的参数；两段式没有再试。
  运行时模型就是两次矩阵乘法，参数是一个 JSON 文件（`src/cuemem/read/controller_model.json`），不依赖 scikit-learn；训练（`evals/routing.py`）与运行时（`read/controller.py`）有测试保证逐位一致。
- **实测**（`docs/results/n7-controller/`）：
  - 记忆题上，B6（λ = 30）81.2%、每千题 $2.14，对 always-L1 +19 / −15，没有赢过规则版 B6r（82.6%、$2.01，+9 / −17，p = 0.17）；
  - 推理类型里多会话 / 多跳最难分（44% 被当成单点事实）；词袋 TF-IDF 分类型比探针特征更准（78% 对 74%）。类型由"问题怎么问"决定，检索反馈帮不上忙。
- **后果**：在 L1 与 L2 之间路由，可挣的空间远小于理想路由显示的那样。同样的证据，换一种读法（先记笔记再回答，L1 只多 $0.0003）比换一档检索更划算：B4-note 在 LongMemEval 上 86%、LoCoMo 上 88.6%，优于所有路由策略。控制器的价值在"要不要动用记忆"（D-039）。N9 复测时可以考虑把 L1 的默认读法改成先记笔记。

## D-039 混合流：通用请求 + 同话题难负例，评测"该不该想起"

- **状态**：已采纳（N7）
- **背景**：三个记忆基准里每道题都要用记忆（拒答题也要先查过才知道没有），评测不出 L0 的决策；但真实的助手流量里，多数轮次不需要长期记忆。设计文档 §8.1 计划自建混合流。
- **决策**：
  - **通用请求**：databricks-dolly-15k（CC BY-SA 3.0）里不带参考材料的四类（开放问答、一般问答、头脑风暴、创作），按类别比例抽 585 条，与记忆题一样多。仓库只记行号，不提交原文。
  - **同话题的难负例**：对每道记忆题，让 qwen3.8-flash 写一个话题相同、但与用户本人无关的问题（"Gina 的网店是什么时候开的？" → "开一家网上服装店通常要经过哪些步骤？"），585 条，生成结果提交在 `evals/mixed/topic_negatives.jsonl`（温度 0，可复现）。
  - **配对的空间**：难负例用它对应的那道记忆题的空间与提问时间，探针在同一个话题上会有很强的命中，最难分辨。通用请求随机借一道记忆题的空间。交叉验证时难负例与对应的记忆题在同一组。
  - **结果的假设**：无关查询在任何一档都能答好（L0 就够），各档成本取所在数据集记忆题的平均值；回答模型对它们不会自称"不知道"，这是对按不确定度升级最有利的假设。报告"记忆题准确率"与"平均成本"两个数，按记忆题占 20% 与 50% 两种比例混合，另报误召回（无关查询走了检索）与漏召回（记忆题被放到 L0 且答错）。
- **实测**（记忆题占 20%）：
  - 总是检索（always-L1）每千题 $1.57；
  - B6 $0.87（−45%），记忆题 81.2%，误召回 19%，记忆题被放到 L0 的 2.4%；
  - 零样本 LLM 路由 B6z $0.72，80.7%，误召回 0.4%，但 5.3% 的记忆题被判"不需要记忆"（偏好类问题、指代已分享图片的问题），而且每问多一次调用（p50 0.58 秒）；
  - 只在门控拿不准时问 LLM 的 B6h $0.80，误召回 10%，19% 的查询多一次调用。
  - "要不要记忆"的 AUC：只看问题线索 0.79、只看探针反馈 0.96、两者合用 0.98、词袋 0.96。
- **局限**：难负例由 LLM 生成，风格整齐（多以 "What are common…" 开头），比真实流量容易识别；MemLens 的问题带格式要求（"Answer with a date…"），也是数据集特有的线索。这些都让交叉验证的数字偏乐观；跨数据集的结果（D-040）更接近换场景时的真实表现。

## D-040 默认 λ 按"不比总是检索差"选；auto 模式默认用学到的控制器，探针的候选直接复用

- **状态**：已采纳（N7）
- **默认 λ**：λ 是运行时旋钮，扫描 λ 得到帕累托曲线。默认值按事先定的产品规则选：三个开发集的记忆题合并后，准确率不低于 always-L1 的最大 λ（"不比总是检索差的前提下最省钱"），结果是 λ = 30（单位：每美元）：多花 $0.001 的期望成本，至少要换来 3 个百分点的答对概率；等价于"多答对一题最多愿意多付 1/λ ≈ 3.3 美分"。
  - 第一版规则是"不低于 always-L2 减 1 个点"：加入无关查询训练后只有 λ = 0 满足，而 λ = 0 时所有查询都走 L2，在混合流上完全不省钱。改规则的原因与时间都记在这里：改在看测试集之前，测试集到 N9 才用。
- **运行时**（`MemorySystem.ask(mode="auto")`，CLI `cuemem ask --mode auto --router …`）：
  - `router="learned"`（默认）：先跑探针（一次查询向量化 + 本地检索，p50 56–271 毫秒），控制器选档；选 L1 时直接用探针的候选打包，不重复检索；选了再感知就附 3 张原图。没有模型文件时退回规则版。
  - `router="hybrid"`：门控的 P(无关) 在 0.1–0.9 之间时问一次零样本 LLM 路由，把它的判断换成固定的概率（0.95 / 0.05）。区间与概率事先定好，没有在评测数据上调。
  - `router="llm"`：零样本 LLM 路由（qwen3.8-flash 只看问题文本）；`router="rule"`：规则版 B6r。
  - 控制器的选择、各动作的答对概率与效用、探针耗时都记在回答的 details 里，CLI `--show-context` 会显示。
- **核对**：最终模型在三个开发集上真实运行，每道题的选择与离线重放逐题一致（585 / 585），回答全部命中缓存。开发集上的真实运行是样本内的，只用来核对代码路径。
- **跨数据集**：只在另外两个数据集上训练时，门控把 LoCoMo 的第三人称问题当成无关查询（55% 的记忆题被放到 L0，86.5% → 43.9%）；词袋迁移得好一些（77.1%）。加上目标数据集里随机的 20 条带标注的样本（总权重是其他数据的一半），LoCoMo 回到 85.7%（被放到 L0 的记忆题 2.5%）；MemLens 要 100 条才从 38% 回到 56%。上线时可以从规则或零样本路由起步，攒几十条带反馈的日志后校准；用线上的部分反馈持续学习（☆ 上下文 bandit）留到以后。

## D-041 H3 否证：换了回答模型，模型自主检索最好；把它作为控制器的一档留到 N9

- **状态**：已记录（N7；对 D-001 的补充）
- **背景**：H3 设想控制器在不同回答模型之间比模型自主检索（B3）更稳定，在小模型上优势更大。N7 用 qwen3.8-flash 作第二个回答模型，在 LongMemEval dev100 与 LoCoMo 385 题上重跑 L0 / L1 / L2 与 B3（探针特征与回答模型无关，B6 用主实验交叉拟合的选档）。
- **实测**：

  | 方法 | LongMemEval：deepseek-flash → qwen3.8-flash | LoCoMo：deepseek-flash → qwen3.8-flash |
  |---|---|---|
  | always-L2 | 89.0% → 82.0% | 89.1% → 86.2% |
  | B6r 规则版 | 88.0% → 82.0% | 86.0% → 81.8%（p = 0.020） |
  | B6 学到的控制器 | 84.0% → 82.0% | 86.5% → 81.8%（p = 0.005） |
  | B3 模型自主检索 | 86.0% → 91.0% | 88.8% → 90.1% |

  qwen3.8-flash 下 B3 在 LoCoMo 上对 always-L2 +28 / −13（p = 0.028），每千题 $1.41 对 $2.28；检索次数更少（1.4 次对 deepseek-flash 的 2.2 次）。
- **解读**：
  - qwen3.8-flash 读一大段静态的检索结果不如 deepseek-flash，但在"查一次、读几条、再决定"的循环里更强。
  - "让 LLM 自己决定检索"好不好，取决于这个模型会不会用工具。控制器的选档不随回答模型变，它的结果却随回答模型变。
  - D-001 的出发点（"质量不应由模型能力驱动"）在这里得到的是反例：换了模型，最好的方法也换了。
  - 两点保留：qwen3.8-flash 不是更小的模型，"小模型上控制器优势更大"没有测到；它与判分模型同一家族（D-008），两个回答模型之间的绝对准确率不能直接比，同一回答模型下方法之间的比较仍然有效。
- **决定**：
  - 控制器保持现在的设计：它的价值在"要不要动用记忆"与成本上限（D-039、D-040），这两点与回答模型无关。
  - N9 把模型自主检索作为控制器的一档（"交给模型自己查"，成本按实际调用计），在 2–3 个回答模型上评测控制器何时该交出去；"小模型"那一半也在 N9 用真正更小的模型补测。

## D-042 Agent：控制器先选、模型兜底（memory_search 作为逃生通道）

- **状态**：已采纳（N8；落实 D-001 里"LLM 自主检索保留为逃生通道"，并回应 D-041）
- **背景**：N7 的结论有两面：控制器的价值在"要不要动用记忆"和成本上限；换了回答模型（qwen3.8-flash），模型自主检索（B3）反而最好。Agent 要在两者之间选一个结构。
- **决策**：每条消息先由控制器选档并召回（不调用 LLM 的探针）；模型拿到召回结果后仍可以调用 `memory_search` 自己补查，编号接着往下排，已经给过的不再重复给。工具调用最多 4 步，最后一步不允许再调用工具。
- **备选**：只用控制器（门控失准时就答不出来）；只让模型自己查（每条消息至少多一次往返，模型也可能不查；B3 在 deepseek-flash 上不如固定检索）。
- **实测**（演示剧本，13 轮）：门控在导购对话里失准，"How has my shoe budget changed since we first talked?" 被判为 96% 与记忆无关、选了 L0；模型调用 `memory_search` 找到被取代的 $120 与现在的 $180，带引用答对。13 轮里有 3 轮用了逃生通道，其余轮次没有多花调用。
- **后果**：控制器决定"至少给什么"，模型决定"还缺什么"；两者都记在轨迹里，可以分别评测。N9 把"控制器先选、模型兜底"作为一种方法放进测试集评测。

## D-043 上下文：分区预算 + 稳定前缀；画像每会话一份快照；工作记忆成段淘汰、检索时排除

- **状态**：已采纳（N8；实现设计文档 §6.6）
- **决策**：
  1. **分区与预算**：系统提示、工具说明、画像（600 token）、工作记忆（3,000）、召回（4,000，L2 6,000）、当前消息。估算法与 L1 打包相同（汉字约 1 个 token，其他文字约 4 个字符 1 个 token）。
  2. **稳定前缀**：系统提示、画像、工作记忆在前，同一会话里每轮的请求都以上一轮请求开头；日期和召回的记忆只放在最后一条消息里，下一轮不保留。工作记忆里的助手回复去掉引用编号（编号只在当轮有意义）。
  3. **画像快照**：会话开始时取一次，会话里不随后台巩固更新（换取前缀稳定）；遗忘后重取。
  4. **成段淘汰**：工作记忆超出预算时一次淘汰到预算的一半，前缀只在淘汰的那一轮变一次；被淘汰的轮已经在长期记忆里，可以检索到。
  5. **检索排除**：工作记忆里的轮与图片不参与探针和检索（L1、L2、memory_search 都排除），召回的名额留给上下文里没有的内容。
- **备选**：召回内容放进系统提示（很多实现的写法，每轮前缀都变）；每轮挤掉最早的一句（前缀每轮都变）；不排除工作记忆（探针被刚说过的话带偏，召回与上下文重复）。
- **实测**（`scripts/n8_context.py`，关掉本地缓存）：16 轮长会话里，稳定布局有 70% 的输入由供应商前缀缓存提供，对照布局 52%；每次调用要现算的输入 1,036 对 1,461（后 8 轮 1,175 对 1,969）。演示剧本那种每轮召回 4k、历史很短的对话里两者差不多（54% 对 56%）：缓存主要来自工具循环和不变的角色说明。
- **后果**：长对话越长越省；短对话不吃亏。代价是画像在会话中途不更新。

## D-045 对话的写入：每轮追加、序号只增不减；进行中的会话不巩固；新任务取代旧的待办任务

- **状态**：已采纳（N8）
- **背景**：评测时整段对话一次导入；Agent 是一轮一轮写的，会话结束前就要能检索到刚说过的话，而巩固（抽取事实）按会话进行。
- **决策**：
  1. 每轮结束后在线写入新的一问一答（原始日志 + 索引 + 图片向量，不调用 LLM）。发言序号由会话维护、只增不减：遗忘删掉的序号不再复用，否则按位置重算序号会把删掉的内容写回来，或让 ID 错位。
  2. 会话进行中不登记巩固任务（`open_session` / `close_session`），别处触发的巩固与遗忘后的重放也跳过它；会话结束时整个会话抽取一次，在后台完成。
  3. 同一会话的内容变了（又追加了发言）时，新登记的任务把还没执行或失败待重试的旧任务标记为 superseded，避免同一会话被抽取两遍。
- **后果**：会话中途说的话立即可检索（工作记忆淘汰后），事实与画像在会话结束后更新。评测的导入路径不受影响（整段导入时每个会话只有一个任务）。

## D-046 遗忘以整轮为单位并沿引用扩散；画像可引用；trace 一并清理

- **状态**：已采纳（N8；补充 D-021）
- **背景**：第一次真实回放时，遗忘"Ana 的生日"之后，助手仍说出了 "Oct 3"。现场会话的问候引用了画像里的这条事实（"Ana 的 30 岁生日在 10 月 3 日，礼物到了吗？"），那一轮不是事实的出处，没有被删，留在了工作记忆与日志里。同样的问题也出在出处那一轮：只删用户的话，助手在同一轮的回复里复述了同样的信息。
- **决策**：
  1. **整轮删除**：删一条事实或一张图，删的是它出自的那一轮（用户的话 + 助手的回复）。
  2. **溯源与扩散**：每次回复引用了哪些记忆（事实、对话片段、图片）记在溯源表里（`provenance`，原始层，重建派生记忆时不清空）。画像在 Agent 的系统提示里逐条编号（[p1]…），引用画像也有记录。遗忘时，引用过要删的记忆的回复所在的轮也删，并继续往下追，直到没有新的。
  3. **会话同步**：进行中的会话去掉工作记忆里被删的轮，作废被删图片的编号，重取画像快照。
  4. **trace**：属性里含被删原话的 trace 条目一并删除（补上 D-021 的已知限制）。
- **实测**：最终回放里遗忘关于 Ana 的 4 条事实，删掉 6 句发言（出处 4 句 + 引用过它们的问候 2 句），之后问"我妹妹生日是哪天"，模型查了两次记忆，回答不知道。
- **已知限制**：没有引用、只是转述的回复追不到（模型不总是引用）；扩散按"引用过就删整轮"处理，可能多删（宁多勿漏）。
- **验证**：`tests/test_agent.py` 的 `test_forget_follows_citations`、`test_forget_removes_traces_with_the_text`、`test_forget_inside_open_session`，`tests/test_service.py` 的 `test_forget_fact_removes_whole_round`。

## D-050 结构化输出在请求超时时也换备用模型

- **状态**：已采纳（N9）
- **背景**：test400 里有一个会话（12 轮、约 1.9 万字符的普通问答），qwen3.8-flash 在 JSON 模式下抽取它时生成失控。流式请求时服务端直接中止（"Model output became abnormal"），非流式请求则一直不返回，直到客户端 120 秒超时。三个小时里重试了 5 次都超时，这道题在所有方法上都跑不成。同样的输入单独请求，有时 6 秒就正常返回，有时等满 240 秒也不返回：问题出在这个模型对这条输入的生成，不是网络。
- **决策**：`LLMClient.structured` 原来只在内容审核拒绝时换用 `fallback_model`（巩固时是 deepseek-flash），现在请求超时（`APITimeoutError`）也换。超时之前 SDK 照常重试；回退只在主模型彻底失败时发生，成功的请求、缓存键都不变。
- **理由**：
  - 生成失控和内容审核误拒是一类问题：都是"这个模型在这条输入上出不来结果"，重发同样的请求多半还是一样，换一家的模型就能过。
  - 回退由备用模型产出的结果照常缓存，复现时直接命中。
- **后果**：
  - 一个会话超时要等满 SDK 的重试（4 × 120 秒）才回退，慢，但不再整题失败。
  - 被回退的会话由另一个模型抽取，事件 `llm_fallback` 记下了原因。
  - 这一次加了回退之后重建，qwen 第一次请求就正常返回了，回退没有触发；测试集上的记忆都是 qwen3.8-flash 抽取的。

## D-051 遗忘一条事实时，也删掉没有引用、只是转述了它的发言

- **状态**：已采纳（N10；补上 D-046 记下的已知限制"没引用、只是转述的回复追不到"）
- **背景**：录 README 的演示动图时，按演示指南在界面上遗忘"Ana turns 30 on October 3"，最后一问"我姐姐生日是哪天"仍然答出了 10 月 3 日。原因有两处：
  - 九月那次对话里，助手在下一轮回复中顺口说了"her birthday is October 3rd"。当时生日还不是一条可引用的事实，所以没有引用；沿引用扩散追不到它。删掉出处、按剩下的日志重建后，抽取器从这句转述里又抽出了"Ana has a birthday on October 3"。
  - 进行中的会话里，助手的问候也提到了生日，同样没有引用。进行中的会话还没巩固，抽不出事实，只看事实的检查也看不到它。

  剧本回放之所以通过，是因为回放删的是所有含"Ana"的事实，碰巧把转述所在的轮也删掉了。现场按指南只删一条，就会漏。
- **决策**：按事实遗忘时（界面、HTTP、MCP、剧本回放都走 `ChatService.forget`）：
  1. **先在原始日志里找复述。** 对每条要删的事实，按向量取最相近的 8 轮（包括进行中的会话），让便宜的模型（qwen3.8-flash）确认哪些轮仍在透露这条信息。完整复述、换了说法、只透露一部分都算；只是提到同一个人或话题的不算。确认的轮与出处一起删。
  2. **重建之后再兜底。** 看重建出的事实里有没有语义等价的（向量候选 + 模型确认），有就删掉它的出处，最多再追 3 轮。
  3. **报告分开计数。** 遗忘报告记下因复述而删的发言数（`restated`）与重新长出来的事实数（`regrown`），界面上的提示一并显示。
- **理由**：
  - 遗忘的语义是"这条信息不能再被想起"，不只是"删掉它出自的那句话"。助手自己的转述也是派生数据；引用是血缘，而没有引用的转述只能按内容去找。
  - 只靠"重建后看事实有没有长回来"不够：进行中的会话没有巩固，转述不会变成事实，却一直留在模型的对话窗口里。所以主要的检查放在原始日志上，事实层面的检查作兜底。
  - 候选用向量取、结论由模型下：开发时实测，等价的复述与原句的相似度在 0.6–0.9，只是提到同一个人的在 0.5–0.57，单靠阈值分不开；模型确认可以区分"Ana 喜欢徒步"（保留）与"她生日在十月初"（删除）。
- **后果**：
  - 按事实遗忘多了 1–2 次便宜模型调用；兜底那一步每追一轮要多重建一次派生记忆（演示空间约 15–35 秒）。
  - 演示录制时，遗忘删了 6 条发言（其中 4 条是复述），最后一问回答"你姐姐的生日从没在我们的对话里出现过"。剧本回放的 14 项检查仍然通过。
  - 仍然的局限：
    - 候选只取最相近的 8 轮，埋在很长的回复深处、相似度很低的转述可能漏掉；
    - 删图片（而不是事实）时不做这一步：图片的信息散在描述里，"什么算复述了这张图"不好界定；
    - 判断依赖模型，可能把只是相关的内容也删掉。宁可多删，是隐私场景下的取舍。
- **修订（N11 之后，2026-10-13）：只删透露了它的那条发言，按内容找到的转述不沿引用扩散。**
  - **发现**：按 N11 的代码重录演示动图时，遗忘"Ana 10 月 3 日满 30 岁"删了 14 条发言（其中 8 条是"引用了它的后续回复"，4 条是转述），事实 14 → 8：当天的对话整段没了，连"跑鞋换成 40 码"也被删掉。两个机制叠在了一起：转述按整轮删，九月"我跑鞋换成 40 码了"那一轮因为助手的回复顺口提了 Ana 的礼物，连用户的话一起删掉；沿引用扩散又从这一轮出发，删掉由它抽出的所有事实，以及后来所有引用 40 码的回复。N10 录制时这几条回复恰好没提生日，所以没有暴露。
  - **改法**：
    1. 转述检查把候选轮里的发言逐条交给模型，只删确认透露了这条信息的发言；同一轮里用户说的别的事保留。
    2. 按内容找到的转述（以及兜底时重新长出来的事实的出处）一起删，但不从它们出发沿引用扩散；沿引用扩散只从这条事实的出处出发。
    3. 进行中的会话：用户的话或助手的回复被删，都把这一轮从工作记忆里去掉。
  - **结果**：重录时遗忘删了 4 条发言（出处那一轮 2 条，加上 2 条顺口提到生日的回复：九月对话里一条、当天问候里一条），事实 16 → 14；最后一问的回答是"我只知道 Ana，你给她买了登山杖，但你没说过她是你姐姐，也没提过生日"。新增回归测试：转述那一轮里用户说的 40 码、以及后来引用它的回答都保留。
  - **新暴露的局限**：出处那一轮整轮删掉后，后面用代词指向它的话会失去指代。一次重录里，"那副登山杖正合适，我给她买了"被重新抽成"给 Lena 买登山杖"（记忆里只剩 Lena 一位女性）。根治要改抽取提示（指代不明时不要猜），会让评测空间的抽取缓存全部失效，这次没有做；演示剧本里这句改成了"给 Ana 买"。之后由 D-059 解决：重新抽取时标出遗忘留下的空缺，这句抽成"给别人买"，不改流水线版本号。


## D-052 控制器 v2：有图空间查图片空间的准确率表，问画面细节不选 L0；测试集只做事后重放

- **状态**：已采纳（N11；处理 N9 在测试集上记下的三个控制器问题，D-048 当时只记录不修）
- **背景**：N9 在测试集上查出：看图增益相加后截断，L1 + 看图与 L2 + 看图同时被截成 1.0（§5.3）；门控对"指代已分享图片"的问题漏判；"各档准确率"按主回答模型标定，换小模型后照样大量选 L1。N10 之后补做，但测试集已经用过一次，不能再拿它做选择。
- **决策**：
  1. 有图的空间里，各动作的成功率不再"不看图的成功率 + 看图增益，截断到 1.0"，而是直接查**图片空间的准确率表**：推理类型 × {L0, L1, L2, L1 + 看图, L2 + 看图}，只用带图的训练题统计，样本少的类向有图题的总体均值收缩（先验强度 5，与文字表相同）。
  2. 有图的空间里，问题带视觉线索（`q_visual`）或画面位置线索（新特征 `q_scene`）时，L0 抬到 L1 + 看图。`q_scene` 只给这条规则用，不进分类器。
  3. 门控、推理类型模型、λ 的选法都不变（按 N7 的规则在开发集上选出来仍是 30）。
  4. 冻结的 v1 另存为 `controller_model_v1.json`，N7 / N9 的复现固定用它；默认改成 v2。配置项 `retrieval.controller` 指定模型文件。
  5. 测试集只做**事后重放**：把冻结的 v2 在 N9 的测试结果上重放一遍，报告与 v1 的差异，不再据此调任何东西。
  6. 换回答模型时按回答模型设 λ，不重新标定准确率表。
- **备选**：在对数几率上相加看图增益（N9 报告里提的改法）：仍要假设"看图的增益与档位无关"，而有图数据里 L2 + 看图与 L1 + 看图的差别本身就随推理类型变；直接查表更简单，离线与运行时也更容易保持一致。按回答模型重新标定准确率表：试过，见后果。
- **后果**：
  - 开发集（交叉拟合）：81.2% → 81.7%（+5 / −2，n.s.），记忆题被放到 L0 的比例 2.4% → 1.7%，成本 +1%；整条成本—准确率曲线的面积 63.0 → 64.9。
  - 测试集事后重放：81.6% → 81.9%（+10 / −5，n.s.），全部在 MemLens；文字数据集逐题不变。离总是 L2 仍差 2.5 个点。
  - **更正 N9 §5.3**：只改查表确实救回了归因于饱和的 6 道题，但同时改变了另外 70 来道题的选择，32K 上净值 +7 / −7。图片空间的每一格只有开发集 100 道 MemLens 题的数据，噪声大。净收益来自保底规则（救回 v1 放到 L0 的 5 道里的 3 道）。
  - 重新标定准确率表是负结果：用开发集上 qwen3.8-flash 的结果标定后，LongMemEval 93% → 89%、LoCoMo 76.5% → 74.0%；两折交叉标定持平。按回答模型调 λ 有效：λ = 15 时三个回答模型都补回了与总是 L2 之间的大部分差距，成本仍低 16–24%（测试子集上的事后曲线，默认 λ 不变）。
  - 控制器"L1 还是 L2"的能力没有因 v2 变好，N9 的结论不变：价值在"要不要想起"。

## D-053 对账提示分清"范围不同""现实变了""说错了"，并附上原话；不改流水线版本号

- **状态**：已采纳（N11；修 N9 错误分析里的两个对账错误）
- **背景**：N9 的错误分析里，"周五 6 点起"取代了"工作日 6 点半起"，问"周五比其他工作日早起多久"时，模型以为 6 点半已经作废。英文示例里"搬到新加坡"被标成"更正"（`corrected`），validity 没有结束时间，时间线上看起来像"一直住在新加坡"。
- **决策**：
  1. `correct` 只用于用户说之前记错了（"sorry, I meant…""actually it was…"），或新事实把同一件事说得更精确；搬家、换工作这类现实的变化是 `update`。
  2. `add` 明确包含范围不同或更窄的事实：工作日与周五、在公司与在家、这一次旅行与另一次，即使新事实是新近的变化（"周一改在家办公"不取代"在公司上班"）；`update` 的例子从"作息变了"改成"同样的日子换了作息"。
  3. **灰区里每条新事实附上它出自的那句话**（用户的原话，最多 400 个字符）。抽取出的事实只剩"Mia 31 岁"，看不出用户是在更正（"之前说错了"）还是过了生日；只改提示时，联网测试里"说错了"仍被当成"现实变了"。
  4. 提示的开头不变（脚本化的测试模型按提示开头分派）。
  5. **不改 `PIPELINE_VERSION`**：巩固指纹只包含流水线版本、抽取模型与巩固参数，不含提示文本，所以已有的评测空间不会被判为过期而整体重建。
- **理由**：改版本号会让所有评测空间重建（全部重新抽取、对账），既贵又让 N9 的数字无法从现有空间复现。提示的修订只影响之后新写入的记忆。
- **后果**：
  - 新增联网测试 `tests/live/test_reconcile_live.py`：一段新编的小对话（不用测试集原题），检查周五与工作日两条都保留、上海 → 新加坡是 `changed`、年龄说错了是 `corrected`。同一段对话重复 5 次，三类都是 5 / 5；N9 的提示是 3 / 5、5 / 5、0 / 5。提示是对着这段对话改了两轮的（过程见 N11 结果记录），它只说明这两类错误修好了。
  - 删掉评测空间、从零复现 N3–N9 时，对账那部分请求的提示变了，不会命中缓存，重建的记忆会与当时略有不同；要逐字复现，检出 N11 之前的提交（a8b8f07）。

## D-054 Agent 的回答缓存按会话归属

- **状态**：已采纳（N11）
- **背景**：Agent 的回答缓存原来标在空间上（`空间|ask`），遗忘时整个空间的回答缓存一起清掉。演示剧本回放时，遗忘之后再问的问题全部重新调用模型，偶尔答得和录制时不一样，回放检查就失败。
- **决策**：回答缓存改标在会话上（`空间|session:会话 ID`）。遗忘只清受影响会话的回答缓存，加上巩固（`consolidate`）与旧的 `ask` 标签。
- **理由**：缓存的归属应当与数据的血缘一致：一个会话的回答只依赖这个会话看到的记忆，被遗忘的内容出现在哪些会话里，遗忘本来就要找出来（D-046）。
- **后果**：新测试：在 B 会话里遗忘一条事实，A 会话的回答缓存保留，B 的清空。旧缓存条目（标在 `空间|ask` 上的）在遗忘时照旧清理。

## D-055 外部基线 Mem0：同样的模型、同样的回答与判分，按它自己的流程写入与检索

- **状态**：已采纳（N11）
- **背景**：之前只能引用别人在不同设置下报的数字（回答模型、判分模型、提示都不同，D-008 讨论过）。需要至少一个外部系统在同一套评测里跑一遍。
- **决策**：
  1. 选开源的 Mem0（mem0ai 2.2.1）：最常被拿来比较、可以本地运行。作为评测方法 `M0` 接进评测框架（`evals/mem0_baseline.py`），mem0ai 不是依赖，运行时用 `uv run --with` 临时装上。
  2. 按它自己的流程：每个会话调用一次 `add`（Mem0 2.x 一次 LLM 抽取，只增不改，提示里带上最相关的 10 条已有记忆）；检索 `search(top_k=30)`（默认 20，多给一些）；装上 spaCy 与 fastembed，让它的混合检索（语义 + BM25 + 实体加权）完整生效。LoCoMo 是两个人之间的对话，照 Mem0 论文的评测代码：每位说话人一个 user_id，各写一遍（自己的话是 user，对方的话是 assistant，都带名字），检索两边各取 30 条，每条注明是谁的记忆（抽取出的 "User" 指这位说话人）。最初的写法是两人都作为 user 写进同一个 user_id，抽取出的 "User" 分不清是谁，在联网运行之前改掉了。
  3. 同样的模型：Mem0 的 LLM 换成 CueMem 写入路径用的 qwen3.8-flash，向量换成 qwen3.7-text-embedding，都经过 CueMem 的客户端（同一本账、同一个缓存）。回答模型、回答提示、判分与其他方法相同；每条记忆标上来源会话的时间。
  4. 日期：开源版不支持 `timestamp`，抽取提示里的"观察日期"默认是运行当天，"昨天"会被换算到 2026 年。适配层把它换成会话日期，相当于平台版传了 timestamp。
  5. 数据：LoCoMo test200r、LongMemEval test100r（N9 的分层子集），CueMem 各方法取 N9 测试运行里同一批题的结果。
  6. 遥测关闭（`MEM0_TELEMETRY=False`），Mem0 的配置目录放在 `data/` 下，不拉取远程公告。
- **备选**：Zep / Graphiti（需要图数据库服务）、Letta（Agent 框架，记忆由 Agent 自己管理，与 B3 更像）：留作以后。用 Mem0 的默认模型（OpenAI）：结果里混进了模型差异，不是在比记忆系统。
- **后果**：
  - Mem0 的写入花费单独统计（写在每个空间的 `build.json`，不算进回答的用量），有 $10 的上限。
  - 通义的 JSON 模式偶尔直接返回记忆列表（少了外层的 `{"memory": …}`），Mem0 解析失败时把整个会话当成"没有可记的"；OpenAI 的 JSON 模式不会返回顶层数组，所以适配层补上外层（约 5,400 次抽取里 8 次），受影响的 7 个空间重建。
  - 结果：LoCoMo 200 题 80.5%、LongMemEval 100 题 83.0%；CueMem 的 L1 81.0%、92.0%（LongMemEval 的两个数字是在泄漏条件下得到的；修复后同配置 L1 90.0%、Mem0 79.0%，见 D-067 与[泄漏对照](results/n12-leak/README.md)），名义写入成本是 Mem0 的 34–44%。详见 N11 结果记录。

## D-056 部署：本地向量库被占用时明确报错；服务端建 payload 索引；可选访问令牌

- **状态**：已采纳（N11）
- **背景**：Qdrant 本地模式同一时间只允许一个进程打开同一个目录，录演示时 `cuemem serve` 与命令行撞上，只得到库内部的 `RuntimeError`。HTTP 接口没有鉴权，只适合在本机演示。没有做过压测。
- **决策**：
  1. 本地目录被占用时抛 `StorageLockedError`，说明要停掉哪个进程，或者设置 `CUEMEM_VECTOR_STORE__URL` 改用服务端。
  2. 服务端模式新建集合时按 `kind`（keyword）与 `ts`（float）建 payload 索引：检索时就按这两个字段过滤。
  3. 设置 `CUEMEM_API_TOKEN` 后，`/api` 下除健康检查外都要带 Bearer 令牌（常数时间比较），界面先登录（用户名任意，密码是令牌）。没设置时不鉴权；`cuemem serve` 监听非本机地址又没设令牌时给出警告。
  4. `cuemem migrate-vectors --to URL`：把本地模式的全部集合（向量与 payload 原样）复制到服务端。写入是幂等的，数据库里已有的记忆不会被重新写入向量库，不迁移就切换会得到一个空的向量库。
  5. 离线延迟基准 `scripts/n11_latency.py`：合成的空间从 500 轮到 2 万轮，本地模式与服务端各测一遍，另做单进程并发压测。
- **后果**：
  - 读路径的本机部分：本地模式随规模线性增长（4.6 万个检索单元时约 1.08 s），服务端 91 ms；并发吞吐量 8.7 → 55 次 / 秒。
  - 压测发现同步的 Qdrant 客户端不能被多个线程同时使用（服务端模式下 "Bad file descriptor"），所以两种模式都保留全局锁。
  - 仍然的局限：鉴权只有一个共享令牌，没有按用户隔离记忆空间；多实例部署需要换掉嵌入式的 SQLite。

## D-057 门控在真实流量上的检验：WildChat 里真实用户消息的第一句

- **状态**：已采纳（N11；回应"支撑控制器结论的混合流是构造的"）
- **背景**：控制器"要不要想起"这一半结论（混合流里比总是检索省 41%）依赖构造的无关查询：Dolly 的人工指令与生成的同话题问题。真实用户的消息更口语、更杂，常带第一人称（"帮我改一下我的简历"），门控可能更容易误判。
- **决策**：
  1. 用 WildChat-1M（真实用户与聊天机器人的对话，ODC-BY）第 1 个分片里英文、无毒、没有打码的会话的**第一句**作无关查询：会话的开头不可能指向之前的会话，所以都不需要长期记忆。筛选与 Dolly 相同（10–300 个字符），按文字去重，候选 14,319 条，随机抽 1,750 条（与测试集记忆题同样多）。
  2. 每条配一个测试集的记忆空间跑探针（与 N9 的混合流相同的做法），用冻结的 v1、v2 控制器离线判定：误召回率、门控 AUC、把混合流里的无关查询换成这些消息后的成本。同一批消息再让零样本 LLM 路由（B6z，qwen3.8-flash 只看消息本身）判一遍，与混合方案（B6h）一起作对照。
  3. 仓库只存会话哈希（`evals/mixed/wildchat_test.json`）；`cuemem data download wildchat` 只在点名时下载（数据集登记加了 `optional`），URL 固定到发布时的提交。
- **局限**：第一句之外的消息才更可能需要记忆，而那部分没有标注；WildChat 的用户群（免费的 GPT 网页版用户）不等于任何一个具体产品的用户。这个检验只回答"真实的、不需要长期记忆的消息会不会被误送去检索"。
- **后果**：结果见 N11 结果记录。

## D-058 控制器 v3：有图的空间里，只在问到图时才看图

- **状态**：已采纳（N11 之后；查明并修掉"Agent 把上一题又答一遍"）
- **背景**：Agent 偶尔把上一题又答一遍：N11 的剧本回放（S3·4）和重录 README 动图时各出现过一次，当时记为回答模型的随机失误。在沙盒副本里关掉缓存，把演示第 3 段的前 4 句重跑 6 次，复现了 2 次（1 次整条答成上一题，1 次两题一起答）。看第 4 句的请求：用户问"预算比第一次聊时有什么变化"，控制器却选了 L1 + 看图，把朋友那双鞋的照片附在用户这句话紧前面；上一句恰好是"找长得像的鞋"，模型照着图又调了一次以图搜鞋。根子在控制器 v2：有图的空间直接查有图数据的准确率表，而表来自 MemLens——那里几乎每道题都在问图，看图总是更准。结果 v2 在有图的空间里对 96–98% 的问题都附原图，演示里连"Hi Cue, I'm back!"都附。
- **决策**：
  1. 加一道再感知的门槛：有图的空间里，问题带画面线索（`q_visual`、`q_scene`），或者图片描述的检索相似度 `p_caption_top1` 不低于 τ，才考虑看图；否则只在不看图的动作里选（档位照样按准确率与成本重选）。门控、推理类型模型、准确率表与 λ 都不变。
  2. τ 按 D-052 的协议只在开发集上选：在 MemLens 32K dev100 上，取准确率不低于 v2 的最大 τ，结果是 0.64。测试集只作事后重放。
  3. 冻结的 v2 另存为 `controller_model_v2.json`，复现 N11 时固定用它；默认改成 v3（`scripts/n11_see_gate.py` 评测并导出）。
- **备选**：
  - 只认画面线索、不看图片描述的相似度：MemLens 里只有约四分之一的题带视觉词，开发集上低 3 个点（60.0%）。
  - 改 Agent 提示（"之前的消息都已经回答过"）：只治标。图照样会把无关的问题带偏，还要多付看图的钱。
- **后果**：
  - 开发集：τ 从 0.30 到 0.64，准确率都在 62–63% 之间（相差不到一道题），v2 是 63.0%；看图的比例从 98% 降到 31%。100 道题分不出这么小的差别，结论是"加门槛不伤准确率"，而不是"更准"。
  - 测试集事后重放：MemLens 32K 62.6% → 61.5%（+9 / −11，n.s.），128K 61.0% → 62.1%（+9 / −7，n.s.）；看图的比例 96–97% → 31–33%，每千题成本低 16%。文字数据集逐题不变。
  - 演示：同样的 4 句再跑 8 次，第 4 句都不再附图，也都答对了；整份剧本完整回放 14 / 14。各句的档位跟着变了：问候和问尺码是 L1，找同款鞋是 L2 + 看图，问预算变化是 L1（剧本里写的期望档位只报告，不算失败）。
  - 局限：τ 是相似度的绝对值，换向量模型要重选。如果一句话在问图，却既没有视觉词、和图片描述也不像，就会少看一次图；不过图片描述仍以文字随召回一起给出。

## D-059 遗忘留下的空缺在重新抽取时标出来；挨着空缺的代词不套到别人身上

- **状态**：已采纳（N11 之后；解决 D-051 修订里记下的局限）
- **背景**：遗忘删掉出处那一轮之后，这段会话会重新抽取。剩下的"那副登山杖正合适，我给她买了"就失去了指代对象。抽取提示要求"用名字代替代词"，模型只好从剩下的内容里挑一个人：同一段里助手提过 Lena（"和 Lena 那双很像"），于是抽成了"给 Lena 买登山杖"。把演示第 2 段按遗忘后的样子重建，关掉缓存抽了 12 次，12 次都是 Lena。
- **决策**：
  1. 发言编号本来就不复用（D-021），遗忘留下的空缺就是编号不连续的地方。渲染会话时在空缺处标 `[deleted]`，并加一段说明：
     - 被删的内容不要补回；
     - 挨着空缺的代词多半指被删的内容，不要套到对话里别处出现的人或物上，写成"某人"，或者不记；
     - 这条优先于"用名字代替代词"。
  2. 只有编号有空缺的会话才这样渲染，没删过的会话请求逐字不变。所以不改流水线版本号，已有的抽取缓存全部有效。已核对：评测空间的 42,071 个会话没有一个编号有空缺。超长会话切成多个窗口时按整段会话判断，后面的窗口编号本来就不从 0 开始，不算空缺。
- **备选**：
  - 改抽取的系统提示，所有会话都加"指代不明时不要猜"：评测空间约 4.8k 条抽取缓存会全部失效，重建要花钱，还可能改变评测数字。
  - 把空缺前后的发言一起删掉：删得更多，用户没让删的话也没了。
- **后果**：
  - 同样重建的会话，第一版说明有 7 / 12 次写成"某人"；把"挨着空缺的代词"写明、并声明优先于"用名字"之后，8 / 8 次都写成"某人"。同一段里的升职、预算 $180、换 40 码照常抽出。
  - 在沙盒里按原来"给她买"的剧本建好记忆，再照界面上的流程只遗忘生日这一条：删了 3 条发言，事实 15 → 12，登山杖那条重新抽成"Maya 给别人买了登山杖"。
  - 演示剧本保留"给 Ana 买"，因为 README 动图是按它录的。

## D-060 换模型供应商：配置随包发布、数据目录、预设与 OpenAI 兼容的向量接口

- **状态**：已采纳（N12）
- **背景**：对照 Mem0、Graphiti、Cognee（[对比](landscape.md)），CueMem 拿来就用的门槛很高。
  - 默认配置在仓库的 `configs/` 里，相对路径以仓库根目录为基准：pip 安装后找不到配置，数据也会往 site-packages 旁边写。
  - 模型只有 DeepSeek 与通义；向量只认通义的原生接口。没有 OpenAI，也没有不要 Key 的本地模型。
  - 客户端每次请求都带 `temperature` 与 `max_tokens`，OpenAI 的推理模型（GPT-5 系列）会拒绝。
- **决策**：
  1. 默认配置移到 `src/cuemem/configs/`，随包发布。数据目录：`CUEMEM_HOME` 优先；在源码仓库里运行时仍是仓库根目录（data/、runs/ 与之前一样）；安装后是 `~/.cuemem`。`.env` 也放在数据目录。
  2. 预设（`configs/presets/*.yaml`）与默认配置深度合并：`openai`（gpt-5.4-mini + text-embedding-3-small）、`ollama`（llama3.1:8b + nomic-embed-text，与 Mem0 文档的本地示例相同，不要 Key）。用 `CUEMEM_PRESET`、`cuemem --preset` 或 `Memory(preset=...)` 选。默认的供应商仍在配置里，`configure` 只问用得到的 Key，`doctor` 标出没用到的。
  3. `embedding.backend: openai`：OpenAI 兼容的 `/embeddings`，地址取供应商的 base_url。只有 dense 向量，关键词检索本来就由本地 BM25 承担（D-026）。返回的维度与配置不符时明确报错。
  4. 模型目录可以声明参数差异：`fixed_temperature`（不带 temperature）、`max_tokens_param`（`max_completion_tokens`）。供应商的 `api_key_env` 可以为空（本地服务）；重排与图片向量可以关掉（`rerank.provider: null`、`multimodal_embedding.backend: none`）；回答模型不能看图时只给文字描述、不附原图。
  5. Docker 镜像（数据卷 `/data`，非 root）与 compose（加 Qdrant 服务端）。
- **备选**：
  - 接 LiteLLM，一次支持上百种模型：多一层依赖与一套参数约定；本项目的模型调用已经统一在 OpenAI 兼容接口上，缺的只是向量接口与几处参数差异。
  - 把预设写成 Python 字典：YAML 与默认配置同一种写法，用户可以照着写自己的预设（`--preset path/to/my.yaml`）。
- **后果**：
  - 默认配置下的请求逐字不变（参数顺序也不变），已有的 LLM 与向量缓存照常命中；`tests/test_providers.py` 专门测了这一点。
  - 一处行为变化：显式指定配置文件（`CUEMEM_CONFIG`）时，相对路径过去以配置文件所在目录的上一级为基准，现在统一以数据目录为基准。仓库里的脚本都没有这样用。
  - 用构建出的 wheel 在仓库外验证过：数据目录落在 `~/.cuemem`，预设生效。Docker 镜像在本地构建并运行过：容器里的 SDK、HTTP 导入与召回、compose 下的 Qdrant 服务端都正常。
  - **局限**：OpenAI 与 Ollama 预设只做了离线测试，没有在真实模型上评测；价格按 OpenRouter 转列的标价记（开发环境访问不了 OpenAI 官网）。巩固的相似度阈值按通义向量调过（N3），换向量模型后可能偏松或偏紧；单值事实遇到同谓词总会交给 LLM 判断，影响有限。换了向量模型的数据目录不能混用：数据库记着建库时的向量模型，打开时报 ConfigMismatchError。

## D-061 Python SDK：照 Mem0 的接口形状，保留 CueMem 的语义

- **状态**：已采纳（N12）
- **背景**：Mem0 的 `Memory().add(...)` / `.search(...)` 几乎成了这类库的通用接口；CueMem 只有 `MemorySystem` 这个内部门面，要先构造 `Conversation`、`SessionIn`，再理解空间、巩固与档位。
- **决策**：`from cuemem import Memory`（另有 `AsyncMemory`、`Memory.from_config`）。
  1. 方法名与返回形状照 Mem0：`add / search / get_all / get / history / delete / delete_all`，结果是 `{"results": [...]}`，每条带 `memory` 文本；兼容 Mem0 v3 的 `filters={"user_id": ...}` 与 `top_k=`。
  2. 作用域：`user_id`、`agent_id` 合起来定一个记忆空间（`alice`、`agent/shop`、`shop/alice`），`run_id` 是空间里的一个会话。`add` 接受 OpenAI 格式的消息（内容块里的图片可以是 data URL 或本地路径）。
  3. 语义保持 CueMem 的：
     - `add` 先在线写入（不调用 LLM，立即可检索），抽取在后台完成；`wait=True` 同步抽取，并按 Mem0 的格式返回 ADD / UPDATE 事件，UPDATE 附上被取代的旧版本与原因（现实变了 / 说错了）；`infer=False` 只记日志。
     - 事实不就地改写：`history()` 返回整条版本链；`get_all` 默认只给当前的，`valid_at`、`known_at` 分别按两条时间轴回放。
     - `search` 先过检索控制器，返回档位与英文理由；L0 表示这句话不需要回忆，只给画像。
     - `delete` 是被遗忘权：删事实出自的对话与没有引用的转述，再重建；`delete_all` 删除整个空间。
  4. 遗忘的编排从服务层移到 `MemorySystem.forget_memories`，SDK、HTTP 接口与 MCP 共用。
- **备选**：照搬 Mem0 的 `update(memory_id, text)`：就地改写一条事实会绕过原始日志，派生记忆就不能再从日志重建（D-021）。要改一条事实，应当像用户那样说一句更正，由对账生成新版本。
- **后果**：`tests/test_sdk.py` 覆盖写入事件、版本链、按时间轴回放、作用域隔离、图片消息、只记日志再巩固、删除后旧版本恢复、后台抽取与异步版本。返回值与报错用英文，与 HTTP 接口、MCP、界面一致；命令行仍是中文。

## D-062 OpenAI 兼容的记忆代理：控制器先选，证据放在最后一句用户消息前面

- **状态**：已采纳（N12）
- **背景**：Mem0 的 proxy、Supermemory 的 Memory Router、Memobase 的 OpenAI 补丁都让应用"改个 base_url 就有记忆"，而且每一轮都检索。CueMem 的核心结论正是"不必每轮都检索"：混合流里控制器比总是检索省 41%（真实流量上 46%，D-057）。代理是展示这一点最直接的形态。
- **决策**：`cuemem proxy`（单独运行，默认端口 8787），`cuemem serve` 也挂上同样的 `/v1/chat/completions` 与 `/v1/models`。
  1. **身份**：请求体的 `user` 字段或请求头 `X-CueMem-User`（可加 `X-CueMem-Agent`）；都没有、又没配默认用户时原样转发，不碰记忆。
  2. **想起**：对最后一句用户消息跑控制器。当前会话里已经写进记忆、并且原样还在请求里的轮，检索时排除。
  3. **注入**：与 reader 相同的证据块（画像、带有效期的事实、按时间排列的对话片段），包在 `<memory>` 里放在最后一句用户消息的开头，与 Mem0 的 proxy 相同的位置。系统提示与之前的消息不动，供应商的前缀缓存照常命中。L0 只给画像，什么都没取到时不加任何东西。
  4. **转发**：`model` 是配置里的别名或模型 ID，否则用 agent 角色的模型；按模型目录补上供应商特有的参数（关思考模式等）与推理模型的参数差异；流式与非流式都支持，响应原样返回。控制器的决定写在响应头 `X-CueMem-Level / -Reasons / -Recalled / -Session` 里，响应体不加字段（严格的客户端不受影响）。上游出错时原样返回、不写记忆。
  5. **写回**：用户的话（含 data URL 与本地图片）与回答在线写入。会话进行中不抽取，结束后整段抽取（与 Agent 相同，D-045）。会话的边界：`X-CueMem-Session` 指定；不指定时，请求里没有之前的消息（调用方开始了新的一段对话）或空闲超过 30 分钟就开新会话。
- **备选**：
  - 把记忆放进系统提示（Memobase 的补丁）：每轮系统提示都变，前缀缓存全部失效。
  - 每轮都检索：与 Mem0、Supermemory 相同，但丢掉了控制器的意义。需要时可以 `--mode l1`。
  - 在响应体里加 `cuemem` 字段：有的客户端严格校验响应结构。
- **后果**：
  - `tests/test_proxy.py` 用 TestClient 覆盖跨会话召回与注入、新对话开新会话、流式转发与写回、模型映射、没有用户时原样转发、上游报错、工具调用的后续请求、访问令牌。
  - 另用官方 OpenAI SDK 端到端跑过（本地假的上游）：非流式、流式、原始响应头、`/v1/models` 都正常。
  - 端到端时发现一个问题：起初假定当前会话写进去的轮都还在请求里。调用方在空闲时间内开了新的一段对话时，上一段既不在请求里、也不会被检索到。已经改为按内容比对，并且新对话开新会话（上面第 2、5 条）。
  - **局限**：并行的多段对话不带会话头时会混进同一个会话；网络图片不下载、不写进记忆。

## D-063 导出与导入只搬原始日志；遗忘可以预演

- **状态**：已采纳（N12）
- **背景**：Letta 的 Agent File、Cognee 的 COGX、MemOS 的 dump / load 都把"记忆可以带走"当作基本能力；Supermemory 与 Redis Agent Memory Server 的遗忘可以先 dry run。CueMem 两样都没有，而遗忘又是不可恢复、会级联的操作。
- **决策**：
  1. 导出格式 `cuemem.space`（JSON，version 1）：会话、发言（序号、角色、原文、时间、说话人）与图片原文件（base64）；另附派生记忆的快照（带版本链的事实与画像），只给别的系统读，导入时不用。
  2. 导入 = 写回原始日志，再由巩固重新生成派生记忆：派生记忆是日志的函数（D-021），换了抽取模型、换了机器也一致，不会搬来一份过期的派生结果。遗忘留下的序号空缺照原样保留（按连续的序号分段写入），重新抽取时照样标出来（D-059）。导入是幂等的。
  3. 入口：`cuemem export / import`、SDK 的 `export()` / `load()`、HTTP 的 `GET /api/spaces/{space}/export` 与 `POST /api/spaces/import`。
  4. 遗忘的预演：`cuemem forget --dry-run`（并支持 `--fact`）、SDK 的 `delete(id, dry_run=True)`、HTTP 的 `dry_run`。预演与真正的遗忘共用目标的计算（沿引用扩散、按内容找转述），列出会删的发言与随之消失的事实，什么都不删。
- **备选**：导出派生记忆、导入时直接写入：快，但事实 ID、实体合并、画像都依赖抽取模型与对账的历史，搬过去就和目标机器上的日志对不上了。
- **后果**：
  - 测试覆盖往返（序号空缺、图片哈希与字节、时间、重新抽取、幂等）、格式校验与命令行。
  - **没有导出的**：回复引用了哪些记忆的溯源表（导入后事实 ID 重新生成，对不上）。因此对导入的空间，遗忘不能沿引用扩散，按内容找转述（D-051）照常工作。
  - 预演里没有"重建之后又长出来"的那一步（D-051 的 regrown，要真的重建才知道），输出里写明了。

## D-064 抽取的补充说明（custom instructions）

- **状态**：已采纳（N12）
- **背景**：不同场景要记的东西不同：导购要记尺码、预算与品牌，陪伴类应用要记心情与人际关系。Mem0 有 `custom_instructions`，Graphiti 有 `custom_extraction_instructions` 与自定义实体类型；CueMem 的抽取提示是固定的。
- **决策**：`consolidation.instructions`（SDK 里 `Memory(instructions=...)`）。它以"应用的补充说明，冲突时优先"的形式追加在抽取的系统提示最后。
  - **不填时**：提示词逐字不变，巩固配置的指纹也不变（这个字段不计入），已有的抽取缓存与已巩固的空间都不受影响。
  - **填了以后**：指纹改变，已巩固的空间在下次巩固时重建派生记忆。
- **备选**：自定义实体与事实类型（Graphiti）：要改输出结构、对账规则与谓词登记表，改动面大；先用文字说明覆盖最常见的需求。
- **后果**：测试覆盖提示词的拼接、SDK 参数与指纹的变化。没有评测补充说明对抽取质量的影响。

## D-065 同一协议下对比更多外部基线

- **状态**：已采纳（N12）
- **背景**：
  - N11 只有 Mem0 一个外部系统在同一套评测里跑过（D-055）。其他同类项目只有各家自己报告的分数，回答模型、判分模型、提示词与题目范围都不同，不能与本项目的数字直接比较（[对比](landscape.md) §4）。
  - 要回答的问题：同样的模型、同样的回答与判分，只换"记忆从哪来"，CueMem 的写入与检索比同类项目好还是差，写入要花多少。
  - 新加四个能在本机运行的开源项目：Graphiti（Zep 的开源内核，时序知识图谱）、LangMem（LangChain 的记忆库）、Cognee（知识图谱 + 向量）、A-MEM（Zettelkasten 式笔记，论文附 LoCoMo 评测代码）。Letta 仍不在内：记忆由 Agent 自己管理，与 B3 更像（D-055）。
- **决策**：
  1. **评测网关**（`evals/gateway.py`）：把 CueMem 自己的 LLM 客户端与向量器包成 OpenAI 兼容的聊天与向量接口。外部系统用自己带的客户端，`base_url` 指到网关。
     - 聊天一律交给 extractor 角色的模型，向量交给同一个向量器；同一本账、同一个缓存。
     - 地址里带桶名，每个系统、每份对话历史的写入用量分别累计，记进 build.json。
     - 照外部系统假定的 OpenAI 语义：带工具的请求没写 `parallel_tool_calls` 时发 true（通义不设时一次只回一个工具调用）；检索阶段的桶（`<系统>.search.<空间>`）按查询向量化；上游限流时回 429、带上 Retry-After 并计数；JSON 模式下解析不了的回复，同样的请求再来时不从缓存重放。
  2. **适配层照作者的评测代码**（`evals/baselines/`）：有公开评测代码的照它，没有的照文档推荐的用法。回答与判分不交给它们：各自检索出的证据标上来源会话的时间，交给同一个回答模型、同一套提示。
     - **MG** Graphiti（graphiti-core 0.30.2，嵌入式 Kuzu）：照 Zep 论文的评测代码，每条发言一个 episode，检索 20 条事实、20 个实体。
     - **ML** LangMem 0.0.30：文档里"后台形成记忆"的记忆管理器，每个会话处理一次。没有照搬 Mem0 论文代跑 LangMem 的"热路径"：逐句喂给 Agent，调用量随对话长度平方增长，记忆是 Agent 改写过的散文，带不上日期。
     - **MC** Cognee 1.6.4：照它自己在长对话基准 BEAM 上的做法，一轮一块，HYBRID_COMPLETION 检索；20 个块、20 个实体、5 条事实全部交给回答模型。
     - **MA** A-MEM（agiresearch/A-mem@ceffb86）：照论文在 LoCoMo 上的评测代码，每句话一条笔记，带记忆演化，检索 k = 10。
     - **M0** Mem0 2.2.1 沿用 N11 的适配（D-055）。这个版本是只增不改的 V3 算法。

     与各自默认用法不同的每一处及原因，都写在各模块的说明里。
  3. **两个协议**。同一协议里所有系统（CueMem，以及外部系统内部的调用）用同样的模型：
     - **pds**（只用 DeepSeek，`CUEMEM_PRESET=deepseek`）：所有角色都是 deepseek-flash，判分也是；向量是本机的 BAAI/bge-small-en-v1.5（fastembed，384 维，不加查询指令）；没有重排，没有备用模型。写入在 data/eval-spaces。
     - **pq**（只用通义，`CUEMEM_PRESET=qwen`，N12 新加的预设）：抽取、规划、回答等角色是 qwen3.8-flash，判分 qwen3.8-max；向量 qwen3.7-text-embedding（1024 维，查询与文档分开）；重排 qwen3-rerank；巩固与网关的备用模型 qwen3.7-plus。写入在 data/eval-spaces-qwen（`CUEMEM_PATHS__EVAL_SPACES`）。
     - 为什么有 pq：做到一半 DeepSeek 的余额用完了（2026-10-15 剩 CNY 0.08），于是加了只用通义的协议把对比做完。后来充了值，其余系统在 pds 下也都跑完了。两个协议都报告：同一批系统换一家模型，结果变了多少，本身就是结论的一部分。
     - 两个协议的判分都不符合 D-008：pds 是回答模型给自己判分，pq 的判分与回答模型同一家族。N11 的第二判分实验里，deepseek-flash 与 qwen3.8-max 判分的一致率是 94.7–97.9%。
  4. **规则**：
     - 同一协议下，抽取模型与向量（经网关）、回答模型与回答提示、判分都相同；
     - 每个系统用自己的写入与检索流程，不替它们改算法（只为跑得起来的改动见第 7 条）；
     - 每个配置跑一次，同一批题上做配对的精确符号检验；
     - 外部系统（MG、ML、MC、MA）的写入用量从网关的桶里读，M0 与 CueMem 的从写入时的 trace 里读；都与回答的用量分开记，比较用名义成本（D-010）。
  5. **新加的四个外部系统只跑 LoCoMo test200r**（Mem0 在 N11 跑过 LongMemEval test100r，N12 的泄漏消融里又跑了，见 D-067）：后 7 段对话（conv-42、43、44、47、48、49、50，共 4,431 轮、202 个会话）上分层抽的 200 道非对抗题。7 段对话只要写 7 份；LongMemEval 每道题有自己的一份历史，test100r 要写 100 份：
     - N11 的 Mem0 在 LongMemEval test100r 上写入的名义成本是 $9.76，在 LoCoMo 上是 $0.70；
     - Graphiti 每条发言一个 episode，模块说明估算 test100r 约 4.9 万条发言，写入要几百美元、一天以上；
     - A-MEM 每句话两次 LLM 调用、只能逐条串行，通义下约 15 秒一句。

     LangMem 与 Cognee 的 LongMemEval 写入没有单独估算，也只跑 LoCoMo，四个新系统在同一批题上比较。CueMem 自己的方法照旧在 LongMemEval 上评测，修复会话 ID 泄漏之后在 test100r 上重跑的数字见 D-067（test400 没有重跑）。
  6. **为了在这两家模型上跑得通，适配层加的处理**（发生几次都计数，记进 build.json）：
     - 回复是 JSON 却不合 schema 时重新采样（MG、MA）。OpenAI 的 strict 结构化输出保证 schema，DeepSeek 与通义的 JSON 模式不保证。重采样时把回复上限减一点，落到新的缓存键上，否则缓存只会还回同一个坏回复。
     - 内容审核的误拒（被拒的发言都很平常），各系统的处理不同：
       - MG 跳过被拒的发言并计数，超过 max(2, 5%) 条才整份作废；
       - ML 跳过被拒的会话并计数，与丢了写入的会话合起来算上限（见下一条）；
       - MA 照 A-MEM 自己的做法跳过被拒的调用（笔记留下，缺分析或演化）并计数，超过一半才作废；
       - M0（N11 的适配）换了备用模型仍失败的会话一律跳过并计数，不设上限。
     - LangMem 丢了写入的会话照实计数（读不出的 PatchDoc 补丁也算丢失）。原来的检查是被拒与丢失合计超过 max(2, 10%) 的会话就否掉整份写入，pq 下 7 份里否掉 4 份；两个协议的完整运行都放宽到 25%（`CUEMEM_LANGMEM_MAX_LOST_SHARE=0.25`，默认仍是 10%），丢失照样记下。
     - Cognee 失败的会话删掉重写一次，仍失败的跳过并计数，超过一半才作废。
  7. **与默认用法不同、只为跑得起来的改动**（这两处改了 Graphiti 的检索）：
     - Graphiti 的 BFS 深度取 1（默认 3：Kuzu 的可变长路径查询在深度 3 时用了超过 12 GB 内存）；
     - Graphiti 自带的重排用不了：pq 下把 qwen3-rerank 包成它的 cross-encoder；pds 没有重排模型，事实检索退回 Graphiti 基础检索的默认做法，BM25 + 向量的 RRF。
  8. **刻意没有调的**：
     - Graphiti 的向量相似度阈值 0.6：pq 下向量路并没有落空，每题事实候选的中位数是 8 条；
     - LangMem 的提示与默认参数；
     - A-MEM 的 k：主结果用论文的主要设置 10。作者给 GPT-4o 级模型（与这里的模型同档）调到 40，README 也说要调 k 才能复现论文的数字。取 10 是为了证据量与其他方法可比（deepseek 预设试跑的 conv-42 上 k = 10 平均约 9k tokens、k = 40 约 27k，CueMem L1 约 4k），这可能对 A-MEM 不利；k = 40 的敏感性运行（`CUEMEM_AMEM_K=40`）见后果；
     - Cognee 交给回答模型的证据不截断，与它的 BEAM 报告相同；
     - 各系统的抽取提示，包括 CueMem 自己的。
- **备选**：
  - 引用各家自己报告的分数：回答模型、判分与提示都不同，一两个点的差距没有意义（landscape §4）。
  - 给每个系统调参（阈值、提示、k）：只能在这批测试题上调，等于拿测试集做选择（D-048）；每个系统都调到最好，工作量与花费成倍增加。不调的代价是 CueMem 有主场优势，写在后果里。
  - 外部系统也跑 LongMemEval：写入的花费与时间见决策第 5 条。

## D-066 框架集成：OpenAI Agents SDK、LangGraph / LangChain、Claude 的 memory tool；召回证据收拢成一份

- **状态**：已采纳（N12）
- **背景**：Mem0、Graphiti、Supermemory 等都有十几个框架的集成，用户最先碰到的问题是"怎么接进我已经在用的 Agent 框架"。CueMem 之前只有 SDK、HTTP、MCP 与记忆代理。框架集成要回答两件事：谁决定要不要想起，对话什么时候算结束、交给抽取。
- **决策**：`cuemem.integrations` 下三个模块，依赖都是可选的（`--extra openai-agents / langgraph / anthropic`，合称 `integrations`），用法见 [框架集成](integrations.md)。
  1. **控制器先选**：三个集成都在每次调用模型之前过一遍控制器（L0 只给画像），证据块与记忆代理、回答模型相同，放在最新一句用户消息的开头，系统提示与之前的消息不动。模型另外可以用 recall / remember / forget 工具补查，工具与 MCP 同名同义。
  2. **OpenAI Agents SDK**：`memory_input_filter` 接在 `call_model_input_filter` 上；`CueMemSession` 实现 Session 协议，内层会话原样保存短期历史，一问一答写成 CueMem 的一轮；服务端保存对话状态时用 `placement="instructions"`，证据不随用户消息存到服务端。
  3. **LangGraph / LangChain**：LangChain 1.x 的中间件 `CueMemMiddleware`（召回在 wrap_model_call 里、只改这次发给模型的请求，写回在 after_agent，回合怎么结束都写回）；旧的 `create_react_agent` 用 `recall_hook` / `save_hook`。一个线程是一个会话；LangGraph Server 上用登录用户的身份，不信任客户端传的 ID。
  4. **Claude 的 memory tool**（`memory_20250818`）：`/memories` 目录接到 CueMem 上。`profile.md`、`facts.md` 是只读的生成文件；Claude 自己建的文件存在旁边的小库里，每次改动同时作为笔记写进原始日志，由巩固抽成事实；删文件就遗忘它写进去的内容。
  5. **会话的结束**：`end()` / `end_thread()`、上下文管理器退出、空闲 30 分钟、`close_sessions()` / `close()` 时交给后台抽取；进程没来得及交出的会话由下一个进程交出。
  6. **一份召回证据**：评审查出"想起 → 排成证据 → 注入"在代理与三个集成里各写了一份，集成还导入了私有函数。收拢到 `cuemem/evidence.py`：`recall_evidence` / `inject_evidence`（自动想起）、`recall_listing` / `format_listing` / `resolve_ids`（给另一个 Agent 的清单与按 ID 遗忘）。代理、服务层、MCP 与三个集成都用它，行为不变。
- **备选**：
  - LangGraph 的 `BaseStore` 后端：Store 是通用键值存储，读写时机由应用决定，放不进控制器；以后可以补上，作为只读的事实视图。
  - 把记忆写进系统提示：每轮都变，前缀缓存不命中（与 D-062 同）。
  - 只给工具、让模型自己决定：这是 Letta 的做法，与 CueMem"调用 LLM 之前由控制器决定"的主张相反；工具保留作补查。
- **后果**：
  - 每个集成先实现，再由两个视角（对框架的忠实度、正确性）评审，按评审修订后才合并。评审查出的真问题包括：CI 没装可选依赖、集成测试一直跳过；一问一答被拆成两轮；证据缓存跨轮沿用；LangChain 的对话总结被当成用户的话写回；身份取自客户端可控的 configurable；代理与集成会读 `file://` 与本地路径的图片。这些都已修正并加了回归测试。
  - 2,592 行测试（离线）；三个集成都在 deepseek 预设上做过联网冒烟。Claude 的 memory tool 没有在真实的 Claude 上跑过：没有 Anthropic 的 Key，DeepSeek 的 Anthropic 兼容接口不认 `memory_20250818`，冒烟时把同一个后端声明成普通工具。
  - **局限**：进行中的会话按进程记在内存里；只注入文字证据，控制器想看原图时原图不附进模型调用；还没有 TypeScript 与 Vercel AI SDK。

## D-067 LongMemEval 的会话 ID 泄漏：修复、量影响、照实披露

- **状态**：已采纳（N12）
- **背景**：
  - LongMemEval_S（`longmemeval_s_cleaned.json`）里 948 个证据会话的 ID 全都以 `answer_` 开头（30 道拒答题的证据会话 ID 还带 `_abs`），其他会话是 `sharegpt_`、`ultrachat_` 或一串十六进制。
  - `read/reader.py` 的 `format_memories` 在每条检索证据的抬头写 `· session <ID>`，回答模型因此看得出哪些片段来自证据会话。
  - **受影响**：所有检索方法，即 B2、B3 / B6a 的工具输出、CueMem L1 / L2 / 控制器、M0，以及 MG / ML / MC / MA（它们的代码路径同样会显示抬头，但没有在 LongMemEval 上跑过，见 D-065）。
  - **不受影响**：B0、L0、B1（全上下文按 1..n 给会话编号）、ORACLE。LoCoMo 不受影响（`session_1..N` 是按时间的序号）；MemLens 的原始 ID 是 `sess_<哈希>`，不透露哪些是证据。
  - N2–N11 发表的 LongMemEval 数字里，检索类方法的都是在这个泄漏下得到的。
  - 审查时还找到第二处：Cognee 的会话蒸馏用的会话 ID 里带着 LongMemEval 的题号（拒答题带 `_abs`），会进到它提炼出的经验文档里。已一并修复；LoCoMo 不受影响，发表的数字都没有用到它。
- **决策**：
  1. **加载时改写**：LongMemEval 与 MemLens 的会话按在这份历史里的时间顺序改写成 `session_<i>`（与 LoCoMo 自带的写法相同），证据会话与证据发言随之改写，检索指标不变。原始 ID 留在 `EvalSession.source_id`，只用于追溯，不进任何模型的提示。
  2. **开关** `CUEMEM_EVAL_RAW_SESSION_IDS`（只影响 LongMemEval / MemLens）：
     - `=1`：恢复原始 ID，与修复之前逐字节相同（旧的空间、写入与缓存照常命中）；
     - `=label`：空间照常用改写后的 ID，只在回答模型看到的证据抬头里换回原始 ID。与默认之间只差抬头里的会话名，用来量泄漏本身。
  3. **两种写法不混用**：改写过的写入放在 `<数据集>-anon` 目录下；写法记在空间数据库、build.json 与 run.json 里，写法对不上的写入不复用，对比脚本遇到写法不同的运行直接报错。LoCoMo 的请求逐字节不变，有测试。
  4. **复现**：`scripts/reproduce.py` 的历史步骤沿用原始 ID，提示与当时逐字相同：有当时的响应缓存时照样复现发表的数字；没有缓存时重跑有抽样波动（N12 的 raw 一臂就是一例，见后果）。
  5. **量影响**：LongMemEval test100r 上跑三臂，回答与判分相同（`scripts/n12_leak.py`）。原协议（orig：抽取 qwen3.8-flash、向量 qwen3.7-text-embedding、回答 deepseek-flash、判分 qwen3.8-max）与 pq 各跑一遍；orig 的写入放在 data/eval-spaces-default（巩固配置的指纹包含备用模型，不能与 pq 共用）。
     - **label 对 anon**：只差证据抬头，是泄漏本身的效应；
     - **raw 对 label**：抬头相同，只差空间里的 ID。同一会话里各轮按含会话 ID 的哈希定先后，换了 ID 顺序就变：这是改名带来的噪声，修复之前就有，LoCoMo 上也一样；
     - **raw 对 anon**：两者都有，即修复前后的差。
  6. **照实披露**：发表过的数字保持原样；本条与 N12 的泄漏对照写明泄漏的范围、修复与量出的影响。
- **备选**：
  - 只在 reader 里去掉抬头的会话 ID：抬头里的会话名有用，回答模型靠它分辨哪些片段来自同一个会话（LoCoMo 也这样显示）。而且 ID 还会从别的路进到提示里，Cognee 的经验文档就是一例，只改 reader 堵不全。
  - 在 reader 里显示时重新编号：同样只管 reader 这一处。在加载时改写一次，下游（CueMem 的写入、外部系统、检索指标）都看不到原始 ID。
  - 不披露、悄悄修掉：修复后的数字与发表的对不上，读者不知道为什么；泄漏可能让某个方法占了便宜，不量就不知道是哪个、占了多少。
- **后果**：
  - 消融（LongMemEval test100r，100 题，准确率 %）：

  | 方法 | orig raw | orig anon | orig label | pq raw | pq anon | pq label |
  |---|---|---|---|---|---|---|
  | B1 全上下文 | 81.0 | 81.0 | — | 77.0 | 77.0 | — |
  | B2 朴素检索 | 82.0 | 86.0 | 87.0 | 82.0 | 83.0 | 84.0 |
  | CueMem L1 | 92.0 | 90.0 | 92.0 | 90.0 | 91.0 | 89.0 |
  | CueMem L2 | 93.0 | 96.0 | 95.0 | 94.0 | 93.0 | 93.0 |

  B1 不受泄漏影响，没有 label 一臂。Mem0 在 orig 下没有重跑 raw 一臂（N11 发表的 83.0% 就是这个条件），在 pq 下只跑了 raw 一臂，anon 与 label 两臂没有跑；`scripts/n12_leak.py` 的 `ARMS` 里列着这三个运行名，没有跑的自动跳过。
  - 汇总 label 对 anon（各检索方法加在一起；同一批题，不独立）：orig +21 / −12（平均每个方法 +1.8 个点，p = 0.16，含 Mem0）；pq +10 / −14（不含 Mem0：它的 anon 与 label 两臂没有跑；−1.0 个点，p = 0.54）。单个方法都不显著，最大的是 orig 的 Mem0：+9 / −3（p = 0.15）。
  - N11 发表的 test100r 数字（orig，原始 ID；CueMem 各方法取自 N9 的测试运行，D-055）：B1 80.0%、B2 86.0%、L1 92.0%、L2 96.0%、控制器 92.0%、Mem0 83.0%。修复后（orig，anon）：L1 90.0%，Mem0 79.0%。raw 一臂是 N12 重新跑的，B1、B2、L1、L2 的回答调用一次也没有命中响应缓存，是重新采样；与发表的数字相比 B1 81.0 对 80.0、B2 82.0 对 86.0、L2 93.0 对 96.0、控制器 88.0 对 92.0，只有 L1 相同。所以臂与臂之间只用 N12 这一批运行比较。
  - **分辨率**：每臂 100 题、只跑一次。只换空间里 ID 的噪声（orig 的 raw 对 label，汇总 +5 / −14，−2.25 个点，p = 0.064）比量出的泄漏效应（+1.8 个点）还大；N12 重跑的 raw 一臂与 N11 发表的数字最多差 4 个点，B1 不受 ID 影响，也差了 1 个点。几个点以内的影响这里分辨不出来。
  - **结论**：test100r 上没有量出 L1、L2 与控制器被泄漏抬高；Mem0 的 label 对 anon 是 +9 / −3（p = 0.15，不显著），发表的 83.0% 可能高了几个点；检索方法与全上下文之间的差距不变。
  - **局限**：
    - 只重测了 test100r 上的 B2、L1、L2、控制器与 Mem0。B3、B6a（模型从工具输出里看到同样的抬头）、B2F 与"L1 + 先记笔记"等消融，以及 N9 的 test400 全集都没有重跑；它们发表的数字受多大影响不知道，D-041（H3）的 LongMemEval 部分也一样；
    - 学到的控制器的准确率表与 λ 是在泄漏下的结果上拟合的，没有重新拟合；
    - 同一会话里各轮的先后仍取决于 ID；
    - 每臂只跑一次。
  - 以后的 LongMemEval 与 MemLens 评测默认用改写后的 ID。
