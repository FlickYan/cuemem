## D-001 检索时机与深度由解耦的控制器决定，而不是由 LLM 自主决定

- **状态**：已采纳（N0）
- **背景**：让 LLM 通过工具调用自主决定检索，效果取决于模型能力，小模型尤其不可靠；行为难预测、难评测；项目价值会被模型能力掩盖。
- **决策**：每轮先运行不调用 LLM 的记忆探针，再由轻量、可训练的控制器在 L0 / L1 / L2（以及是否再感知原图）之间做成本感知的决策；证据不足时级联升级。LLM 自主检索保留为对照基线（B3）和逃生通道。
- **备选**：总是检索（浪费 token、引入干扰）；纯规则触发（脆弱）；基于模型不确定度触发（FLARE / DRAGIN 式，对私人记忆不可靠，而且 API 模型拿不到内部信号）。
- **后果**：可度量、可训练、与底座无关、成本可调；代价是需要构造训练标签，控制器本身也可能过拟合。
- **验证**：N7 的帕累托曲线、与 B3 的对比、跨数据集与跨底座实验（H1–H3）。

## D-002 原始日志不可变、派生记忆可重建；事实采用双时间轴有效期

- **状态**：已采纳（N0）
- **背景**：用户信息会变化。直接覆盖或删除旧事实会丢失历史，无法回答"我以前……"；派生数据（摘要、事实）可能抽错，需要能修复。
- **决策**：原始轮次是唯一事实来源；事实、摘要、画像、图片描述都是带溯源、可全量重建的派生数据；冲突时让旧事实失效（设置 `valid_to`、`superseded_by`），而不是删除。
- **备选**：Mem0 式 UPDATE / DELETE 覆盖（简单，但丢失历史）；不做抽取、只存原文（无法显式处理冲突）。
- **后果**：能回答历史状态问题、可审计、抽取逻辑升级后可以重跑；代价是存储与实现更复杂。
- **验证**：N3 的场景单测；开发集"知识更新"类别（H4）。

## D-003 多模态采用"索引时压缩 + 回答时再感知"

- **状态**：已采纳（N0）
- **背景**：MemLens 发现长上下文 LVLM 随长度退化，而记忆智能体因存储时压缩丢失视觉细节。
- **决策**：图片以三种表示入库（视觉向量、上下文感知描述 + OCR、实体绑定）；回答时由控制器决定是否取回原图交给 VLM。
- **备选**：只存描述（便宜但丢细节）；所有图片常驻上下文（昂贵，且随长度退化）。
- **后果**：兼顾长度稳定性与视觉保真度；代价是回答时多出图片 token，需要控制器管理。
- **验证**：N6 在 MemLens 上的对比（H5、H6）。

## D-004 模型全部走 API：DeepSeek + 通义千问，按角色分工

- **状态**：已采纳（N0 提出，N1 修订）
- **背景**：开发机为 Apple M2、8GB 内存、可用磁盘约 29GB。可用的 API 是 DeepSeek 与通义千问（2026-10-12 确认）。DeepSeek 只提供对话模型（其中 deepseek-flash 支持图片输入）；通义提供对话、视觉、文本向量、多模态向量与重排。
- **决策**：
  - LLM / VLM 通过 OpenAI 兼容接口按角色接入，分工见设计文档 §9.3；
  - 向量也走通义 API（qwen3.7-text-embedding，原生接口一次返回 dense + sparse），外面套一层内容哈希缓存；本地向量模型作为可选后端，接口已预留，暂不实现。
- **修订原因**：N0 原计划在本地运行 BGE-M3。改走 API 是因为：
  1. 8GB 内存跑本地模型，会和浏览器、IDE 抢内存；
  2. 通义向量每百万 tokens 只要 $0.07（QwenCloud），加上缓存后评测的向量化成本可以忽略；
  3. 原生接口同样给出 sparse 向量，混合检索不受影响；
  4. 不必下载约 1GB 的 torch 与 2GB 的模型权重，环境一条命令就能装好。
- **代价**：查询向量化多一次网络往返，探针的"几十毫秒"目标要放宽（待实测）；依赖网络。
- **验证**：`scripts/spike_embeddings.py` 实测延迟；N4 比较召回质量。

## D-005 存储全部嵌入式：SQLite + Qdrant 本地模式（可切服务端）+ 进程内图计算

- **状态**：已采纳（N1 技术验证后确认）
- **背景**：希望在笔记本上一条命令跑起来，不依赖 Docker 或外部服务；内存有限。
- **决策**：结构化数据和事实用 SQLite；向量用 Qdrant 本地模式（命名向量支持 dense / sparse / image，payload 支持时间与有效性过滤）；PPR 用 scipy.sparse 计算。所有存储都在接口之后；配置 `vector_store.url` 即可改用 Qdrant 服务端，代码不变。
- **备选**：Neo4j（图能力强但重）；Postgres + pgvector（需要起服务）；LanceDB（嵌入式、磁盘友好）。
- **验证数据**：N1，M2 / 8GB，1024 维 dense + 每条约 60 个非零项的 sparse，`scripts/spike_storage.py`。

  | 点数 | 写入耗时 | dense p50 / p95 | sparse p50 / p95 | 带过滤的 dense p50 | 重新打开 | 进程峰值内存 |
  |---|---|---|---|---|---|---|
  | 1,000 | 0.8 s | 1.2 / 1.4 ms | 12.2 / 12.4 ms | 5.3 ms | 0.1 s | 223 MB |
  | 5,000 | 4.0 s | 4.7 / 4.9 ms | 61.0 / 61.8 ms | 25.4 ms | 0.4 s | 661 MB |
  | 20,000 | 16.2 s | 16.9 / 17.5 ms | 244.5 / 248.0 ms | 100.6 ms | 1.9 s | 1,676 MB |

- **结论**：评测时每个样本是一个独立的记忆空间，规模在几千条以内，本地模式完全够用。本地模式的检索是暴力计算，sparse 与带过滤的检索在 Python 里逐点计算，2 万条时分别到约 245 ms 和 100 ms，内存也接近 1.7 GB。规模更大时切到 Qdrant 服务端（有 HNSW 与倒排索引），或在 N4 用 BM25 倒排索引替代 sparse 路。
- **后果**：零运维、易复现；分布式能力不在本地体现，扩展方案见设计文档 §12。

## D-006 自研 Agent Runtime，不用 LangChain / LlamaIndex 作为核心

- **状态**：已采纳（N0）
- **背景**：本项目最想展示的正是 agent loop / harness、上下文组装与记忆读写这些机制。自己构建 runtime，它们才讲得清楚、能单独测试；框架的抽象会把它们遮住。
- **决策**：核心循环、上下文组装、工具调用、记忆读写全部自研；只使用基础库（LLM SDK、存储客户端）。
- **后果**：每个机制都讲得清楚、可控、可测；代价是要自己处理重试、并发、结构化输出等细节（见 D-009、D-011）。

## D-007 评测先行

- **状态**：已采纳（N0）
- **背景**：文本记忆基准的报告值已经接近饱和，而且不同论文的 reader、judge、prompt 各不相同，数字不能直接比较。
- **决策**：在实现任何高级方法之前，先搭好统一的评测框架与基线；所有方法在同一框架、同一 reader 与 judge 下比较；主结果是准确率–成本帕累托曲线。
- **后果**：每个改动都有证据，结论可信；代价是前期看起来进展慢。

## D-008 judge 与主 reader 来自不同模型家族

- **状态**：已采纳（N1）
- **背景**：用 LLM 判分时存在自我偏好，倾向于给同家族模型的回答打高分。LongMemEval 的官方 judge 是 GPT-4o，但我们没有 OpenAI 的 API。
- **决策**：主 reader 用 DeepSeek（deepseek-flash），judge 用通义（qwen3.8-max），所有实验固定同一个 judge。跨底座实验中 reader 换成通义模型时，额外人工抽检，看 judge 是否偏向同家族。
- **备选**：reader 自己判分（偏差大）；多个 judge 投票（成本翻倍，留作 N9 的鲁棒性检查）。
- **验证**：N2 人工抽检 50 条看一致性；N9 做跨家族交叉检查。

## D-009 同步核心 + 线程池并发，而不是全面 asyncio

- **状态**：已采纳（N1）
- **背景**：评测要并发调用大量 API；很多 Agent 框架基于 asyncio。
- **决策**：核心代码全部同步。需要并发的地方（评测 runner、L2 的多路检索）用线程池；每个供应商一个信号量限流；SQLite 与 Qdrant 本地模式的访问加锁。
- **理由**：瓶颈是网络 I/O，线程足够；同步代码更容易读、调试和讲解；避免 async 的"传染性"（整条调用链都得改成 async，而 SQLite、Qdrant 本地模式都是同步库）；FastAPI 也能在线程池里运行同步接口。
- **代价**：极高并发的在线服务场景下不如 asyncio；届时可把 LLM 客户端换成 openai SDK 的异步版本。

## D-010 成本口径：名义成本用于比较，实际花费单独统计

- **状态**：已采纳（N1）
- **背景**：DeepSeek 有错峰半价，两家都有缓存命中折扣，通义还有新用户免费额度；命中本地响应缓存时更是一分钱不花。如果直接用"实际花费"比较方法，同一个实验在不同时间运行，成本会不一样。
- **决策**：账本给每次调用记两种成本。
  - **名义成本**：全部按高峰、未命中缓存的标价计算，用于实验比较与帕累托分析；
  - **估算花费**：扣除本地缓存命中和供应商缓存折扣，用于管理预算。
  - token 数与调用次数作为与价格无关的补充指标。
- **后果**：实验结论不受运行时间影响；价格变动时只需改 `configs/default.yaml`。
- **更新（D-024）**：估算花费现在也计入 DeepSeek 的错峰价（非高峰 = 标价 × 0.5），名义成本不变。

## D-011 结构化输出：JSON 模式 + Schema 提示 + 校验重试

- **状态**：已采纳（N1）
- **背景**：抽取、规划、判分都需要可靠的结构化输出。两家都支持 JSON 模式，但对严格 json_schema 模式的支持不一致（DeepSeek 文档未提及）；DeepSeek 的 JSON 模式偶尔会返回空内容。
- **决策**：统一使用 `response_format={"type": "json_object"}`，把 pydantic 生成的 JSON Schema 写进系统提示，再用 pydantic 校验。校验失败时把具体错误反馈给模型重试，默认最多 3 次；空回复不写入缓存。
- **后果**：与供应商无关；失败可观测（重试次数记录在结果里）；代价是偶尔多一次调用。

## D-012 两个存储之间不用事务：确定性 ID + 写入顺序保证一致

- **状态**：已采纳（N1）
- **背景**：一条记忆要同时写 SQLite（内容）和 Qdrant（向量），两者无法放在同一个事务里。
- **决策**：
  - 所有 ID 都由内容确定性地派生，重复写入是覆盖而不是新增；
  - 先写向量、后写数据库，所以数据库里有的记录一定有向量；中途失败时重跑即可补齐，向量化命中缓存，不会重复计费；
  - 建库时把向量模型指纹写进数据库，换模型时直接报错，避免新旧向量混用。
- **后果**：写入幂等、可恢复，不需要事务协调器。

## D-013 通义经 QwenCloud 接入；Key 只进 .env；成本统一按美元计

- **状态**：已采纳（N1）
- **背景**：阿里把 DashScope、百炼、Model Studio 统一成了两个品牌：中国大陆以外叫 QwenCloud，中国大陆叫千问 AI 平台。不同平台的接口域名、API Key、可用模型都不一样，例如 QwenCloud 目前没有 qwen3-vl-embedding，多模态向量用的是 tongyi-embedding-vision 系列。本项目的账号在 QwenCloud。
- **决策**：
  - 默认配置直接指向 QwenCloud：对话走 `https://maas.qwencloudapi.com/compatible-mode/v1`，向量走同一域名下的原生接口（只有原生接口能返回 sparse 向量）。换平台只需覆盖这两个地址；
  - API Key 只写入 `.env`（不进仓库），用 `cuemem configure` 交互式填写：输入不回显，只显示首尾几位，文件权限 600。缺 Key 时在调用前就提示运行 `cuemem configure`；
  - 名义成本统一用美元标价：DeepSeek 与 QwenCloud 都公布美元价格，评测比较只需要一种币种。
- **后果**：仓库里没有任何账号信息；成本可以直接相加比较。代价：换用其他平台时，名义成本仍按 QwenCloud 标价计算，与实际账单不完全一致，但不影响方法之间的比较。

## D-014 文本向量默认用 text-embedding-v4

- **状态**：已采纳（N1 联网验证后），检索质量的正式对比在 N4 完成
- **背景**：N1 原定用 qwen3.7-text-embedding。拿到 Key 后实测（`scripts/spike_embeddings.py`，QwenCloud）：

  | 模型 | 单条查询 p50 / p95 | 10 条文档一批 | 稀疏向量非零项（平均） | 稀疏向量的性质 |
  |---|---|---|---|---|
  | qwen3.7-text-embedding | 164 / 247 ms | 1,481 ms | 约 523 | 带语义扩展："Max 是一只金毛"扩展出"狗狗、汪汪、狗粮"，甚至德语"Hunde" |
  | text-embedding-v4 | 52 / 69 ms | 113 ms | 约 20 | 原文词项权重："Max 是一只金毛"只有"毛、是、金、Max、一只" |
  | qwen3.7-text-embedding-flash | — | — | — | QwenCloud 上不存在该模型 |

  在一个小样例上，两者的语义区分度接近：问题与相关 / 无关文档的余弦相似度，v4 为 0.646 vs 0.225，qwen3.7 为 0.601 vs 0.166。
- **决策**：默认改用 text-embedding-v4。
  1. 写入快 13 倍：写入 LongMemEval 这种规模的数据，从约 10 小时降到 1 小时以内，评测迭代快得多；
  2. 查询约 50 ms，与探针"几十毫秒"的目标一致；
  3. 稀疏向量是真正的词项权重，正好承担混合检索中"精确匹配"的角色；带语义扩展的稀疏向量与 dense 路重叠，而且每条 500 多项，会让 Qdrant 本地模式的稀疏检索慢一个数量级（参见 D-005 的测试条件：每条约 60 项）。
- **代价与验证**：qwen3.7-text-embedding 是更新的模型，检索质量可能更好。N4 在开发集上用 Recall@k 正式对比，模型只是一个配置项，可以随时切回。
- **N4 修订：默认改为 qwen3.7-text-embedding（只取 dense）**。N1 选 v4 的两个理由在 N4 之后都不成立了：稀疏路改由本地 BM25 承担（D-026），不再需要 qwen3.7 那种带语义扩展、又慢的稀疏向量；只取 dense 时速度慢约 6 倍，但写入是一次性的。而语义召回差距很大（`scripts/compare_embeddings.py`，dev100 分层抽 30 题，只比较"轮"上的 dense 检索，k = 10）：

  | 向量模型 | 发言召回（任一） | 发言召回（全部） | 会话召回（全部） | 发言 NDCG | 30 份历史的向量化耗时 |
  |---|---|---|---|---|---|
  | text-embedding-v4 | 83.3% | 74.1% | 84.4% | 54.3% | （缓存） |
  | qwen3.7-text-embedding | 93.3% | 89.3% | 89.2% | 72.7% | 354 秒 / 328 万 tokens |

  两者单价相同（QwenCloud 标价 $0.07 / 百万 tokens）。端到端（同一份代码、同一批题，只换向量模型）：B2 在 dev100 上 65% → 76%，在 LoCoMo 385 题上 71.2% → 75.6%；B2F 只从 80% → 80%、77.7% → 78.7%，说明事实增强键已经补上了弱向量模型的大部分召回损失（`docs/results/n4-dev100-l1/README.md`）。教训：**N1 时只看了速度与稀疏向量的性质，没有量化语义召回**——选型要用目标指标说话，前提条件变了要重新评估。

## D-016 评测运行器的设计

- **状态**：已采纳（N2）
- **决策与理由**：
  - **每题独立的内存存储，共享缓存**：LongMemEval 每道题有自己的对话历史，评测时为每组题新建内存中的数据库与向量库，用完即弃；向量缓存与 LLM 缓存则持久共享，重跑时不重复计费。这样内存占用稳定，8GB 机器上也能并发。
  - **用 trace 计量**：每个（题目，方法）在独立的 trace 中执行，从事件里汇总 token、调用次数和名义成本；判分在另一个 trace 中，不计入方法成本。trace 允许嵌套，内层调用（如 `MemorySystem.ask`）的事件会记到外层。
  - **断点续跑**：结果逐行追加到 `results.jsonl`，已完成的组合自动跳过；出错的组合记入 `errors.jsonl`，不算完成，下次运行会重试。
  - **预算保护**：按实际花费（不含本地缓存命中）累计，超过 `--max-cost` 就不再开始新的组合。
  - **可追溯**：`run.json` 记录配置、各角色的模型 ID 与标价、向量模型、代码版本（git 提交号，有未提交改动时带 `-dirty`）。
  - **先试跑再全量**：从开发集分层抽 10 题试跑，确认流程、成本与判分质量后再跑全量。
- **后果**：一条命令即可复现结果表；一次 100 题开发集评测的成本与耗时可以准确预估。

## D-017 试跑后修订 Reader 提示词（v2），只在开发集上调整

- **状态**：已采纳（N2）
- **背景**：pilot10 试跑后逐条检查了答错的题，判分都正确，但发现两个与方法无关的 Reader 问题：
  1. **过度拒答**：偏好类问题（"在东京出行有什么建议"）应结合记忆给出个性化建议，模型却回答"没有相关记忆"；还有一题模型找到了答案，却先说"没有这段记录"，被判错。原因是"答不出就说不知道"这条规则过强，而且只考虑了事实题。

## D-018 抽取模型用 qwen3.8-flash（与 deepseek-flash 抽样比对后确认）

## D-019 事实对账：规则只管合并、否定与多值累积，取代一律由 LLM 确认；取代分"现实变了"与"认知变了"

- **状态**：已采纳（N3；dev100 实测后修订）
- **背景**：新事实要和已有记忆比较，决定新增、取代、合并还是忽略。Mem0 对每条新事实都调用一次 LLM 在 ADD / UPDATE / DELETE / NONE 之间选择，简单但贵（LongMemEval 一题约 50 个会话、几百条事实），而且行为难以审计。
- **最初的设计**：规则优先——登记过的单值谓词（住址、工作、职位……）换了新值就直接取代，只有未登记的谓词才交给 LLM。
- **实测推翻了它**：dev100 首轮运行后，从回放里抽样人工核对：
  - 规则取代 31 次，正确的只有 3 次（**约 10%**）。原因有二：抽取模型给谓词贴标签不稳定（"有个小衣柜""家里墙多影响 Wi-Fi"都被标成 `lives_in`，"在做某个项目"被标成 `works_at`）；LongMemEval 的干扰会话来自不同的人，"用户 32 岁"与"用户 20 岁"本来就互相矛盾。
  - LLM 裁决的取代 28 次，正确约 18 次（**约 64%**），错误主要是把能同时成立的事实判成了"更新"。
  - 错误的"已失效"标签会误导 reader：知识更新题里有 2 题因此答错（新值被标成了"不再成立"），而不标有效期的消融版本反而答对。
- **修订后的决策**：
  1. **规则只做精确的事**：同主语、同谓词、同宾语 → 合并溯源；陈述几乎相同且宾语一致 → 合并；否定已有的同宾语肯定事实（"不再喜欢……"）→ 取代；登记过的多值谓词 → 新增。
  2. **取代一律由 LLM 确认**：单值事实（登记过的或模型标注的）遇到同谓词或相似的已有事实、多值事实遇到高度相似的已有事实，交给 LLM 在 update / correct / duplicate / add 中选择。提示词明确"两条事实能同时成立就选 add，拿不准也选 add"。同一会话的灰区事实合并成一次调用，每条最多带 3 条候选。
  3. **取代分两种**：现实变了（update：搬家、换工作）时，旧事实的 `valid_to` = 新事实的开始时间；认知变了（correct：用户更正、补充细节）时，旧事实只设 `invalidated_at`，`valid_to` 保持为空——它在现实中并没有"结束"。单一时间轴区分不了"我搬家了"和"我说错了"。
  4. **相似度不能单独决定合并**：向量对数字和专名不敏感，"预算 8000 元"和"预算 6000 元"的余弦相似度可能很高，所以按相似度合并时还要求宾语一致。
  5. **时间先后的比较**：只有两条事实都带明确的事件时间时才按事件时间比较，否则按说出的先后。首轮里"参加了五次互助小组（事件时间 2022）"被拿去和"参加了三次（2023-05 说的，没有事件时间）"的说出时间比较，更新的计数反被判成迟到的旧消息。
- **备选**：每条事实都问 LLM（Mem0 式，贵且难审计）；只存原文不对账（冲突留给 reader，即 B2 的做法）；改进抽取提示让谓词更规范（会让 4,800 个会话的抽取缓存全部失效，留到下次升级流水线版本时一起做）。
- **后果**：对账的 LLM 调用增加（单值冲突也要确认），但每次只是一次很短的批量调用；每个决定都记录了来自哪条规则，可以审计。教训：**规则的前提（谓词标签可靠）要先验证**；结构化信息错了会主动误导模型，比没有更糟。
- **验证**：`tests/test_reconcile.py`、`tests/test_consolidate.py` 的场景测试；修订前后的 dev100 对比见 [N3 结果](results/n3-dev100-facts/README.md)。

## D-020 巩固流水线：抽取无状态、并行；对账有状态、串行；记录时间取对话时间

- **状态**：已采纳（N3）
- **背景**：一个 LongMemEval 记忆空间约 50 个会话。逐个会话"抽取 → 对账"串行处理太慢；而对账依赖之前所有会话的结果，不能随意并行。
- **决策**：
  - **拆成两段**：抽取只看会话本身（和会话日期），是无状态的，可以并行，并且命中响应缓存（不同题目共用的会话只抽一次）；对账、实体消歧依赖已有记忆，按会话时间顺序串行。中间一步把所有新陈述、实体描述、摘要一次性批量向量化。
  - **任务键** = 记忆空间 + 会话 + 会话内容指纹 + 流水线版本：同一任务只执行一次；会话追加了轮次、或抽取逻辑升级，任务键随之改变。版本变化时自动清空派生记忆并重放。
  - **原子写入**：每个会话的结果（事实、实体、片段、检索单元、任务状态）在一个数据库事务里提交；向量先写、数据库后写（沿用 D-012）。中途失败只需重跑，已完成的会话不会重复处理。
  - **记录时间取对话时间**，不取程序运行时间：重放结果确定、可复现。代价是"系统何时得知"指的是"用户何时说的"，与真实的入库时间不同；对记忆系统来说前者才有意义。
  - **迟到的旧消息不覆盖新状态**：如果新事实的事件时间早于当前事实（例如后导入一段更早的对话），它直接作为历史版本写入，失效时间取取代它的那条事实被说出的时间。测试验证了"先导入新会话、再导入旧会话"与"按时间顺序导入"得到相同的当前事实。
  - **抽取时助手回复只保留开头**（默认 600 字符）：LongMemEval 里助手回复占对话文本的 87%，而记忆主要关于用户；完整回复仍在原始日志和"轮"索引里，"助手说过什么"照样能检索到。
  - **后台线程**：在线写入只登记任务，`ConsolidationWorker` 在后台按空间串行执行，不阻塞对话；评测与命令行可以同步执行。
- **后果**：一个空间的巩固耗时约等于"最慢的几次抽取 + 串行对账"，而不是所有抽取之和；重建派生记忆几乎免费（全部命中缓存）。代价是要处理并行线程里的 trace 上下文传递（`contextvars.copy_context`），否则抽取成本不会被计入。
- **验证**：`test_consolidation_is_idempotent_and_replayable`、`test_late_arriving_old_session_does_not_override`、`test_background_worker`。

## D-021 遗忘 = 删除原始日志 + 重放派生记忆，并按归属清理缓存

- **状态**：已采纳（N3）
- **背景**：用户说"忘掉这件事"或在界面里删除时，必须删得干净（新加坡 PDPA、欧盟 GDPR 的被遗忘权）。难点在派生数据：一条事实可能取代过别的事实，删掉它之后，被取代的旧事实应该恢复为当前有效；实体、摘要、画像也都可能受影响。逐条追溯这些关系很容易漏。
- **决策**：
  1. **派生记忆是原始日志的函数**。遗忘 = 从日志里删除这些轮次 + 用剩下的日志重放派生记忆。重放命中缓存，未受影响的会话不需要重新抽取。
  2. **缓存同样要清**：LLM 响应缓存的每个条目带归属标签（抽取按会话、对账与回答按空间），遗忘时删除受影响会话的抽取缓存和该空间的对账、回答缓存；向量缓存删除"遗忘前有、遗忘后没有"的文本对应的条目——向量本身也可能泄露原文信息。
  3. **物理删除**：SQLite 打开 `secure_delete`，删除时覆写内容；遗忘结束后执行 `VACUUM`。测试直接读取数据库文件的字节，确认被删的词不存在（取证式测试）。
- **备选**：沿溯源关系逐条级联删除（实现复杂，取代关系的恢复容易出错）；只标记删除（不满足被遗忘权）。
- **后果**：正确性容易保证，测试也简单（遗忘后的状态应当等于"从没说过这段话"的状态）；代价是整个空间重放一遍。当前实现命中缓存后很快；空间很大时可以按会话做快照，只重放受影响会话之后的部分。
- **已知限制**：trace 文件里有提问和回答原文，目前没有随遗忘清理（N8 做服务时加上脱敏与保留期限）；Qdrant 本地模式的存储文件没有做字节级检查，但 payload 里本来就不存原文。
- **验证**：`tests/test_forget.py`。

## D-022 核心记忆是事实表的物化视图，由规则生成，不用 LLM 改写

- **状态**：已采纳（N3）
- **背景**：核心记忆（用户画像）每轮常驻上下文，内容必须准确。常见做法是让 LLM 把重要信息改写成一段画像，但改写可能编造内容，也可能和事实表不一致（事实被取代了，画像里还是旧的）。
- **决策**：画像 = 参与者（用户本人，或多人对话里的各位说话人）的重要度 ≥ 4、当前有效的事实，按重要度和新近程度排序，截断到约 400 tokens。事实一变就重新生成，不调用 LLM。
- **后果**：画像永远不会和事实表矛盾，每一条都能追溯到来源，生成零成本；代价是行文是逐条陈述，不如 LLM 改写流畅——对 reader 来说并无影响。
- **验证**：`test_core_memory_is_a_view_of_current_facts`；B2F 与"不给核心记忆"消融的对比。

## D-023 用 B2F 隔离写入路径的贡献：检索算法不变，只换写入结构

- **状态**：已采纳（N3）
- **背景**：N3 只做了写入路径，但需要在开发集上证明它有用。如果同时改检索算法，就分不清提升来自哪里。
- **决策**：新增方法 B2F，检索仍是 B2 的 dense top-k（k = 10），只是用上写入路径的产出：
  - **事实增强键**：事实与"轮"一起检索，命中的事实把分数传给它的来源轮（LongMemEval 论文的 key expansion：键是事实，值仍是原始对话）；
  - **带有效期的事实**：命中的事实连同时间和有效状态放进上下文，并沿版本链把新旧版本互相带出；
  - **核心记忆**常驻上下文。
  
  同时跑四个消融：只用事实增强键（不展示事实）、只给当前事实（相当于覆盖式更新）、事实不标有效期、不给核心记忆。
- **后果**：写入路径的贡献可以单独度量，后续 N4 的检索改进也有了清晰的对照；B2 本身保持不变（只检索"轮"），之前的结果可以直接复用。
- **结果**（dev100，详见 [N3 报告](results/n3-dev100-facts/report.md)）：B2 65% → B2F 80%（配对符号检验：+18 / −3，p = 0.001），与 ORACLE 83% 无显著差异；只用事实增强键 78%，只给当前事实 80%，不标有效期 80%，不给核心记忆 79%——四个消融与完整版的差异都不显著。检索层面：发言召回 87% → 96%，NDCG 58% → 80%。
- **跨数据集**：LoCoMo 前 3 段对话（385 题，未在其上调参）：B2 71.2% → B2F 77.7%（+42 / −17，p = 0.002），多跳 42% → 61%。
- **比较方式**：两种方法在同一批题上比较时用配对检验（只看"一个对、一个错"的题），比两个独立的置信区间灵敏得多：B2 与 B2F 的置信区间有重叠，但配对检验的 p = 0.001。脚本见 `scripts/paired_compare.py`。

## D-024 DeepSeek 错峰调度：批量任务在高峰时段暂停，花费估算计入错峰价

- **状态**：已采纳（N4 开始前）
- **背景**：DeepSeek 工作日 09:00–12:00、14:00–18:00（北京时间）为高峰，价格是其他时段的两倍。评测里 reader（deepseek-flash）是花费的大头，用户希望大部分调用落在便宜的时段。
- **决策**：
  - 供应商配置里声明高峰时段（`providers.deepseek.peak_hours`：时区、星期、时段、错峰系数 0.5）；没有分时价格的供应商（QwenCloud）不受影响；
  - LLM 客户端在真实调用之前检查：`peak_policy = wait` 时暂停到这一段高峰结束，命中本地缓存的请求不受影响；`warn` 照常调用并记录事件；`allow` 照常调用；
  - 评测（`cuemem eval run`）默认 `wait`，进入高峰时打印提示，可用 `--peak allow` 关闭；交互式命令（ask、ingest、consolidate）发的请求很少，用 `warn` 照常调用并提示一句；
  - 名义成本仍按高峰标价（D-010，保证不同时间的实验可比）；估算花费改为计入错峰折扣，预算保护按估算花费累计；
  - 工作安排：需要大量 DeepSeek 调用的评测放在清晨、午间（12–14 点）、晚上或周末；高峰时段写代码、跑离线测试。
- **后果**：同样的实验，实际花费最多可降一半，代价是评测可能被暂停几小时；可测试性靠注入时钟保证（测试不依赖运行时刻）。法定节假日未处理（按普通工作日算高峰），影响很小。
- **验证**：`tests/test_peak.py`。

## D-025 L1 融合：模态内按分数取最大，模态间用 RRF

- **状态**：已采纳（N4）
- **背景**：L1 要把三种粒度（轮、事实、会话摘要）和两种模态（dense、sparse）的检索结果合成一个"轮"的排序。RRF（倒数排名融合）是最常用的做法，最初的实现是每种单元、每种模态各自排名，全部做 RRF。
- **实测**：dev100 上纯检索评测（`scripts/tune_l1.py`，不调用 reader）：按单元类型全部 RRF 的发言 NDCG 只有 65.8%，比 N3 的 B2F（dense，事实键按余弦取最大）的 80.1% 还低 14 个点；"助手说过"类题从 79% 掉到 39%。原因是 RRF 只看名次、丢掉了分数大小：助手说的内容没有对应的事实，一条余弦很高的直接命中，被好几条名次中等的事实键叠加挤了下去。
- **决策**：先在**同一模态内部**按分数取最大值（轮自己的分数与它来源事实的分数取最大，即事实增强键；dense 的余弦在各类单元间本来可比，sparse 分数按各自列表的最大值归一化），再只在 **dense 与 sparse 两种模态之间**做 RRF（sparse 权重 0.5，网格搜索确定）。RRF 适合融合分数尺度不同的列表，不适合拆开本来可比的分数。
- **后果**：dense 部分与 B2F 完全一致（可作为正确性校验），加入 BM25 后发言召回（任一）95.7% → 100%，NDCG 基本持平（79.3% vs 80.1%）。按类型 RRF 保留为 `fusion="kind"` 的对照选项。
- **换用 qwen3.7-text-embedding 后复测**（dev100 纯检索，k = 10）：结论不变。按类型 RRF 的 NDCG 75.3%，模态内取最大 79.5%；"助手说过"类题 51.5% 对 95.5%。不用稀疏路时，L1 的排序与 B2F 仍然完全一致。

## D-026 稀疏路用 BM25，不用 text-embedding-v4 的词项权重

- **状态**：N4 采纳；**N5 复议后修订**：qwen3.7 下 L1、L2 默认都不用 BM25（实现保留为选项）；N4 的 B4 仍按原配置评测，结果可复现
- **背景**：text-embedding-v4 的原生接口同时返回稀疏向量（词项权重），N1 起就存进了 Qdrant；也可以在本地对文本建 BM25 索引。
- **实测**（dev100，纯检索，k = 10）：

  | 稀疏路 | 发言召回（任一） | 发言召回（全部） | 会话召回（全部） | 发言 NDCG |
  |---|---|---|---|---|
  | BM25 | 100.0% | 92.5% | 96.4% | 79.3% |
  | v4 词项权重 | 96.8% | 90.4% | 94.8% | 77.1% |

  端到端准确率：BM25 版 80%，v4 版 82%，配对差异不显著（p = 0.73）。
- **决策**：默认用 BM25。检索指标更好；分词可控（去掉每轮都有的 "User:" "Assistant:" 标签、数字整体保留、中文单字加二字组）；不依赖向量接口，离线可用、零成本，结果可解释（命中了哪些词）。
- **代价**：每个空间的 BM25 索引在内存里现建（LongMemEval 一个空间约 25 ms，之后按空间缓存，查询约 3 ms）；没有词形还原（"buy"匹配不到"bought"），留给 dense 路弥补。
- **换用 qwen3.7-text-embedding 之后**（D-014 修订）：qwen3.7 只取 dense，v4 词项权重这个选项不存在了，问题变成"还要不要稀疏路"。

  | 对比 | 带 BM25（B4） | 不用稀疏路 |
  |---|---|---|
  | dev100 纯检索（k = 10，不加时间分）发言召回（全部） / NDCG | 92.9% / 79.5% | 96.8% / 83.0% |
  | dev100 端到端 | 83% | 81%（B4 对 +5 / −3，p = 0.73） |
  | LoCoMo 385 题端到端 | 84.9% | 86.2%（B4 对 +10 / −15，p = 0.42） |

  纯检索上 BM25 反而让多会话与时间题的排序变差；端到端两个数据集方向相反，都不显著。dense 足够强以后，关键词路的边际价值消失了。N4 报告的数字保持评测前定好的配置（BM25 权重 0.5），不事后换默认值；N5 加入重排后，BM25 的角色是给重排提供候选，而不是直接参与排序，到时再决定去留。
- **N5 复议**（dev100 纯检索，94 道非拒答题，`scripts/tune_l2.py`；按 token 预算装入，指标是"发言召回（全部） / 发言 NDCG"）：

  | 配置 | 带 BM25 | 不用 BM25 |
  |---|---|---|
  | L1，预算 4k | 90.1% / 79.2% | 91.4% / 81.8% |
  | L1，预算 6k、最多 60 轮 | 92.2% / 80.2% | 95.6% / 83.7% |
  | L1 6k + 重排（qwen3-rerank，前 30 条） | 94.3% / 83.4% | 96.0% / 85.1% |
  | L2：查询规划 + 补检索 | 96.3% / 83.7% | 96.3% / 85.7% |

  BM25 在每个预算、有没有重排、单查询还是多查询下都不提高召回，多数情况下降低；它只在"L2 规划、不补检索"时让多会话题的召回高一些（87.6% 对 84.0%），补检索之后这点差别也没了。重排救不回来：作为重排的候选来源，加上 BM25 的召回反而更低。
- **修订后的决策**：L1 与 L2 的默认配置都不用稀疏路（`L1Config.sparse = "none"`）。BM25 的实现保留：向量模型较弱时它是有用的（text-embedding-v4 时就是）。B4 及其消融固定用 N4 的配置（带 BM25）评测，N4 的数字照样可以复现；N5 起"L1 的默认"等同于 B4-nobm25（dev100 81%、LoCoMo 86.2%，与 B4 的差异都不显著）。端到端不显著时，选纯检索指标更好、更简单、延迟更低的一边。

## D-027 时间感知：区间加分按宽度打折 + 相对时间打包；摘要先验与新旧加分默认关闭

- **状态**：已采纳（N4）
- **决策与依据**（dev100）：
  - **时间表达解析**：规则解析中英文时间表达，以**提问时间**为参照换算成区间（"两周前""上周六""in March""去年""5月20日""情人节"）。"today / tonight"在提问里通常指当下（"今晚看什么电影"），不当作检索线索。
  - **区间加分**：落在区间内的轮（或来源事实的事件时间在区间内的轮）加分，并按区间宽度打折（"上周六"全额，"过去两个月""去年"几乎不加）——宽区间覆盖大半历史，加分只会打乱排序。纯检索上时间题 NDCG 73% → 77%（qwen3.7），但"会话召回（全部）"下降：LongMemEval 的时间题会把几段相似的会话都标成证据，而题目只问其中一段，加分把答案顶上来、把干扰挤下去。dev100 里只有 12 道题带可解析的时间表达，LoCoMo 385 题里有 31 道；端到端都没有可测的差异（dev100 83% vs 不加分 84%，LoCoMo 两者相同）。代价几乎为零、可解释，保留默认开启；时间约束的完整处理交给 N5 的查询规划。
  - **相对时间打包**：每条证据标"距提问 N 天"。最终评测（qwen3.7）去掉后 dev100 83% → 79%（+5 / −1，p = 0.22），多会话题 54% → 42%、时间推理题 80% → 76%；LoCoMo 持平（+11 / −11）。text-embedding-v4 时也是同一方向（80% → 78%）。不显著但方向一致，保留。
  - **会话摘要先验、"最近 / 最早"新旧加分**：纯检索上都降低了 NDCG，默认关闭（保留开关，N5 的查询规划可能按问题类型启用）。

## D-028 评测提速：记忆空间落盘复用、纯检索调参、相同请求合并

- **状态**：已采纳（N4）
- **背景**：N3 起每次评测都要为每道题重建记忆空间（写入 + 巩固，全部命中缓存时 dev100 也要 5 分钟以上），而 N4 要反复调检索参数。
- **决策**：
  - **记忆空间落盘**：评测运行器把每道题的空间存在 `paths.eval_spaces` 下，下次运行直接复用（写入与巩固都是幂等的，复用时只是空操作）；`build.json` 记下首次构建时的写入与巩固统计，报告里的写入成本照样有数；向量模型或巩固配置变了时自动重建。dev100 的 100 个空间约 1 GB。
  - **纯检索调参**：`scripts/tune_l1.py` 直接在落盘的空间上跑各种检索配置，只算召回与 NDCG、不调用 reader，一轮 dev100 约 30 秒、零 LLM 成本，可以在 DeepSeek 高峰时段做。端到端评测只用来确认最终配置。
  - **相同请求合并（single-flight）**：多个线程同时发出同样的请求（不同题目共用的会话被同时抽取）时，只调用一次 API，其他线程等结果。
  - **续跑一致性检查**：同名运行会断点续跑。N4 换向量模型后误用了已存在的运行名，新结果差点混进旧目录（发现后立即停止、按原始行数恢复）。现在续跑前核对数据集、划分、向量模型与回答模型，不一致就报错，要求换运行名。
- **后果**：N4 的检索迭代从"每次几分钟加几美元"变成"每次半分钟、几乎零成本"。

## D-029 L1 上下文按 token 预算打包，而不是按固定条数

- **状态**：已采纳（N4）
- **背景**：B2、B2F 都是"取前 k = 10 轮"。但一"轮"的长度因数据集差很多：LongMemEval 的一轮是用户提问加助手的长回复，约 490 tokens；LoCoMo 是两个人的闲聊，一轮只有一句话，约 40 tokens。固定 k 会让两个数据集拿到的上下文差十几倍，在 LoCoMo 上，10 轮常常装不下多跳题需要的几处证据。
- **决策**：按 L1 的分数从高到低装入轮，直到用完 token 预算（默认 4k tokens，至少 1 轮，最多 40 轮）。事实（10 条，含版本链补齐）与核心记忆另算。
- **数据使用的说明**：这一项不是只在开发集上定的。text-embedding-v4 时的 LoCoMo 检查里，固定 10 轮的 B4（76.1%）不如 B2F（77.7%），这才引出了按预算打包；预算大小也同时看了两边：2k 在 dev100 上明显更差，在 LoCoMo 上与 4k 相当，所以取 4k。因此 LoCoMo 对 D-029 不是独立检验，N9 的最终评测（test400 与 LoCoMo 其余对话）才是。
- **实测**（qwen3.7-text-embedding；括号里是平均装入的轮数与每题输入 tokens）：

  | 配置 | dev100 | LoCoMo 385 题 |
  |---|---|---|
  | 固定 5 轮 | 82%（5 轮，3,908） | — |
  | 固定 10 轮 | 82%（10 轮，6,559） | 77.1%（10 轮，2,104） |
  | 预算 2k | 78%（4.7 轮，3,149） | 85.5%（37.7 轮，4,378） |
  | **预算 4k（默认）** | **83%（8.2 轮，4,973）** | **84.9%（40 轮，4,586）** |

  LoCoMo 上预算 4k 对固定 10 轮配对 +41 / −11（p < 0.001），多跳题 53% → 81%。dev100 上 4k 与固定 10 轮准确率相当，输入少 24%；2k 在 dev100 上少答对 5 题（p = 0.23，平均不到 5 轮，长回复题装不下证据）。
- **后果**：同一个配置在两种数据上都合适，不用按数据集调 k。LoCoMo 上实际起作用的是 40 轮的上限（40 轮只占约 2k tokens），这个上限没有在 LoCoMo 上调过。每题输入 token 随数据变化，所以检索质量表新增"平均轮数"一行：按预算装入的方法与固定 k 的方法，召回不能直接比较。

## D-030 L2 深度检索：查询规划 + 多查询"取最好名次"融合 + 充分性检查补检索 + 笔记式阅读

- **状态**：已采纳（N5）
- **背景**：N4 之后 B4 在 dev100 上答错 17 题，多会话题只有 54%（13 / 24）。错题有两类：一类是"一共几次 / 一共多少钱"这种聚合题，证据散落在多次对话里，L1 只找到一部分（多会话题的发言召回（全部）只有 71%）；另一类连只给证据会话的 ORACLE 也答错，是阅读与推理问题（数漏、重复计数、日期算错）。
- **决策**（各组件的默认值先在 dev100 的纯检索上定，再跑端到端）：
  1. **查询规划**：一次 qwen3.8-flash 调用，给出答案类型、是否需要穷尽、1–4 个子查询、时间区间、目标实体；失败时退回规则版计划。
  2. **多查询融合用"取最好名次"**：每条候选取它在各查询里最好的名次分，再加 0.1 倍的名次分之和打破平局。子查询各找一块信息，每块的最佳命中都应该进入上下文；名次分直接求和（RRF）奖励的是"几个查询里都排中游"的轮。
  3. **预算 6k tokens、最多 60 轮**；计数、求和、列举类问题给 25 条事实（L1 是 10 条）。
  4. **充分性检查**：最多 2 次，每次一次 qwen3.8-flash 调用；不够时按它给的查询补检索，每次再装入 1k tokens。
  5. **笔记式阅读**：系统提示不变，上下文末尾加阅读提示，输出先写笔记再作答（见设计文档 §6.5）。
  6. 图扩散、重排、BM25 默认都不用（D-031、D-032、D-026 修订）。
- **纯检索**（dev100，94 道非拒答题，发言召回（全部） / NDCG / 多会话题召回）：

  | 配置 | 召回（全部） | NDCG | 多会话题 | LLM 调用 / 题 |
  |---|---|---|---|---|
  | L1，4k（B4） | 90.1% | 79.2% | 70.9% | 0 |
  | L1，6k、60 轮（带 BM25） | 92.2% | 80.2% | 77.8% | 0 |
  | L1，6k、60 轮，不用 BM25 | 95.6% | 83.7% | 85.0% | 0 |
  | 规划，名次分求和（RRF） | 92.5% | 80.2% | 76.8% | 1 |
  | 规划，取最好名次 | 95.4% | 83.3% | 87.6% | 1 |
  | 规划 + 补检索，不用 BM25（B5 的检索） | 96.3% | 85.7% | 89.9% | 2.2 |

  RRF 融合的多查询完全没有收益，换成"取最好名次"后多会话题召回 +10 个点。但要如实看：同样 6k 预算，单查询的 L1 去掉 BM25 就能到 95.6%，L2 的检索只再多 0.7 个点（多会话题多 5 个点）。

- **端到端**（dev100，100 题，同一个 reader 与 judge）：

  | 方法 | 准确率 | 多会话 | 时间推理 | 名义成本 / 题 | LLM 调用 / 题 |
  |---|---|---|---|---|---|
  | B4（N4 的 L1） | 83% | 54% | 80% | $0.0016 | 1.00 |
  | B4-nobm25（N5 起的 L1 默认） | 81% | 58% | 72% | $0.0016 | 1.00 |
  | B4-b6k：L1 给 6k 预算 | 85% | 58% | 80% | $0.0022 | 1.00 |
  | B4-note：L1 + 先记笔记 | 86% | 62% | 84% | $0.0019 | 1.00 |
  | **B5：L2** | **89%** | **79%** | **84%** | **$0.0034** | **3.25** |
  | B5-noplan：不做查询规划 | 88% | 79% | 84% | $0.0033 | 2.29 |
  | B5-noiter：不做充分性检查 | 85% | 62% | 84% | $0.0026 | 2.00 |
  | B5-nonote：不记笔记 | 81% | 58% | 72% | $0.0031 | 3.25 |
  | B5-ppr：加图扩散 | 88% | 71% | 84% | $0.0034 | 3.26 |

  配对符号检验：B5 对 B4 +10 / −4（p = 0.18），对 B4-nobm25 +11 / −3（p = 0.057）；多会话题对 B4 +8 / −2（p = 0.11）。消融：不记笔记 −8（+12 / −4，p = 0.077），不补检索 −4（+4 / −0，p = 0.13），不做规划 −1，加图扩散 −1。

- **怎么解读**：
  - **最大的杠杆是阅读方式，不是检索**：同样的 L2 证据，不记笔记只有 81%；L1 的证据加上笔记就有 86%。"ORACLE 也答错"的阅读类错题从 B4 的 11 题降到 B5 的 6 题。计数题的笔记里，模型会逐项列出每次看房、每张专辑，再去重计数。
  - **检索上真正起作用的是补检索**：补检索救回来的 4 题都是"散落在多次对话里"的计数或时间题（看过几个医生、预约前一天几点睡），检查模型给出的补充查询都很对路。
  - **查询规划的子查询在纯检索上提升明显，端到端几乎没有**：没有规划时，充分性检查自己会提出补充查询，起到了同样的作用（B5-noplan 的纯检索召回反而略高）。
  - **误拒答减少**：有答案的题回答"不知道"，L1 6 次，B5 1 次（按措辞粗略识别）。
- **成本与延迟**：B5 每题名义成本 $0.0034，是 L1 的 2.1 倍；平均 3.25 次 LLM 调用（规划 1 次、检查 1.25 次、回答 1 次），输出 tokens 从 87 涨到 405（笔记）。回答端到端延迟 p50 1.8 秒、p95 6.2 秒（L1 约 1 秒）。
- **LoCoMo 检验**（前 3 段对话，385 题；L2 的所有默认值都只在 dev100 上定，LoCoMo 没有参与任何调参）：

  | 方法 | 准确率 | 多跳 | 时间 | 名义成本 / 题 |
  |---|---|---|---|---|
  | B4（N4 的 L1） | 84.9% | 81% | 87% | $0.0015 |
  | L1（B4-nobm25） | 86.2% | 80% | 88% | $0.0015 |
  | B4-note：L1 + 先记笔记 | 88.6% | 84% | 92% | $0.0017 |
  | **B5：L2** | **89.1%** | **88%** | **93%** | **$0.0032** |
  | B5-nonote：不记笔记 | 86.8% | 86% | 87% | $0.0030 |
  | ORACLE | 87.5% | 74% | 91% | $0.0005 |

  B5 对 B4 +27 / −11（**p = 0.014**），对当前 L1 +21 / −10（p = 0.071）；多跳题对当前 L1 +10 / −4（p = 0.18），时间题 +5 / −0（p = 0.06）。笔记式阅读的方向与 dev100 一致：L1 加上笔记就到 88.6%，B5 对它只多 2 题（+8 / −6）。误拒答：L1 12 次，B5 6 次。
- **验收**：路线图要求"多会话推理、时间推理显著提升"。两个数据集上方向都一致（dev100 多会话 +8 / −2、时间 +1 / −0；LoCoMo 多跳 +10 / −4、时间 +5 / −0），但分题型都没有到 p < 0.05；整体只有 LoCoMo 上对 B4 显著。最终以 N9 的 test400 与 LoCoMo 其余 7 段对话为准。
- **另一个代价**：笔记式阅读让回答更长（LoCoMo 平均 33 → 41 个词），按 LoCoMo 原论文的 token F1 计反而下降（0.236 → 0.195）。F1 惩罚长回答，本项目以 LLM 判分为主指标，F1 只作参考。

## D-031 图扩散（个性化 PageRank）：实现了，默认不开

- **状态**：已实现，默认关闭（N5；回答了设计文档 §11 "图结构用三部图还是只用实体图"）
- **背景**：设计里 L2 的多跳手段是 HippoRAG 式的实体图扩散：以问题点名的实体为种子，在"实体—事实—片段"图上跑个性化 PageRank，一步召回多跳相关的事实与片段。
- **先看图本身**：只用巩固时抽取出的实体关系，图上几乎没有边可走。dev100 的一个空间平均约 230 条事实、150 个实体，"用户"本人连着约 95% 的事实，其余实体的中位度数是 1；LoCoMo 每段对话的两位说话人各连着 39%–56% 的事实。所以图做了三处改动：
  - 节点用实体、事实、轮三类（三部图），边有四种：事实—实体、事实—来源轮、实体名在原话里出现的提及边（抽取只把少数关系记成事实，原话里提得更多）、语义相近的事实之间的边（余弦 ≥ 0.8，每条最多 5 个邻居，把散落在不同会话的同类事实连起来，相当于结构化的伪相关反馈）；
  - 连着超过 20% 事实的枢纽实体不进图：经过它们的扩散等于把分数均匀撒开；
  - 种子 = 问题与计划里点名的实体（越专指权重越高）+ 第一轮融合后排在前面的 10 条事实与 5 轮；d = 0.5，scipy.sparse 迭代，几百个节点几毫秒。图扩散作为一路排名，以 0.5 的权重并入融合。
- **实测**（dev100 纯检索，与"查询规划、不补检索"相比；指标为发言召回（全部） / NDCG / 多会话题召回）：

  | 配置 | 召回（全部） | NDCG | 多会话题召回 |
  |---|---|---|---|
  | 查询规划，不做图扩散 | 95.4% | 83.3% | 87.6% |
  | + 图扩散（四种边） | 95.2% | 84.1% | 86.9% |
  | + 图扩散（只用抽取出的边） | 95.5% | 83.8% | 87.8% |
  | + 图扩散（不连相似事实） | 95.0% | 83.9% | 85.9% |
  | + 图扩散，权重 1.0 | 95.2% | 81.1% | 86.9% |
  | 查询规划 + 补检索，再加图扩散 | 96.3% → 96.4% | 83.7% → 84.6% | 90.9% → 91.4% |

  所有变体的召回差异都在 ±0.5 个点以内。证据按时间排序展示，排序只决定"哪些轮装得进预算"，NDCG 的小幅变化对 reader 没有意义。
- **决策**：默认关闭，保留为选项（`L2Config.ppr`）。LongMemEval 的多会话题主要是"同一类事情散落在多次对话里"（买过几件首饰、修过几样厨房用品），靠的是把同一类事情找全，不是沿实体关系跳几步；这件事子查询与补检索做得更直接。dev100 端到端：B5-ppr 88%，B5 89%（+1 / −2）。LoCoMo 的多跳题更依赖人物关系，所以在 LoCoMo 上另跑一个预先声明的变体 B5-ppr 作检验。
- **LoCoMo 检验**（385 题）：B5-ppr 90.1%，B5 89.1%（+8 / −4，p = 0.39）；多跳题 91% 对 88%（+3 / −1）。对当前 L1，B5-ppr +22 / −7（p = 0.008），多跳题 +10 / −2（p = 0.04），比不加图扩散的 B5（+21 / −10、+10 / −4）更稳。方向与"实体关系更稠密的数据上图扩散更有用"一致，但对 B5 的差异不显著，默认值不因检验集的结果改变；N9 用 LoCoMo 其余 7 段对话（没看过的数据）再测一次。
- **为什么在这里不灵**：图扩散的上限由图的质量决定，而对话抽取出的实体图是"一个人连着所有事"的星形图；PPR 适合实体关系稠密、需要桥接实体的多跳问答。

## D-032 重排（cross-encoder）：不采用

- **状态**：已实现，不采用（N5）
- **实现**：QwenCloud 的 qwen3-rerank（原生接口，$0.10 / 百万 tokens），对融合后的前 30 条候选打分，最终名次 = 融合名次与重排名次的 RRF；结果进响应缓存，用量记账。
- **实测**（dev100 纯检索，发言召回（全部） / NDCG）：查询规划 95.4% / 83.3%，加重排 95.2% / 84.7%；L1 6k 不用 BM25 95.6% / 83.7%，加重排 96.0% / 85.1%。召回基本不变，NDCG 提高 1–1.5 个点。成本：LongMemEval 一轮约 490 tokens，30 条候选每题约 1.5 万 tokens，约 $0.0015，是查询规划的 10 倍，与 B4 整题的回答成本相当；延迟加几百毫秒。
- **决策**：不采用。原因是打包方式：证据按时间排序展示，排序只决定哪些轮装得进预算，衡量它的是"预算内的召回"，而重排没有提高这个指标；NDCG 的提高只是预算内部的顺序，对 reader 没有影响。实现保留，供以后"证据按相关度排序"或预算更紧的场景使用。
- **附带结论**：重排没有让 BM25 变得有用（D-026 修订）。

## D-033 N7 的两个基线：规则版控制器（B6r）与模型自主检索（B3）

- **状态**：已采纳（N5）
- **背景**：核心问题（D-001）是"要不要检索、检索多深"由谁决定。N7 要训练可学习的控制器，需要先有两条基线：最简单的外部策略（规则），以及把决定完全交给 LLM 的做法（ReAct 式自主检索）。N5 有了 L1、L2 两档之后就能实现它们。
- **决策**：
  - **B6r 规则版控制器**：只看问题里的线索，不调用 LLM、不看检索结果；问计数或聚合（how many、total、几次……）、时长（how long、几天）、先后（first、last、before、after，排除 "last week" 这类时间表达）、比较（more、most……）时走 L2，其余走 L1。规则在看到 L2 的逐题结果之前写定。L1、L2 两条路径与 B4-nobm25、B5 完全相同，回答直接命中它们的缓存，成本按实际走的路径计。
  - **B3 模型自主检索**：reader（同一个 deepseek-flash、同一套系统提示）带 `memory_search`（L1 检索，每次 2k tokens，跨次去重、编号连续）与 `date_diff` 两个工具，再加一个 `answer` 工具交卷；最多 5 步，最后一步点名要求调用 `answer`。只限制可用工具不够：最后一步只给 `answer` 时，DeepSeek 仍会照着历史里出现过的工具名继续调用 `memory_search`，第一版因此在多步之后全部回答"不知道"。点名之后仍不交卷的（100 题里 3 题），用标准 reader 读它检索到的全部记忆作答，并在结果里注明。
- **dev100 结果**：

  | 方法 | 准确率 | 名义成本 / 题 | LLM 调用 / 题 | 说明 |
  |---|---|---|---|---|
  | L1（B4-nobm25） | 81% | $0.0016 | 1.00 | |
  | B6r 规则版控制器 | 88% | $0.0028 | 2.45 | 62% 的题走 L2 |
  | B5 always-L2 | 89% | $0.0034 | 3.25 | |
  | B3 模型自主检索 | 86% | $0.0033 | 2.59 | 平均检索 2.8 次 |
  | 理想路由（每题选最便宜且答对的一档，事后看答案） | 92% | $0.0019 | — | 不可部署，N7 的上限 |

  B6r 对 L1 +8 / −1（p = 0.039），对 B5 −1（+2 / −3），成本低 18%。走 L2 的 62 题里答对 90%，走 L1 的答对 84%；多会话类的 27 题（含 3 道拒答题）里 26 题走 L2，单会话题几乎都走 L1。B3 对 L1 +5（p = 0.30），对 B5 −3（p = 0.55）。
- **成本口径的说明**：名义成本按全部输入计价（D-010）。B3 每一步都把前面的对话重新发一遍，DeepSeek 的前缀缓存命中了 46% 的输入 tokens，按缓存价计算每题约 $0.0020；B5 的各次调用之间没有这种重复。比较 B3 时两种口径都要看。
- **LoCoMo**（385 题）：B6r 只把 30 题（8%）送到 L2，准确率 86.0%，与 L1（86.2%）几乎一样，比 always-L2 少 12 题（+9 / −21，p = 0.043）；理想路由 91.7%、每题 $0.0016。规则看的是计数、时长、先后、比较这类措辞（how many、how long、first……），LongMemEval 的多会话题和时间题大多带这些词；LoCoMo 的多跳题（"Caroline 可能会选什么专业？"）几乎不带：74 道多跳题里只有 5 道走了 L2。只看问题措辞的规则不能跨数据集迁移，这正是 N7 要用检索探针特征、做跨数据集评测的原因。B3 只在 dev100 上跑（成本与 N7 的计划）。
- **后果**：在 dev100 上，规则版控制器拿到了 L2 的大部分收益；在 LoCoMo 上它几乎不触发、等于 L1。两个数据集上理想路由都在 92% 左右、成本接近 L1，说明"何时升级到 L2"还有很大的空间，这是 N7 可学习控制器要做的事，规则版是它必须超过的基线。B3 在这个强 reader 上不差，但调用次数和延迟不可控（检索 0–10 次），N7 会把它作为"让 LLM 自己决定"的代表做正面比较，并在更小的 reader 上复测（H3）。

## D-034 MemLens 的接入：开发集取子集之外的题，官方 195 题整体留作测试；判分用官方提示词

- **状态**：已采纳（N6；修订了设计文档 §8.1 "从 195 题子集里划出约 45 题做开发"）
- **数据**：MemLens（arXiv 2605.14906，CC-BY-4.0）789 题，五种能力（信息抽取 / 多会话推理 / 时间推理 / 知识更新 / 拒答），同一批题按对话历史长度分 32K、64K、128K、256K 四档；图片附在发言上，共 4,695 张（中位尺寸约 390×280）。格式与 LongMemEval 相同，证据只标到会话。32K 档每题约 13.5 个会话、12.8 张图；128K 档约 47 个会话、48 张图。
- **划分**：原计划从官方的 195 题记忆智能体子集里划 45 题做开发，太少。改为：子集之外还有 594 题，从中按题型分层抽 100 题作开发集（`memlens_dev100`），195 题子集（`memlens_agent195`，61 / 35 / 48 / 29 / 22）整体留作测试集，便于与论文里的 7 个记忆智能体比较。两套划分没有重叠；划分文件对 32K、128K 两档通用。
- **判分**：逐字照搬官方 `llm_judge.py` 的提示词（按题型给评分标准与例子，`src/cuemem/evals/memlens_prompts/`，MIT 许可），输出 `{"answer_score": 0/1}`；超过 500 词的回答按官方做法直接判 0。官方判分模型是 Qwen3-VL-235B，QwenCloud 上没有，用与其他数据集相同的 qwen3.8-max（与 DeepSeek 的回答模型不同家族）。数字与论文横向比较时要注明这一差异。判分提示词约 1,750 tokens，每次名义 $0.004；QwenCloud 的隐式前缀缓存命中约 1,024 tokens 后，实际约 $0.0022。
- **构建与回答分开**：`cuemem eval run --build-only` 只做写入与巩固（全部用通义的模型：向量、图片向量、图片描述、事实抽取），可以在 DeepSeek 高峰时段跑；回答与判分放到非高峰。巩固时遇到通义内容审核误拒，兜底用 deepseek-flash，在高峰时段会暂停到 18:00（32K 开发集 3 / 100 份、32K 测试集 12 / 195 份、128K 测试集约 20 份）。线程会被这些暂停占住，128K 的构建因此改用 24 个线程，暂停的空间各占一个线程，其余照常推进。
- **评测中发现并修复**：QwenCloud 在 JSON 模式下偶尔中止生成（400 "Model output became abnormal"），同样的请求重发多半还会中止。结构化输出遇到它时补一句提示、换一个请求重试；单张图描述失败不再让整份历史的巩固失败。

## D-035 图片写入：原图按内容哈希存放，描述在巩固时生成（上下文感知 + 孤立两种），并填回原话参与事实抽取

- **状态**：已采纳（N6）
- **决策**：
  - **在线写入**（不调用 LLM）：原图按 SHA-256 存进媒体库（同一张图只存一份），每次出现记一条图片记录（同一张图在不同发言里上下文不同）；用 tongyi-embedding-vision-plus 算图片向量（1152 维，与文字同一个向量空间），每个记忆空间另建一个图片向量集合。
  - **巩固**：每张图生成两种描述——**上下文感知**（模型同时看图和前后各一条发言）与**孤立**（只看图），外加图中文字与关键词。模型用 qwen3.8-flash：实测能读图，单价最低，写入不在读路径上，不受 DeepSeek 高峰影响。两种描述都作为检索单元（`image`、`image_iso`），像事实一样指回原话所在的轮；孤立描述只用于对比实验。
  - **实体绑定**：抽取事实时，把上下文感知描述填回原话里图片的位置（`[Image: 描述 Text in the image: …]`），图片里的信息因此也进入事实与实体（"用户在 Oxford Street 拍到一辆 390 路红色双层巴士"）。不带图的会话渲染结果与之前逐字相同，LongMemEval、LoCoMo 的抽取缓存照常命中，流水线版本不变。
  - **遗忘**：删除发言时一并删除图片记录与图片向量；原图文件没有其他记录引用时删除。
- **成本**（MemLens 32K dev100，100 份历史、1,279 张图、1,205 个不同的会话）：构建实际花费 $1.28，其中通义对话模型（描述 + 抽取 + 对账）$1.07、文本向量 $0.20、图片向量 $0.008。图片描述一次平均输入 652 tokens（图片 + 前后对话 + 提示词）、输出 147 tokens，每张图两种描述约 $0.00033。128K 测试集 195 份 $7.95（每份约 $0.04）。
- **描述的作用**（dev100 端到端）：加上下文感知描述，对纯文本记忆 +13 / −3（p = 0.021），38% → 48%；"不知道"式的误拒答 48 → 30 次。
- **上下文感知 vs 孤立（H6）：没有得到支持**。检索上上下文感知描述略好（关键图片所在轮的召回 65.1% 对 60.7%），端到端反而是孤立描述多对 3 题（51% 对 48%，+7 / −4，p = 0.55）。例子里能看到原因：上下文感知描述会写出图片在对话里的含义（"用户提到的、上一段感情留下的礼盒""用户说自己喜欢的那副图案简洁的塔罗牌"），孤立描述把同样的字数都用在画面细节上；MemLens 的题大多问画面细节（颜色、数量、图中文字）。默认仍用上下文感知描述：它帮助检索，也把图片和对话里的实体绑在一起（事实抽取的输入）；"描述里该写多少对话含义、多少画面细节"留到 N9 用更有针对性的题检验。

## D-036 图片检索：描述作检索键，再加一路以文搜图（默认开启）

- **状态**：已采纳（N6）
- **背景**：图片的信息在检索时只有两条路能用上：描述（文字）与图片向量。MemLens 每道题的关键图片放在 `needle_images/` 下，可以直接衡量"关键图片所在的轮有没有装进上下文"。
- **实测**（dev100 中已构建完成的 89 道非拒答题，75 道的证据会话里有关键图片；`scripts/tune_mm.py`，只用通义的向量接口）：

  | 配置 | 会话召回（全部） | 关键图片所在轮的召回 |
  |---|---|---|
  | 纯文本（图片只留占位） | 90.9% | 51.2% |
  | 对话 + 上下文感知描述 | 90.9% | 64.2% |
  | 对话 + 孤立描述 | 90.2% | 60.1% |
  | 对话 + 描述 + 事实 | 92.5% | 56.5% |
  | 对话 + 描述 + 事实 + 以文搜图 ×0.5 | 92.6% | **85.3%** |
  | 只用以文搜图（不用描述键） | 94.1% | 85.4% |

  - 描述让关键图片所在轮的召回 +13 个点；上下文感知描述比孤立描述多 4 个点（H6 在检索上方向成立）。
  - 事实键会把预算让给别的轮，多会话题上关键图片的召回从 48% 掉到 26%。
  - **以文搜图是最大的杠杆**：+29 个点，多会话题 26% → 80%、知识更新 48% → 78%。问题里的视觉线索（"那辆红色巴士""收据上的金额"）与图片本身在图文向量空间里很近，而描述只是有损的文字转述。
- **决策**：L1 默认开启以文搜图（作为与 dense、sparse 并列的第三种模态参与 RRF，权重 0.5）。空间里没有图片时这一路自动跳过，不增加延迟与成本，LongMemEval、LoCoMo 的结果不变。描述键保留：只用以文搜图时召回相同，但描述还要作为可读的证据给 reader。
- **端到端：检索提高了，准确率没有**。

  | 对比（去掉以文搜图 → 默认） | 关键图片所在轮的召回 | 准确率（配对） |
  |---|---|---|
  | dev100：B4-novis → B4-mm | 57.0% → 86.2% | 52% → 51%（+2 / −3） |
  | dev100：B4-see-novis → B4-see | — | 61% → 58%（+3 / −6，p = 0.51） |
  | 测试 32K：B4-see-novis → B4-see | 61.7% → 87.2% | 62.6% → 63.1%（+8 / −7） |
  | 测试 128K：B4-see-novis → B4-see | 53.6% → 72.0% | 57.4% → 55.9%（+8 / −11，p = 0.65） |

  事先声明的"历史越长、以文搜图越有用"在 128K 上也没有出现。可能的原因：以文搜图找来的是"看起来像"的图，所在的轮挤掉了预算里别的证据（装入的轮数少 1–2 轮）；而关键图片本身，描述键与事实已经能把它附近的对话找回来，回答需要的往往是对话里的信息加上看清图。默认值是在端到端之前按开发集的纯检索定的，不因为测试集的结果改；它的价值可能在"挑哪几张原图附上"而不是"装哪几轮"，留给 N7（控制器决定要不要用、用在哪）与 N9 复核。

## D-037 回答时再感知：附上相关度最高的 3 张原图

- **状态**：已采纳（N6；验证了假设 H5）
- **背景**：MemLens 论文的发现是：长上下文模型能直接看图，但随长度退化；记忆智能体对长度稳定，但写入时把图压缩成文字，丢了视觉细节。设计上的折中是"索引时压缩 + 回答时再感知"（D-003）：检索与阅读都基于描述，需要细节时把原图取回来再看一眼。
- **决策**：装入上下文的轮里的图片按相关度排序（描述键与以文搜图的名次），取前 3 张，缩放到最长边 768 像素，附在文字证据之后、问题之前；文字里在对应位置注明"see picture k"。回答模型仍是 deepseek-flash（实测能读图），方法之间只差"给不给原图"。是否附图目前是方法级的开关（B4-see、B5-see），N7 交给控制器按问题决定。
- **实测**：

  | 对比（配对） | dev100（32K） | 测试 32K | 测试 128K |
  |---|---|---|---|
  | B4-see 对 B4-mm（再感知） | +8 / −1，p = 0.039 | +26 / −2，p < 0.001 | +19 / −5，p = 0.007 |
  | 准确率 | 51% → 58% | 50.8% → 63.1% | 48.7% → 55.9% |
  | 信息抽取题 | 45% → 71% | 41% → 72% | 44% → 69% |
  | 误拒答（"不知道"） | 25 → 14 | 49 → 20 | 45 → 24 |

  提升集中在信息抽取题：颜色、数量、图中文字、位置关系这类细节，描述写不全，看原图才答得出。
- **成本**：每题多约 670 个输入 tokens（3 张图，每张约 220 tokens；MemLens 的图中位尺寸约 390×280），名义成本 +$0.0002，约 +11%；延迟 p50 +0.2 秒。对照：全上下文直接看图每题 2.7 万（32K）到 13.5 万（128K）tokens。
- **长度稳定性**（同一批 195 题从 32K 换到 128K，配对）：B1 全上下文 52.3% → 46.2%（+4 / −16，p = 0.012），成本涨 5 倍；L1 的 B4-see 63.1% → 55.9%（+8 / −22，p = 0.016，证据会话的召回 93% → 80%）；L2 的 B5-see 65.6% → 64.6%（+14 / −16，p = 0.86，会话召回 89%）。"记忆系统对长度稳定"不是自动成立的：L1 的单次检索在长历史里同样会丢证据，靠 L2 的子查询与补检索才稳住。
- **与只给证据会话的 ORACLE 比**：B5-see 在 32K 上比 ORACLE 高 10 个点（+30 / −11，p = 0.004）。ORACLE 一次给出全部证据会话与其中所有图片，回答模型要在长对话和十几张图里自己找；B5-see 给的是事实、带描述的片段、挑过的 3 张原图，外加先记笔记再回答。"给对的东西"比"给全部相关的东西"更好。
- **参照**（判分模型不同，不能直接比较）：论文里最强的长上下文模型在全部 789 题、32K 上是 58.68%，128K 上表现最好的 Gemini-3.1-Pro 是 51.99%；多会话推理上多数系统低于 30%。本项目 B5-see 在 195 题子集上 65.6% / 64.6%，多会话题 49% / 49%。
